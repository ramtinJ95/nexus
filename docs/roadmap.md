# Nexus roadmap

This page lists the work planned for Nexus and its clients: the web dashboard, the Claude Code mod in `claude-mods`, and the `pi-nexus` extension. When an item lands, take it off this page and update the docs that describe the behaviour. Decisions go in [the design's decision table](design.md#decisions), and unknowns that need a spike go under [open questions](design.md#open-questions).

Several items copy ideas from [t3code](https://github.com/pingdotgg/t3code), which is MIT licensed. Code copied from it keeps its copyright notice beside the code.

## Next

- **Live checks on a verify pylon.** The merge policy's live check has no place to run, so every landing relies on the pull request saying what it could not check live. [The open question](design.md#open-questions) weighs where a verify stack could run and recommends a verify pylon that loads the KVM modules its kernel already ships, which nested virtualization on `rj-firebat` and `infra-testbench` allows. The image recipe loads them on every boot whose boot spec asks for nested virtualization, and fails that boot when no `/dev/kvm` results. Next, the control plane asks for it when it starts a verify pylon, and the review loop starts the stack after `.nexus/check` passes and records the result for the policy.
- **The review loop uses the builder's own reviewer.** A Claude worker now has a shepherdr reviewer check its diff in its own pylon before a pull request. [The proposal](design.md#proposal-the-review-inside-the-builders-thread) moves `nexus review`'s rounds for a Claude worker into its thread, with the control plane keeping `.nexus/check`, the round cap and landing. An in-thread approval can be forged by the builder, so landing still needs a verdict from outside the pylon. Build it once the open changes to `src/control/review.ts` land.
- **The clients use the attention status, the seen marker and the latest-turn base.** The mod and pi-nexus drop their own seen stores (the mod's store and `pi-nexus/viewed.json`) and read the control plane's fields instead.

## The orchestration wave

Run the whole build pipeline on Nexus, with no coordinator chat on the Mac. On 2026-10-25 and 2026-10-26 dozens of pull requests landed this way: Nexus threads built them, Nexus reviews checked them and agents deployed them. A Claude Code chat on the Mac still did the orchestration, helped by two pi workers there: one polled the threads for news, the other ran deploys and read the nodes. That chat picked items from this page, wrote each builder's brief, started builder threads, started `nexus review`, merged under [the merge policy](merge-policy.md), ran `nexus deploy --wait`, started short-lived threads to check a deploy live, gathered evidence over SSH when a pylon's controller crashed, archived finished threads, kept its state in notes, and brought the person only real decisions. It moved only while it had a turn, and stalled whenever it waited on the person. On 2026-10-25 it stopped three ways: it asked the person about calls it could have made, such as merging a reviewed PR whose live check couldn't run locally; a thread stopped at a draft and no one noticed until it was read; and a deploy needed a sudo password. The person decides the shape and starts the wave. Live checks on a verify pylon, under Next, come first. Reviews already start on their own in a project that asks for it, and land, rebasing a branch that conflicts. A builder in such a project that ends its turn with no pull request gets a nudge, and after two its attention goes to the person. A review that lands archives its builder and its reviewer. Pipeline items line up work ahead: each becomes a queued thread once the items before it are, and starts once their pull requests merge, with its phase on the dashboard's Pipeline page.

- **A coordinator that runs inside Nexus.** The control plane's passes take over what the Mac chat did: they start builders from the person's items, start reviews, land within the merge policy, deploy, check the deploy and clean up. They wake on events instead of holding a turn, and they keep their state in the registry instead of a chat's notes, so they survive a restart and need no laptop. The coordinator is deterministic code, not an agent, because a Nexus thread never starts, messages, waits on or drives another thread, as the person decided on 2026-10-28. An agent that needs helpers runs them in its own pylon, and a call that needs a model goes to a short-lived judgment thread whose brief holds every fact it needs. [The orchestration exploration](explorations/orchestration.md) surveys how other tools orchestrate, weighs the shapes and plans the steps left, among them how a planning thread proposes items, which is the person's call.
- **Wake-ups from the event stream.** The Mac's watcher polled every thread and reported by ending its turn. The coordinator should wake on the events that matter instead: a builder's turn ends or fails, a pull request opens, a review ends, a deploy finishes, or a node's pylon crashes. The stream and the background follower exist, but nothing inside Nexus consumes them yet. This is the control plane's side of the event consumers under Later.
- **Asking the person through the attention status.** The coordinator should bring the person only the calls the merge policy reserves for them, such as image rebuilds, secrets and the egress allowlist, and wait without stalling the rest of the pipeline. A question shows on the dashboard as a card the person answers there, like the AskUserQuestion card in the dashboard wave, and the answer wakes the coordinator.

## The dashboard wave

Planned for later, as one wave of interface work. The person scopes it and starts it, and has more changes in mind than this list holds yet. Add them here as they come up.

- **Decide whether a desktop app becomes the main interface.** Neither the client mods nor the web dashboard feels good enough as the place to work with threads. [The desktop app exploration](explorations/desktop-app.md) compares building a Nexus app from [t3code](https://github.com/pingdotgg/t3code)'s MIT code, adapting t3code or [Jetline](https://github.com/MartinRybergLaude/jetline) so that Nexus threads appear in them, and keeping the web dashboard and closing its gaps. It recommends the dashboard. Both apps assume the machine their server runs on owns the checkout, the terminals and the agent, which a pylon breaks. A browser terminal on the thread page already works over the attach route. The gaps are a terminal drawer, pushed updates instead of polling and an installable window. Previews over HTTPS already landed in [nexus#87](https://github.com/ramtinJ95/nexus/pull/87), latest-turn snapshots for Claude worker turns in [nexus#91](https://github.com/ramtinJ95/nexus/pull/91), highlighted diffs in [nexus#94](https://github.com/ramtinJ95/nexus/pull/94), and review notes on the diff in [nexus#97](https://github.com/ramtinJ95/nexus/pull/97). A native shell would come later, and only if notifications must arrive with no dashboard window open. The person decides. Settle this before the rest of this wave, which would otherwise land in an app instead. Their API and probe parts serve any client, as the Claude transcript route already does. This overlaps with the orchestration wave above, which asks what the person's interface to every pylon should be.
- **Answering AskUserQuestion from the dashboard.** When a Claude worker calls AskUserQuestion, its thread shows "waiting for input", but the dashboard shows neither the questions nor their options, so the only way to answer is to attach a terminal. The PreToolUse hook already carries the questions, headers, options, previews and the multi-select flag, and PostToolUse carries the answers, as [the activity check](verification/claude-activity-accuracy/README.md) recorded. Show the questions as a card on the thread page, with the options, multi-select, an answer of the person's own and notes, and keep the answered card in the conversation. Getting the answer back into the waiting dialog needs a spike. Typing keys into the terminal is fragile. A PreToolUse hook that waits for the dashboard and returns the answers in the tool's input may work, but that is unchecked. This is a question the agent chose to ask, not an approval prompt, so it does not reopen the decision under Not planned.
- **An agent asking for a secret.** A card in the dashboard where the person enters the value, built alongside the question card above. The agent gets only a reference, and Gondolin's placeholder swap delivers the value. A person can already change a project's secrets with `nexus project edit` ([nexus#73](https://github.com/ramtinJ95/nexus/pull/73)), but an agent can't ask for one.
- **Bugs and scrolling.** The dashboard is buggy in general, and scrolling does not work properly. Collect the bugs with steps and screenshots as they come up, and fix them before or alongside the larger reworks here, since a redesign built on broken scrolling inherits it.
- **The diff panel renders badly.** The side panel's diff has rendering problems. Collect them with screenshots before changing it. Highlighting landed in [nexus#94](https://github.com/ramtinJ95/nexus/pull/94) and review notes in [nexus#97](https://github.com/ramtinJ95/nexus/pull/97).
- **Working with a thread feels clunky.** Sending a message, steering a running turn and following what the agent does all take too much effort today. Rework the thread page's interaction as a whole rather than patching single controls. Without a native app, the closest thing to working in the agent's own terminal may be that terminal itself, unless the dashboard really copies how Amp does it. So make the terminal the easy path: every thread page and `nexus show` print the `nexus attach <thread>` line to copy, and attaching lands in the running agent's session, ready to type into. The dashboard then carries what a terminal does badly: the overview of threads, diffs, images and questions. The browser terminal over the attach route is the in-page version of the same thing.
- **Images in the conversation.** When the person asks a thread for screenshots, as UI work does, the dashboard shows them in the conversation. Today a Claude worker's transcript turns an image into the text `[image]`. Show image blocks from the transcript, and image files the agent writes or the person asks about, at a size that fits the column with a click to open them full size. Changes could show an image file's before and after instead of a binary diff.
- **Transcripts and tool calls.** The conversation view and the way tool calls look need a redesign, for both the harness's conversations and a Claude worker's transcript.
- **Answers and GitHub for diff reviews.** A review written on the dashboard's diff goes to the agent as one message, questions included, and the answers come back in the conversation. Show an answer beside the lines it was asked about. That needs either a way to ask the thread's model without adding to the conversation, as the review-pane mod forks its conversation, or replies the dashboard can match to notes. Neither exists for a Claude worker or the Nexus agent. When the thread has a pull request, offer to post the review to GitHub as review comments instead. Its line numbers are the working tree's, which match the pull request's head only once the work is pushed, so posting needs that check and a route that calls GitHub. The pull request's own review comments could show in place too, building on the pull request watch.

## Later

- **Event consumers in Claude Code and pi-nexus.** The shared stream and background CLI follower now exist; client wake-ups and automatic reactions do not.
- **Placement by a scheduler.** A client or an agent submits work without naming a node, and Nexus boots the pylon on the node where it fits with the least load. Nodes now report what their pylons hold, `auto` picks the node with the most room left, as [the design's placement](design.md#placement) describes, and new projects default to it. What remains:
  - There is no model tool `start` yet. A thread such a tool starts without a node would follow its project's default, which may be `auto`.
  - There is no move job, so a pylon stays on the node it booted on. [The lifecycle](design.md#lifecycle-follows-amp) describes how a move could work, and spike S7 showed that copying checkpoints needs verifying.
- **Investigate an always-on agent with scheduled wake-ups.** One agent that lives on, for example in a named pylon, and that the person gives standing jobs with a schedule or a trigger. Examples: check new issues every 4 hours, post a summary to a Slack channel, or search the web for the latest CVEs that touch what the person runs. Find out where the schedule lives: the control plane is always on, so it could keep the timers and wake a paused pylon with a prompt, the way a human message does today, rather than keep a VM running. Also work out how a job's output reaches the person (attention, notifications, the event stream, or a message elsewhere), and which hosts and secrets such a job needs, such as Slack's API or a search API, under the egress allowlist and the explicit secret grants. Decide how its cost and its runs stay bounded and visible. It builds on named pylons, the event stream and the tools for driving other threads, and it overlaps with the coordinator in the orchestration wave.
- **Forking a thread.** Start a new thread from a point in another one. It needs a copy of the source pylon's disk, which is the same problem as the move job.
- **Templates across nodes, and their cleanup.** A thread now boots from a template its node holds, as [the lifecycle](design.md#lifecycle-follows-amp) describes. What remains:
  - The registry records no template's sha256, so a template is never copied to another node, and each node builds its own. Recording the manifest's sha256 when a build lands would let the planner's `fetch-artifact` rule copy it instead.
  - Nothing calls `garbage()` in `src/images.ts`, so templates past 72 hours, and what a build that failed with a retryable code left on its node, stay on the node's disk. Images are not collected either.
  - A remote that needs SSH always boots fresh, because the control plane holds no SSH key to read `.nexus/setup` with. A probe could read it with the node's key instead.
  - A template build is a VM that neither placement nor the node's committed capacity counts, so the first start of a setup runs two VMs on its node for as long as the build takes.
  - A failed build blocks its key on its node until the key changes, even when the failure was a flake in `.nexus/setup`. It could expire, or `nexus` could offer a rebuild.
  - If `.nexus/setup` changes tracked files, a template boot's checkout of a commit that changes them too fails, and retries until the planner gives up. Git refuses rather than carrying the old content over, so no thread gets stale code, but it should boot fresh instead.
  - The dashboard does not show `Thread.setup` yet.
- **Named pylons that outlive a thread.**
- **Deleting a thread's conversation from the harness.** pi-durable can't delete one yet, so a deleted thread's transcript stays in the harness's storage.
- **A Firecracker backend.**
- **Phone steering through Claude Code Remote Control.** This is low priority, because Nexus is rarely used from a phone.

## Not planned

These come from t3code, and we decided against them for Nexus:

- **Event sourcing** with an effect outbox and projections. pi-durable, the registry and the pure planner already make Nexus durable.
- **Remote access machinery,** such as several routes per machine, pairing links, a relay, OAuth and guest links. The tailnet and its whois check already cover a single user.
- **Approvals and permission modes.** Pylons run unattended in a VM with an egress allowlist, and approval prompts would stop work while you're away.
- **Settle and snooze shelves.** Idle pylons already pause, and archived threads fold away.
