# Nexus roadmap

This page lists the work planned for Nexus and its clients: the web dashboard, the Claude Code mod in `claude-mods`, and the `pi-nexus` extension. When an item lands, take it off this page and update the docs that describe the behaviour. Decisions go in [the design's decision table](design.md#decisions), and unknowns that need a spike go under [open questions](design.md#open-questions).

Several items copy ideas from [t3code](https://github.com/pingdotgg/t3code), which is MIT licensed. Code copied from it keeps its copyright notice beside the code.

## Next

- **Nexus's own live check on the person's nodes.** Nexus's `.nexus/verify` drives the verify-nexus skill's stack in a verify pylon with the image's Docker ([decisions](design.md#decisions), 2026-10-31), so it runs once the person rebuilds the pylon image with `docker.io`. Until then it exits 127 and each Nexus review goes to the person. Check the first verify pylon on `rj-firebat` after the rebuild: that its probe reports nested virtualization, that the boot gets `/dev/kvm`, that `dockerd` starts, and that the live check passes well inside its hour.

## The orchestration wave

Run the whole build pipeline on Nexus, with no coordinator chat on the Mac. On 2026-10-25 and 2026-10-26 dozens of pull requests landed this way: Nexus threads built them, Nexus reviews checked them and agents deployed them. A Claude Code chat on the Mac still did the orchestration, helped by two pi workers there: one polled the threads for news, the other ran deploys and read the nodes. That chat picked items from this page, wrote each builder's brief, started builder threads, started `nexus review`, merged under [the merge policy](merge-policy.md), ran `nexus deploy --wait`, started short-lived threads to check a deploy live, gathered evidence over SSH when a pylon's controller crashed, archived finished threads, kept its state in notes, and brought the person only real decisions. It moved only while it had a turn, and stalled whenever it waited on the person. On 2026-10-25 it stopped three ways: it asked the person about calls it could have made, such as merging a reviewed PR whose live check couldn't run locally; a thread stopped at a draft and no one noticed until it was read; and a deploy needed a sudo password. The person decided its shape on 2026-10-28, as [the design's decision table](design.md#decisions) records. Nexus's own live check, under Next, comes first. Reviews already start on their own in a project that asks for it, and land, rebasing a branch that conflicts. A builder in such a project that ends its turn with no pull request gets a nudge, and after two its attention goes to the person. A review that lands archives its builder and its reviewer. Pipeline items line up work ahead: each becomes a queued thread once the items before it are, and starts once their pull requests merge, with its phase on the dashboard's Pipeline page. When a builder's pylon fails in a project that runs the pipeline, [a failure judgment](design.md#failure-judgments) decides whether to retry it, retry it on another node or ask the person ([nexus#186](https://github.com/ramtinJ95/nexus/pull/186)). The control plane asks the person through [question records](design.md#questions-for-the-person), which show as decision cards on the thread page ([nexus#172](https://github.com/ramtinJ95/nexus/pull/172)). A [planning thread](design.md#planning-threads), opened with `nexus start --plan`, proposes items as such cards, and each one the person accepts becomes a pipeline item ([nexus#185](https://github.com/ramtinJ95/nexus/pull/185)).

- **A coordinator that runs inside Nexus.** The control plane's passes take over what the Mac chat did: they start builders from the person's items, start reviews, land within the merge policy, deploy, check the deploy and clean up. They run on a 15-second poll instead of holding a turn, and they keep their state in the registry instead of a chat's notes, so they survive a restart and need no laptop. The coordinator is deterministic code, not an agent, because a Nexus thread never starts, messages, waits on or drives another thread, as the person decided on 2026-10-28. An agent that needs helpers runs them in its own pylon, and a call that needs a model goes to a short-lived judgment, a conversation with no tools and no pylon whose brief holds every fact it needs. [The orchestration exploration](explorations/orchestration.md) surveys how other tools orchestrate, weighs the shapes and orders the steps, all of which have landed except one the person dropped. Planning already works as the person decided on 2026-10-28: a planning thread's proposals are cards on its page that the person accepts or rejects one by one ([nexus#185](https://github.com/ramtinJ95/nexus/pull/185)).
- **Wake-ups from the event stream.** The Mac's watcher polled every thread and reported by ending its turn. The coordinator should wake on the events that matter instead: a builder's turn ends or fails, a pull request opens, a review ends, a deploy finishes, or a node's pylon crashes. The stream and the background follower exist, but nothing inside Nexus consumes them yet. The passes in `src/control/main.ts` poll every 15 seconds and read state on every pass. As [the exploration](explorations/orchestration.md#wake-ups-from-the-event-stream) says, an event would only make a pass run sooner, so this item cuts the wait of up to one pass and adds no capability. This is the control plane's side of the event consumers under Later.
- **Asking the person through the attention status.** [Question records](design.md#questions-for-the-person) and their decision cards exist since [nexus#172](https://github.com/ramtinJ95/nexus/pull/172), and failure judgments and planning threads ask the person through them. Two askers are left. The review's hold for the person still uses its own Land card rather than a question record. The pipeline does not yet ask the calls the merge policy reserves for the person, such as image rebuilds, secrets and the egress allowlist, as questions. No question asked today names a reserved case. An item waiting on such a question should hold only that item.

## The maintenance wave

The current wave. Keep a running install healthy without the person reading logs over SSH: report its state every day, keep its disks from filling, survive a reboot, clean up what it no longer needs with the person's yes, back it up, and move the control plane to another machine.

The person decided these on 2026-10-28, as [the design's decision table](design.md#decisions) records. A machine that is reset and has an encrypted root unlocks over SSH at boot, from an SSH server in the initramfs. Backups stay on the control-plane host only. An archived pylon's disk was to be kept 7 days; on 2026-10-30 the person changed that to 24 hours, deleted automatically, while its thread record and conversation stay.

`infra-testbench`'s root disk is LUKS with no automatic unlock, so a reboot waits at a passphrase prompt and the node stays offline until someone types it. This was inferred on 2026-10-28 from its initramfs and kernel command line, not from a boot.

- **`nexus doctor` and a daily report.** One command that checks each node and the control plane: services, release, disk, certificates, the harness's login, tailnet reachability and what [node diagnostics](design.md#node-diagnostics) already serve. The control plane runs the same checks once a day, keeps each report 30 days, and shows a badge on the dashboard when the latest one found a problem.
- **Disk space.** Watch the free space of every path Nexus writes: `/var/lib/nexus/pylons`, `/var/lib/nexus/artifacts`, the Docker and Gondolin caches under `/var/lib/nexus`, `/var/lib/nexus-control`, and `/opt/nexus/releases`. Report it in the node's health and the daily report, and refuse a start on a node about to run out. Rotate each pylon's `controller.log`, which grows for the pylon's whole life today.
- **A node shutting down pauses its pylons.** A clean shutdown or reboot pauses every running pylon first, as an archive does, records it as paused, and the boot wakes each one, so a reboot keeps every pylon's disk, services and sessions. As with any pause, what was only in memory and running commands are lost ([the lifecycle](design.md#lifecycle-follows-amp)). Today nothing orders this. The probe's unit stops only the probe (`KillMode=process` in `deploy/nexus-probe.service`). Each pylon's controller does try a disk checkpoint when it gets SIGTERM (`src/pylon-vm/daemon.ts` lines 97 to 113), but nothing makes systemd wait for it, records the pylon as paused or wakes it after the boot. With an encrypted root, the node waits for its unlock over SSH before anything wakes.
- **Cleanup the person confirms.** The control plane proposes cleanups as questions with a node as their subject, which the person accepts or rejects on cards. Questions today belong to a thread (`questions.thread` is `NOT NULL` in `src/control/schema.ts`), so a node subject needs a registry migration. The candidates:
  - Templates past their 72 hours, what a build that failed with a retryable code left, and images no pylon and no recorded image needs, through `garbage()` in `src/control/templates.ts`, which nothing calls yet. It keeps each project's newest ready template past 72 hours, and counts as garbage every image but the current one that backs no template, so the previous image a rollback needs would need a rule of its own.
  - Releases under `/opt/nexus/releases` that no service links and no pylon controller runs. `deploy/release.sh` never removes one, because a controller keeps running the release it started from.
- **A daily backup of the control plane.** The registry, the harness's storage, the credentials and `/etc/nexus`, copied consistently once a day on the control-plane host, with a few days kept and a restore that `nexus doctor` can check.
- **The control plane's identity in one place.** The control plane's node ID is written into every probe's `auth.controlPlane` (`src/probe/config.ts` line 43), every deployer's `controlUrl` and `controlNodeId` (`src/deploy/setup.ts`), and the role assumes a probe on the same host (`src/control/releases.ts` lines 36 to 40). Keep it in one place each node reads, so moving it is one change.
- **Moving the control plane with one command.** Copy the backup to another machine, install the control role there and point every probe and deployer at it, then retire the old one, with threads paused for the move rather than lost.

## The dashboard wave

Planned for later, as one wave of interface work. The person scopes it and starts it, and has more changes in mind than this list holds yet. Add them here as they come up.

- **Decide whether a desktop app becomes the main interface.** Neither the client mods nor the web dashboard feels good enough as the place to work with threads. [The desktop app exploration](explorations/desktop-app.md) compares building a Nexus app from [t3code](https://github.com/pingdotgg/t3code)'s MIT code, adapting t3code or [Jetline](https://github.com/MartinRybergLaude/jetline) so that Nexus threads appear in them, and keeping the web dashboard and closing its gaps. It recommends the dashboard. Both apps assume the machine their server runs on owns the checkout, the terminals and the agent, which a pylon breaks. A terminal tab on the thread page attaches over the attach route, as [the thread page's interaction](https://github.com/ramtinJ95/nexus/blob/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/thread-page-interaction/README.md) describes. The gaps are a terminal drawer, pushed updates instead of polling and an installable window. Previews over HTTPS already landed in [nexus#87](https://github.com/ramtinJ95/nexus/pull/87), latest-turn snapshots for Claude worker turns in [nexus#91](https://github.com/ramtinJ95/nexus/pull/91), highlighted diffs in [nexus#94](https://github.com/ramtinJ95/nexus/pull/94), and review notes on the diff in [nexus#97](https://github.com/ramtinJ95/nexus/pull/97). A native shell would come later, and only if notifications must arrive with no dashboard window open. The person decides. Settle this before the rest of this wave, which would otherwise land in an app instead. Their API and probe parts serve any client, as the Claude transcript route already does. This overlaps with the orchestration wave above, which asks what the person's interface to every pylon should be.
- **An agent asking for a secret.** A card in the dashboard where the person enters the value, like the card that answers a Claude worker's AskUserQuestion. The agent gets only a reference, and Gondolin's placeholder swap delivers the value. A person can already change a project's secrets with `nexus project edit` ([nexus#73](https://github.com/ramtinJ95/nexus/pull/73)), but an agent can't ask for one.
- **Bugs and scrolling.** The scrolling fixes landed in [nexus#192](https://github.com/ramtinJ95/nexus/pull/192): the page no longer scrolls past the window, the conversation keeps a reader at its end while its pane shrinks or a diff tab covers it, question cards show their options, the open thread shows in the sidebar, the inspector's tabs stay in view, and the pipeline's cells wrap. [The capture](https://github.com/ramtinJ95/nexus/blob/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/dashboard-scrolling/README.md) reruns every check at a desktop and a phone width, on main and on a branch. Collect further bugs with steps and screenshots as they come up, and fix them before or alongside the larger reworks here. What remains:
  - On a phone, the dock crowds out the conversation. At 390 px wide, open a thread with a waiting question or an approved review, and focus the composer so the keyboard opens. The questions take up to 40% of the window and a landing card up to 45%, so the conversation shows about 90 px ([screenshot](https://github.com/ramtinJ95/nexus/blob/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/dashboard-scrolling/branch/phone-14-window-shrank-then-reply.png)). The thread page's interaction was reworked in [the terminal and composer change](https://github.com/ramtinJ95/nexus/blob/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/thread-page-interaction/README.md), which left the cards where they were, so where they go is still open.
  - Nothing has checked a real phone. iOS Safari lays its keyboard over the page instead of shrinking it, so whether the composer and the conversation's end stay in view there is unknown.
  - An approved review on a project that leaves landing to the person never reaches Needs you, so nothing tells the person a pull request waits for them to land it ([nexus#358](https://github.com/ramtinJ95/nexus/issues/358)).
- **Themes.** Landed in [nexus#202](https://github.com/ramtinJ95/nexus/pull/202): the sidebar picks System, Light, Dark, or macarchy's Tokyo Night, Catppuccin Mocha and Kanagawa Wave, a toggle switches between light and dark, and the diff panel and the terminal tab follow the theme. [The capture](https://github.com/ramtinJ95/nexus/blob/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/dashboard-themes/README.md) shows every theme on every page. Nothing has checked Safari, Firefox or a real phone.
- **Answers and GitHub for diff reviews.** A review written on the dashboard's diff goes to the agent as one message, questions included, and the answers come back in the conversation. Show an answer beside the lines it was asked about. That needs either a way to ask the thread's model without adding to the conversation, as the review-pane mod forks its conversation, or replies the dashboard can match to notes. Neither exists for a Claude worker or the Nexus agent. When the thread has a pull request, offer to post the review to GitHub as review comments instead. Its line numbers are the working tree's, which match the pull request's head only once the work is pushed, so posting needs that check and a route that calls GitHub. The pull request's own review comments could show in place too, building on the pull request watch.

## Later

- **Event consumers in Claude Code and pi-nexus.** The shared stream and background CLI follower now exist; client wake-ups and automatic reactions do not.
- **Placement by a scheduler.** A person or the control plane's pipeline submits work without naming a node, and Nexus boots the pylon on the node where it fits with the least load. Nodes now report what their pylons hold, `auto` picks the node with the most room left, as [the design's placement](design.md#placement) describes, and new projects default to it. What remains:
  - No model tool starts a thread, and none is planned, because a thread never starts another thread. The pipeline's starts already follow a project's default node when an item names none, and that default may be `auto`.
  - There is no move job, so a pylon stays on the node it booted on. [The lifecycle](design.md#lifecycle-follows-amp) describes how a move could work, and spike S7 showed that copying checkpoints needs verifying.
- **Investigate an always-on agent with scheduled wake-ups.** One agent that lives on, for example in a named pylon, and that the person gives standing jobs with a schedule or a trigger. Examples: check new issues every 4 hours, post a summary to a Slack channel, or search the web for the latest CVEs that touch what the person runs. Find out where the schedule lives: the control plane is always on, so it could keep the timers and wake a paused pylon with a prompt, the way a human message does today, rather than keep a VM running. Also work out how a job's output reaches the person (attention, notifications, the event stream, or a message elsewhere), and which hosts and secrets such a job needs, such as Slack's API or a search API, under the egress allowlist and the explicit secret grants. Decide how its cost and its runs stay bounded and visible. It builds on named pylons and the event stream, and it overlaps with the coordinator in the orchestration wave. The control plane keeps its timers and wakes it, and under the rule that a thread never drives another thread, it may propose pipeline items for the person to accept but never start, message or wait on another thread.
- **Forking a thread.** Start a new thread from a point in another one. It needs a copy of the source pylon's disk, which is the same problem as the move job.
- **Templates across nodes, and their cleanup.** A thread now boots from a template its node holds, as [the lifecycle](design.md#lifecycle-follows-amp) describes. What remains:
  - The registry records no template's sha256, so a template is never copied to another node, and each node builds its own. Recording the manifest's sha256 when a build lands would let the planner's `fetch-artifact` rule copy it instead.
  - Nothing calls `garbage()` in `src/control/templates.ts`, so templates past 72 hours stay on the node's disk. Collecting them is a cleanup in [the maintenance wave](#the-maintenance-wave).
  - A remote that needs SSH always boots fresh, because the control plane holds no SSH key to read `.nexus/setup` with. A probe could read it with the node's key instead.
  - A template build is a VM that neither placement nor the node's committed capacity counts, so the first start of a setup runs two VMs on its node for as long as the build takes.
  - A failed build blocks its key on its node until the key changes, even when the failure was a flake in `.nexus/setup`. It could expire, or `nexus` could offer a rebuild.
  - If `.nexus/setup` changes tracked files, a template boot's checkout of a commit that changes them too fails, and retries until the planner gives up. Git refuses rather than carrying the old content over, so no thread gets stale code, but it should boot fresh instead.
  - The dashboard does not show `Thread.setup` yet.
- **Named pylons that outlive a thread.**
- **Deleting a thread's conversation from the harness.** pi-durable can't delete one yet, so a deleted thread's transcript stays in the harness's storage.
- **A Firecracker backend.**
- **A Kubernetes branch, as a side quest.** Try Nexus on Kubernetes on a branch of its own, with custom resources, deployments and controllers in place of the control plane's own loops: a thread or pylon as a custom resource, the planner's reconciliation as a controller, and placement as the scheduler. Nexus already borrows Kubernetes's ideas: desired and actual state reconciled by a pure planner (`src/reconcile.ts`), a probe on each node much as a kubelet, and placement by the room each node reports. It is not a focus any time soon, and nothing is built for it yet.
- **Phone steering through Claude Code Remote Control.** This is low priority, because Nexus is rarely used from a phone.

## Not planned

These come from t3code, and we decided against them for Nexus:

- **Event sourcing** with an effect outbox and projections. pi-durable, the registry and the pure planner already make Nexus durable.
- **Remote access machinery,** such as several routes per machine, pairing links, a relay, OAuth and guest links. The tailnet and its whois check already cover a single user.
- **Approvals and permission modes.** Pylons run unattended in a VM with an egress allowlist, and approval prompts would stop work while you're away.
- **Settle and snooze shelves.** Idle pylons already pause, and archived threads fold away.
