# Nexus roadmap

This page lists the work planned for Nexus and its clients: the web dashboard, the Claude Code mod in `claude-mods`, and the `pi-nexus` extension. When an item lands, take it off this page and update the docs that describe the behaviour. Decisions go in [the design's decision table](design.md#decisions), and unknowns that need a spike go under [open questions](design.md#open-questions).

Several items copy ideas from [t3code](https://github.com/pingdotgg/t3code), which is MIT licensed. Code copied from it keeps its copyright notice beside the code.

## Next

- **Live checks on a verify pylon.** The merge policy's live check has no place to run, so every landing relies on the pull request saying what it could not check live. [The open question](design.md#open-questions) weighs where a verify stack could run and recommends a verify pylon that loads the KVM modules its kernel already ships, which nested virtualization on `rj-firebat` allows. The image change is the person's to approve. Then the review loop starts the stack after `.nexus/check` passes, and records the result for the policy.
- **Node 26 in the pylon image.** The project needs Node 26 or newer, as the control plane's and the probe's units check, but the pylon image pins Node 24.22.1, so agents and `.nexus/check` run the typecheck and the tests on Node 24 and npm warns `EBADENGINE`. The suite passes on Node 24 today, so the warning changes no verdict, but a change that uses an API Node 24 lacks fails its check, and one that breaks only on Node 26 passes it. Moving the pin is an image rebuild, which is the person's to approve.
- **Reviews start on their own.** `nexus review` starts the review loop for one thread. Once it has run on a few pull requests, start it when the PR watch first links an open pull request, perhaps per project.
- **Decide whether a desktop app becomes the main interface.** Neither the client mods nor the web dashboard feels good enough as the place to work with threads. [The desktop app exploration](explorations/desktop-app.md) compares building a Nexus app from [t3code](https://github.com/pingdotgg/t3code)'s MIT code, adapting t3code or [Jetline](https://github.com/MartinRybergLaude/jetline) so that Nexus threads appear in them, and keeping the web dashboard and closing its gaps. It recommends the dashboard. Both apps assume the machine their server runs on owns the checkout, the terminals and the agent, which a pylon breaks. A browser terminal on the thread page already works over the attach route. The gaps are a terminal drawer, pushed updates instead of polling and an installable window. Previews over HTTPS already landed in [nexus#87](https://github.com/ramtinJ95/nexus/pull/87), latest-turn snapshots for Claude worker turns in [nexus#91](https://github.com/ramtinJ95/nexus/pull/91), highlighted diffs in [nexus#94](https://github.com/ramtinJ95/nexus/pull/94), and review notes on the diff in [nexus#97](https://github.com/ramtinJ95/nexus/pull/97). A native shell would come later, and only if notifications must arrive with no dashboard window open. The person decides. Settle this before the dashboard items below, which would otherwise land in an app instead. Their API and probe parts serve any client, as the Claude transcript route already does. This overlaps with the orchestration rethink under Later, which asks what the person's interface to every pylon should be.
- **The clients use the attention status, the seen marker and the latest-turn base.** The mod and pi-nexus drop their own seen stores (the mod's store and `pi-nexus/viewed.json`) and read the control plane's fields instead.
- **Answers and GitHub for diff reviews.** A review written on the dashboard's diff goes to the agent as one message, questions included, and the answers come back in the conversation. Show an answer beside the lines it was asked about. That needs either a way to ask the thread's model without adding to the conversation, as the review-pane mod forks its conversation, or replies the dashboard can match to notes. Neither exists for a Claude worker or the Nexus agent. When the thread has a pull request, offer to post the review to GitHub as review comments instead. Its line numbers are the working tree's, which match the pull request's head only once the work is pushed, so posting needs that check and a route that calls GitHub. The pull request's own review comments could show in place too, building on the pull request watch.

## Later

- **Event consumers in Claude Code and pi-nexus.** The shared stream and background CLI follower now exist; client wake-ups and automatic reactions do not.
- **Placement by a scheduler.** A client or an agent submits work without naming a node, and Nexus boots the pylon on the node where it fits with the least load. Nodes now report what their pylons hold, and `nexus start --node auto` picks the node with the most room left, as [the design's placement](design.md#placement) describes, but only when the person asks for it. What remains:
  - The model tools' `start` takes no node, so an agent cannot ask for `auto`.
  - There is no move job, so a pylon stays on the node it booted on. [The lifecycle](design.md#lifecycle-follows-amp) describes how a move could work, and spike S7 showed that copying checkpoints needs verifying.
  - Two `auto` starts that overlap can choose the same room, so the scheduler needs a reservation.
  - Decide when `auto` becomes the default, for example per project.
- **Tools for an agent to drive other threads.** Delegate a task, send to a thread, wait on it and read it, with retry-safe request IDs and a cap on what a child thread may do. The agent loop runs on the control plane, so these tools could run there. Whether pi-durable can run a tool on the host rather than in the pylon is unchecked.
- **Rethink how work is orchestrated.** Revisit this after more of the roadmap has been built through Nexus. Today the coordinator is a Claude Code chat on the Mac. It moves only while it has a turn, so the whole pipeline stops whenever it waits on the person. On 2026-10-25 it stopped three ways. The coordinator asked the person about calls it could have made, such as merging a reviewed PR whose live check couldn't run locally. A thread stopped at a draft and no one noticed until it was read. A deploy needed a sudo password. The rethink should also ask whether there should be one coordinator at all. Today a single chat is the person's only interface to every pylon, and that may not be the right workflow. Before deciding, look at how other tools do it, among them Grok's bot, Muse and t3code, and note their ideas and approaches. One direction among others: a coordinator that runs inside Nexus could fix this, reacting to attention changes and pull request events instead of polling. It would act alone within [the merge policy](merge-policy.md), as the review loop already does once `nexus review` starts it, and bring the person only real decisions, through the attention status. It builds on the tools above and on deploys that agents can run.
- **Investigate an always-on agent with scheduled wake-ups.** One agent that lives on, for example in a named pylon, and that the person gives standing jobs with a schedule or a trigger. Examples: check new issues every 4 hours, post a summary to a Slack channel, or search the web for the latest CVEs that touch what the person runs. Find out where the schedule lives: the control plane is always on, so it could keep the timers and wake a paused pylon with a prompt, the way a human message does today, rather than keep a VM running. Also work out how a job's output reaches the person (attention, notifications, the event stream, or a message elsewhere), and which hosts and secrets such a job needs, such as Slack's API or a search API, under the egress allowlist and the explicit secret grants. Decide how its cost and its runs stay bounded and visible. It builds on named pylons, the event stream and the tools for driving other threads, and it overlaps with the orchestration rethink above.
- **An agent asking for a secret.** A card in the dashboard where the person enters the value. The agent gets only a reference, and Gondolin's placeholder swap delivers the value. A person can already change a project's secrets with `nexus project edit` ([nexus#73](https://github.com/ramtinJ95/nexus/pull/73)), but an agent can't ask for one.
- **Forking a thread.** Start a new thread from a point in another one. It needs a copy of the source pylon's disk, which is the same problem as the move job.
- **Templates across nodes, and their cleanup.** A thread now boots from a template its node holds, as [the lifecycle](design.md#lifecycle-follows-amp) describes. What remains:
  - The registry records no template's sha256, so a template is never copied to another node, and each node builds its own. Recording the manifest's sha256 when a build lands would let the planner's `fetch-artifact` rule copy it instead.
  - Nothing calls `garbage()` in `src/images.ts`, so templates past 72 hours, and what a build that failed with a retryable code left on its node, stay on the node's disk. Images are not collected either.
  - A remote that needs SSH always boots fresh, because the control plane holds no SSH key to read `.nexus/setup` with. A probe could read it with the node's key instead.
  - A template build is a VM that neither placement nor the node's committed capacity counts, so the first start of a setup runs two VMs on its node for as long as the build takes.
  - A failed build blocks its key on its node until the key changes, even when the failure was a flake in `.nexus/setup`. It could expire, or `nexus` could offer a rebuild.
  - If `.nexus/setup` changes tracked files, a template boot's checkout of a commit that changes them too fails, and retries until the planner gives up. Git refuses rather than carrying the old content over, so no thread gets stale code, but it should boot fresh instead.
  - The dashboard does not show `Thread.setup` yet.
- **Named pylons that outlive a thread.**
- **Deleting a thread's conversation from the harness.** pi-durable can't delete one yet, so a deleted thread's transcript stays in the harness's storage.
- **A Firecracker backend.**
- **Phone steering through Claude Code Remote Control.** This is low priority, because Nexus is rarely used from a phone.

## Not planned

These come from t3code, and we decided against them for Nexus:

- **Event sourcing** with an effect outbox and projections. pi-durable, the registry and the pure planner already make Nexus durable.
- **Remote access machinery,** such as several routes per machine, pairing links, a relay, OAuth and guest links. The tailnet and its whois check already cover a single user.
- **Approvals and permission modes.** Pylons run unattended in a VM with an egress allowlist, and approval prompts would stop work while you're away.
- **Settle and snooze shelves.** Idle pylons already pause, and archived threads fold away.
