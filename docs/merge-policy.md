# Merge policy

The person approved this policy on 2026-10-26. It says when an agent may merge and deploy a pull request without the person, and which changes always go to the person. [The review loop](design.md#the-review-loop-and-landing) applies it on the control plane, and `src/control/policy.ts` holds its checks.

## An agent may merge and deploy without the person

An agent may merge and deploy a pull request without the person when all of these hold:

1. A reviewer on a different model from the builder approved it with no P0, P1 or P2 finding open, and so did the second reviewer where the project asks for one, as [A second reviewer](#a-second-reviewer) describes. The builder fixed or rejected, with a reason, every P0 to P2 finding. P3 findings never block a merge and need no fix.
2. The typecheck and the full test suite pass.
3. A live check passed on a verify stack, or the pull request says what couldn't be checked live and none of it is on the always-needs-the-person list below.
4. After merging, `nexus deploy --wait` reports every service healthy. If it doesn't, the agent rolls back to the previous release and tells the person.

The reviewer gives each finding a priority. The person decided on 2026-10-26 that only P0 to P2 findings block a merge into main:

| Priority | Means | Blocks |
|---|---|---|
| P0 | It breaks main or loses data. | Yes |
| P1 | A real bug or security problem that users hit. | Yes |
| P2 | A bug in a less common path, a missing test for new behaviour, or docs the change makes wrong. | Yes |
| P3 | Style, naming, small cleanups and nitpicks. | No. The builder gets them as notes it may take up in a later pull request. |

## Always needs the person

- Changes to secrets, the egress allowlist, login or auth, or the tailnets.
- Database migrations that delete or rewrite existing data.
- Pylon image rebuilds.
- Breaking changes to the CLI's contract.
- Anything irreversible.

The person decided on 2026-10-27 that pressing Land on the dashboard confirms it: a landing the person starts with the dashboard's Land button satisfies "always needs the person" for the holds the person may waive, which [What the person may waive](#what-the-person-may-waive) lists. Every other condition above still holds. Since 2026-11-04 the review asks the person through a question, whose Land answer is the same press, as [Asking the person](#asking-the-person) describes.

## How Nexus checks each condition

| Condition | What the landing checks |
|---|---|
| A reviewer on another model approved | The review's reviewer model differs from the builder's, and its latest round's verdict is an approval with no P0 to P2 finding open. A failed `.nexus/check` counts as a P0 finding. The approval must come from a harness reviewer, whose verdict the control plane's own agent loop produces. A Claude reviewer's verdict is read from its transcript in its pylon, where code it runs, such as the pull request's tests, could write a forged one, so a landing it approved goes to the person. Where the review has a second reviewer, its verdict on the latest round must be an approval too, and a round with no verdict from it holds the landing. |
| Every P0 to P2 finding fixed or rejected with a reason | Every P0 to P2 finding of every round has the builder's answer: fixed, or rejected with a non-empty reason. A P3 finding needs no answer. |
| Typecheck and full test suite | The control plane ran the repository's `.nexus/check` at the approved head in a fresh check thread, started beside the reviewer's round at that head, a pylon with no agent cloned at that commit, in the environment the pylon's image gives its agents, and the pipe the probe carried reported the check's process exiting 0. Nothing the check writes in the pylon decides it, and the thread is deleted afterwards, so nothing it leaves running reaches a later round or any reviewer. A Land press at a head whose check passed keeps that result, since the check clones that commit alone, and a head where it has not passed runs it again. Any GitHub check on the pull request must not be failing or pending either. |
| Live check, or a statement of what couldn't be checked live | When the approved head has a `.nexus/verify`, the control plane ran it after `.nexus/check` passed, in a fresh verify pylon: a pylon with no agent cloned at that commit, whose boot asks for nested virtualization, on a node whose probe reports that its KVM nests. The pipe the probe carried reported the script exiting 0, which is a live check that passed, and the statement is not needed. A live check that failed holds the landing as a failed check does: the builder gets it as a `LIVE` finding (P0), and only a new head whose live check passes lands. The verify pylon is archived afterwards, and nothing in it decides the verdict. A head with no `.nexus/verify` takes the second branch. A round that recorded neither holds the landing. The reviewer quotes the passage of the pull request's description that says what couldn't be checked live, at least 20 characters, which must appear in the description. When the person presses Land at a head with no live check, and the round has no such quote or its landing held on it, the reviewer is asked again first, at the same head and with no new round, to quote the passage from the description as it is then. A landing whose only hold left is a quote the description has lost since the reviewer gave it asks the same, once per description, so one press is enough there too. The reviewer quotes the passage only if it holds up against the change it approved at that head, claiming nothing as checked live that the change gives no way to check and leaving out no part that only a live run would show works, and answers null otherwise. A null holds the landing as a missing statement does. What the passage names is not a reserved case by itself. |
| Nothing reserved for the person | The reviewer lists every reserved case the change touches, which must be none. A case counts only when the diff changes it in code or config that ships, so docs, test stand-ins and verification harnesses touch none. A pylon image rebuild is a change to `images/` or to what the pylon image is built from, so that merging it means the person must rebuild the image. For Nexus's own pull requests, the changed paths must also touch none, as the table below says. In any repository, a change to `.nexus/check` or `.nexus/verify` holds the landing. Each of these holds is met instead when the person waived it for the approved head by pressing Land on the dashboard, as [What the person may waive](#what-the-person-may-waive) says. |
| Deploy healthy, else roll back | Landings that deploy go one at a time: one waits to merge while another deploys or rolls back, while a deploy drains the control plane, and while not every service reports the desired release healthy, so the previous release it would roll back to is one every service reported healthy. Nexus's own pull requests deploy their merge commit and wait up to 30 minutes, extending the deadline while fresh waiting-for-idle reports show admitted turns draining; a busy turn is not a failed release. A failed, rolled-back or late deploy sets the desired release back to the previous one and waits, up to 30 minutes again, for every service to report it healthy. Only then does the person hear that it rolled back; a rollback that fails too is reported as failed. Another repository's pull request is merged with nothing to deploy. |

The landing also refuses a pull request that is not open, whose head moved after the approval, whose base changed since, or whose branch conflicts with its base. A moved head is not merged but reviewed again, in a new round, and so is a retargeted pull request at its approved head, against the new base, since the reviewer read its change against the old one, and the person's waiver no longer covers it. One merged outside the review into another base than its approval's is not deployed. So is a head pushed while a landing waits for the person, or after a review stopped at approval: the loop compares the pull request's head with the approved one on every pass, and a new head gets a new round, a check and every condition here again, with a hold for the person again where one applies. A head whose change is the approved head's on the same base, every file's patch and mode the same with hunk positions aside, keeps the reviewer's approval instead, with no reviewer round and no round spent, and the person's waiver too when it covers every hold there, but still gets the check, the live check and every condition here. A waiver otherwise covers only the head it names. A review with no round left goes to the person with a reason that names the new head, and one the loop already gave up on only gains that reason, unless its rounds ran out and the new head keeps the change they judged, which keeps the hold as it was at the new head. A branch that only conflicts goes back to the builder to rebase, after the last round too, and the rebased head gets a new round, a check and every condition here again before it can merge, or only the check and the conditions when the rebase kept the change. A builder that cannot rebase, or a rebase that changed the change with no round left, goes to the person, and a rebase it pushes later, while a round is left, gets that new round after all. So does a fix pushed later for a failed check or live check the builder first answered without one. A landing merges and deploys for a deployer: the one who asked for it, or, for a project that lands on its own, the one who turned that on, and it is held for the person if they are no longer a deployer or the project no longer asks. It checks every condition again, with what GitHub says at that moment, right before each merge attempt, including one retried after a restart, since checks can fail after an approval and branch protection may not enforce them. It merges with GitHub's head check, so it merges only the commit the reviewer approved. A pull request someone merged outside the review, at the approved commit, is deployed only if every condition here holds for it, and otherwise goes to the person.

## Paths that hold a Nexus pull request

Text in the pull request can mislead the reviewer but cannot change which files it touches or what their patches say, so for Nexus's own pull requests the changed paths are checked too, both a file's path and the path it was renamed from. Some files hold whatever their change. In the rest of the code a case watches, a file holds only when its patch names what the case guards: a line of code in one of its hunks names one of the case's words below, whether the line was removed, added, or is context around the change, or the hunk's header, which names the code around it, does. Context counts because a line added beside a guard can get around it without naming it. A line that is only a comment, `// ...` or `/* ... */`, counts for nothing. A file GitHub shows no patch for, such as one too large to diff, holds as if its patch named them, and so does a file renamed or moved from another path, whose body the patch does not show. A watched folder's tests (`*.test.ts`) and notes (`*.md`) hold for nothing by being in it, since neither ships, though one whose name a rule matches, such as `src/pylon-vm/network.test.ts`, still holds. The rules are drawn wide: a file, or a patch, that might touch a reserved case holds the landing, and the person decides. They are still a list, so a reserved change in a file they do not name, or worded so its patch names none of a case's words, rests on the reviewer alone. Nothing under `docs/` deploys, so a path there holds only when the table names it outright, never because its name says secret, network, auth or tailnet. The paths are read once the checks pass at the approved head and recorded with that round and the base they were read against, so the dashboard shows, and a Land press waives, the same path holds the landing meets there. A pull request retargeted to another base since gets a new round there, and its paths are read again at the new base.

| Reserved case | Whatever their change | When the patch names what the case guards |
|---|---|---|
| Secrets | any path naming a secret or a credential, `src/probe/redact.ts`, which keeps granted secrets out of what the probe sends, and everything under `deploy/` but its notes, such as `deploy/README.md` | |
| The egress allowlist | any path naming a network, egress or an allowlist, `src/pylon-vm/host-bridge.ts`, and `src/pylon-vm/runtime.ts`, which builds the VM | `src/control/project.ts`, `src/control/overlay.ts`, `src/control/threads.ts`, `src/control/live.ts` and every path under `src/pylon-vm/` or `src/backends/pylon-vm/`, when the patch names a host, an allowlist, egress, a network, DNS, a proxy, a firewall, TLS, an IP, SOCKS, SSH, a secret or grant, a login, the host bridge, a hook or an interception, such as Gondolin's `httpHooks`, a portal, a public URL or a port, or quotes a host name such as `"api.anthropic.com"`, though not a file name such as `"status.json"` |
| Login or auth | any path naming auth, login or whois, `src/control/api/server.ts`, which admits every request, `src/control/login.ts`, `src/control/attach.ts`, `src/control/policy.ts`, `src/control/holds.ts`, `src/protocol/http.ts`, `src/protocol/routes.ts`, `src/control/api/access.ts`, `src/control/api/kit.ts`, `src/control/api/pylon-access.ts`, `src/probe/config.ts`, `src/probe/server.ts`, the probe's request guard, `src/deploy/control-plane.ts` and `src/deploy/http.ts` | `src/control/main.ts`, `src/control/releases.ts`, `src/protocol/deploy.ts`, the deployer's wire contract, and everything under `src/control/api/`, `src/probe/` and `src/deploy/`, when the patch names whois, a caller, what is allowed, a person, a deployer, `roleOf`, `demand`, `mayLand`, `isPerson` or `isReporter`, admitting, access, trust, a peer, an identity, auth, a token, a bearer, 401 or 403, the control plane or control node, the tailnet, a login, a join, a refusal, a secret, redaction, a route's `open:` guard, or a file's mode (`chmod`, `chown`, `umask`, an octal mode such as `0o600`); and every path under `src/pylon-vm/` or `src/backends/pylon-vm/`, when the patch names a file's mode, which decides who on the node may call a controller |
| The tailnets | any path naming tailscale or a tailnet | |
| Pylon image rebuilds | everything under `images/`, and `src/image/agent-setup.ts` | |
| Anything irreversible | | a registry migration, or a table or index created, altered or dropped, in `src/control/schema.ts`, and a change to the `@earendil-works/pi-durable` version in `package.json` |

A registry migration counts as irreversible even when it only adds a table: a control plane refuses a registry newer than its code, so a rollback past a migration could not start the control plane. A pi-durable upgrade may migrate the harness's storage in the same way. A change to `.nexus/check` also holds the landing, since it is the check this policy relies on, and so does a change to `.nexus/verify`, the live check it relies on.

## Known limits

- The check's exit status, and the live check's, is what the pylon reports for the pipe's process. Code in the check runs as the pylon's `user`, who has sudo, so a check written to attack its own VM's process reporting could still lie about it. That is a deliberate attack on Nexus rather than a test that writes the wrong file, and the reviewer reads the change for it.
- The typecheck and the tests are whatever the pull request's `.nexus/check` and its scripts run, and the live check whatever its `.nexus/verify` runs. A change to either file holds the landing, but a change to what they call, such as `package.json`'s scripts or the verify-nexus skill's scripts that Nexus's `.nexus/verify` runs, is for the reviewer to catch. A pull request that deletes `.nexus/verify` runs no live check, and lands on its statement of what it could not check live once the person accepts the change.

## What the person does with a held landing

`nexus show <thread>` and the dashboard list every condition that failed and every reserved case that applies, and the thread's attention is `decision` until the person acts. So is that of a review that stopped at approval, which only the person's Land merges, until it lands, its pull request merges or closes outside it, or its builder is archived. The person can land it from the dashboard, waiving the holds reserved for them, merge and deploy the pull request themselves, fix what held it and land it again, or start a new review with `nexus review <thread>`. Deciding not to land needs nothing new: for a landing that has not merged, closing the pull request ends the review `closed`, and archiving the builder ends it `cancelled`, which takes the dashboard's Land button away and clears the builder's `decision`. A held landing archives nothing on its own. Only a review that lands archives its builder and its reviewer.

Landing again is `nexus land <thread>`, or the Land button on the builder's page of the dashboard, which calls the same route and so needs a deployer's device too. The button sends the commit its confirmation named, and the route lands nothing if the review has moved to another commit since. It checks every condition again, so without a waiver it helps only when what held the landing has changed, such as checks that have passed since or a description that now says what could not be checked live. For the description, the landing first asks the reviewer to quote, from the description as it is then, what could not be checked live, at the same head, and goes on with that quote. The reviewer checks the passage against the change it approved before it quotes it, so the statement still comes through the reviewer's judgment and never straight from the builder's description. The route refuses, with 409, a press on a hold that meets every landing of the head again and that the person cannot waive, such as a Claude reviewer's approval, and the dashboard offers no Land for one, by the same rule. `nexus land` without `--waive` never waives, so a hold reserved for the person holds it again. `nexus land --waive` answers Land to the review's open question about its holds, once the person confirmed the holds it names in a terminal. With no question open, it sends what the button sends, the commit the review is at and the holds the person may waive there. A waiver through the land route that names the holds of the open question answers it too.

## Asking the person

A review asks the person about the holds they may waive as soon as Nexus knows them, rather than once it is merging. When a round starts, the control plane reads the head's change against its base and works out the holds that change decides, such as a reserved path. It asks one [question](design.md#questions-for-the-person) that names every hold a Land press at that head would waive, so the person can answer while the reviewer reads and the check runs. The question's first line names each reserved case by the name this policy gives it, such as "pylon image rebuilds" or "changes to login or auth", and a line per hold says why it holds. Its options are Land and Leave it, and only a deployer may answer it.

Land does what pressing Land did before questions: it waives the holds the question names, at that head and at a rebase of it that leaves the change as it is, and asks for the landing. On a review that the land route takes, the answer is that press. On a review still under way, it records the waiver and the request, and the review lands only once the reviewer approves and the checks pass, as every landing does. That request is for the head and base the question named: a later round at another head or against another base drops it, unless the round carries the approval of the same change on the same base, and the review then stops at approval for the person, as one started without `--land` does. A review started with `--land`, or by its project, keeps the request it had. Leave it waives nothing, and the review holds for the person when it tries to land.

Holds that appear later are asked about then: a reserved case the reviewer names in its verdict, or a hold the landing meets, such as a changed `.nexus/check` that GitHub's files show. If the question about the earlier set is still open, the new question replaces it, and an answer to the old one finds no question. If the person already answered Land, the waiver covers only the holds they saw, so the landing holds on the new one and the review asks again, naming the whole set. A question never asks about holds the waiver covers, a review that cannot land, or one that a Claude reviewer or a reviewer on the builder's own model approved, since no press lands those. A question waits on the person for its own review only: it makes the builder's attention `decision`, and nothing else in the pipeline waits on it.

## A second reviewer

Since 2026-11-05 a project can ask for a second reviewer on another model, with `nexus project edit --second-reviewer`. On 2026-11-04 a diff read on a second model found a serious bug in three of the five pull requests that landed that day, [#442](https://github.com/ramtinJ95/nexus/pull/442), [#444](https://github.com/ramtinJ95/nexus/pull/444) and [#445](https://github.com/ramtinJ95/nexus/pull/445), and Nexus's reviewer had already approved #444 with its bug. A project that never sets it gets one reviewer, as before.

The project's rule names which pull requests get one: every one, or one whose change has at least a number of changed lines, or a hold for the person on its paths, or either. Changed lines are the added and deleted lines of every file, tests and docs included, and a file GitHub shows no patch for counts as large enough. A hold on its paths is a reserved path of a Nexus pull request, or a change to `.nexus/check` or `.nexus/verify` in any repository. `--second-reviewer on` sets either 150 changed lines or a hold on its paths. The three pull requests had 249, 158 and 220 changed lines, and only #444 and #442 had a path hold, #442 only by a word its patch happened to use, so the size catches all three and the paths catch a small change to the policy itself. The rule reads the change when the review starts and again at each new round's head, so a pull request that grows past the size in a fix round, or in a push after its approval, gets a second reviewer from that round on, and keeps it for every round after.

The second reviewer runs on another model than the builder's and the first reviewer's. The harness runs one model for every thread, and one of the two already runs it, so the second reviewer is a Claude worker on the first of Claude Opus 5.5, Claude Fable 5.1 and Claude Sonnet 5.5 that neither runs, which needs the project to grant a Claude token. It gets the same first request as the first reviewer, the diff, the pull request's description and the builder's brief, its first message, cut at 8,000 characters as the description is, and never hears what the other reviewer found or answered: in each later round, each reviewer gets the builder's answers to its own findings alone. Both read each round at the same time. The builder gets both reviewers' findings in one message, under the reviewer that found each, and answers the second reviewer's under IDs that start with `2.`. A round approves only once both approve, and it counts once against the review's rounds.

A second reviewer never approves by failing. One that gives no verdict Nexus can read, whose model keeps failing, or whose thread the person archives holds the review for the person, as the first reviewer would. A thread that cannot start, as when no node has room, is tried again each minute, and the round waits for it. Where no model can run for it, or its thread has not started within 30 minutes, the review says so and runs with the first reviewer alone, and its landing holds for the person, who may waive that hold. Once both reviewers approved a round and the review waits at the approval or for the person, the loop archives the second reviewer's thread, since only the first is asked to quote what could not be checked live, and a new round starts a fresh one at its head. A reserved case the second reviewer names holds the landing as one the first names does. A Claude second reviewer's approval is read from its pylon too, but it never stands in for the first reviewer's, so it needs no hold of its own: forging it gets a landing no further than the first reviewer's approval alone would.

## What the person may waive

Answering Land to the review's question, pressing Land on the dashboard, or confirming `nexus land --waive` in a terminal, is how the person waives a hold. `nexus land` without the flag never waives one, so an agent that drives the CLI does not waive a hold by accident. A project in yolo mode answers for the person, as [Yolo landing](#yolo-landing) says.

| Hold | The person may waive it | Why |
|---|---|---|
| A reserved case the reviewer named | Yes | The policy reserves it for the person, and pressing Land is the person confirming it. |
| A reserved path of a Nexus pull request | Yes | The same, for the paths that might touch a reserved case. |
| A change to `.nexus/check` | Yes | Accepting a new check is the person's call. |
| A change to `.nexus/verify` | Yes | Accepting a new live check is the person's call. |
| No second reviewer could run where the project asks for one | Yes | Landing on one reviewer's approval is the person's call. |
| A Claude reviewer's approval | No | A Claude reviewer's verdict is read from its pylon, where code the pull request runs could write a forged one. The findings and reserved cases the person would be waiving come from that same verdict, so a waiver would accept what a forger chose to show. Only a harness reviewer's approval lands, or the person merges on GitHub. |
| A deployer no longer asking for the landing, or a project that no longer lands on its own | No | The landing needs a deployer who asked for it. |
| An open P0 to P2 finding, or one the builder left unanswered | No | Findings block until they are fixed or rejected with a reason. |
| `.nexus/check` failed or did not run at the head | No | Only a passing check at the approved head lands. |
| The live check failed or did not run at the head | No | A repository with a `.nexus/verify` lands only once its live check passed at the approved head. |
| Failing or pending GitHub checks | No | They hold every landing until they pass. |
| A head that moved after the approval, or a merge at another head | No | Only the approved commit lands. |
| A branch that conflicts | No | It cannot merge. When it is the only hold the waiver does not cover, the builder rebases. A rebase that leaves the change as it was, on the same base, keeps the approval and the waiver, and the checks run again. Any other needs a new review and a new waiver. |
| A pull request that is not open | No | It cannot merge. |
| A reviewer on the builder's own model, or no statement of what was not checked live | No | These are the policy's other conditions, which an agent can meet. The first holds every landing of the review, so a press cannot land it. The second clears once the description says what could not be checked live and a Land press has the reviewer quote it. |

The Land card on the dashboard marks each hold "you may waive" or not, with the reason. While the review's question about these holds is open, the card sends the person to it. Otherwise, when every hold that would meet the landing again is one the person may waive, its Land button waives them, as after a Leave it. Its confirmation names the pull request, the commit and that it waives the holds the policy reserves for the person, and the button sends that commit and those holds. The caller must still be a deployer, and each named hold must be one the review has at that commit. The landing then checks every condition again, as `nexus land` does, with the named holds met at that commit and nothing else. The review records the waiver, who waived which holds at which commit, `nexus show` prints it, and the event stream gets a `review.waived` event.

A waiver names each hold by the text the person saw, and the control plane records the kind of hold that text was. The landing matches a waiver by that kind at the waiver's head, so rewording a hold does not undo a waiver, and a waiver of a reserved case the reviewer named never covers a reserved path that hits the same case. A waiver lasts for the landing it starts, across a rebase that leaves the pull request's change as it was: the same patch and mode for every file against the same base, hunk positions aside. A changed line, a changed mode, a new base, or a file GitHub shows no patch for, stops it, and the review names the files whose patches differ. If that landing holds again for anything else, such as checks that turned pending or a reserved path the reviewer did not name, the review lists every hold it met, those the person waived too, and the person confirms them all again.

## Yolo landing

`nexus project edit <id> --auto-review yolo`, or the dashboard's Auto review switch on the project, turns on yolo landing: the project reviews and lands its builders' pull requests on its own, as `land` does, and the review loop also answers each review's holds question with Land, in the person's place, so a batch keeps landing while no one watches. It answers for the caller who turned it on, who must be a deployer, as `land` needs, and again on every answer. The loop answers in the same pass that asks, once that pass has saved its steps, through the same code a Land answer takes: the waiver names the holds the question named, at its head, and records the project whose setting gave it, so `nexus show` prints `waived by <caller>, by project <id>'s yolo setting`, and the `review.waived` event carries `yolo`. It answers only a review asked to land, by its project or with `--land`, so a review the person started without `--land` still stops at approval.

The setting waives only what the person may waive, which the table below lists, every reserved case among them, data-deleting migrations and changes to auth included. Everything else still holds every landing: open findings, a failed or missing check, a reviewer that has not approved, a Claude reviewer's approval, failing GitHub checks. A waiver lasts for the head it names, as any waiver does, so a new push asks again and the setting answers again. Switching the project back to `land` or `review` answers nothing from the next pass on, and a question already answered stays answered. A landing the project asked for stays the project's when the setting answers it, so under `land` it goes on, and under `review` or off it holds for the person. A landing a deployer asked for with `--land` becomes `enabledBy`'s, as the same press by them on the dashboard would. The setting has no expiry and covers the whole project, not one batch.

## Known limits of waivers

- A waiver is not a security boundary. The control plane identifies callers by their tailnet node, and an agent on the person's Mac is the same node as the person, so an agent with the person's deployer identity could post the same request the Land button does.
- The control plane's own code decides what the person may waive. A change to it is a change to auth, which holds the landing for the person.
