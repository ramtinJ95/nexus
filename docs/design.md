# Nexus design

Nexus runs coding agents inside microVMs on your own Linux machines. Each microVM is called a pylon. Nexus is modelled on Amp Orbs: you start a thread, a fresh pylon boots with the repository and tools ready, and the agent keeps working after your laptop sleeps. You come back later to steer it, open previews of the running app, and collect what it produced.

Status: Nexus runs on both nodes. The control plane and a probe run on `rj-firebat`, and a second probe runs on `infra-testbench`. A thread starts from any client, its pylon boots from the current image, and the agent's answers stream to every client as it writes them. `nexus attach` gives a Mac terminal on the pylon's Herdr sessions, through the control plane. A port that something in the pylon listens on can be published as a preview on the tailnet, and unpublished again. [The CLI reference](cli.md) lists the ports that cannot. Archiving pauses the pylon, and unarchiving wakes it with its disk, services and sessions intact. A Claude Code session logged in inside a pylon resumes its conversation after an archive and a wake, which was proven by hand on `rj-firebat`. `src/control/thread-on-node.ts` checks a thread's lifecycle on a node with a scripted model. The record shapes live in [the data model reference](data-model.md). The probe, project config and template image contracts live in [contracts](contracts/rationale.md). The CLI is described in [the CLI reference](cli.md). Planned work is listed in [the roadmap](roadmap.md).

## Nexus copies Amp's split between the agent loop and the machine

Amp runs model inference and the agent loop on its own servers. The orb only executes tools and holds the checkout, the build output, and the running apps. Amp's self-hosted orb providers make this explicit. Amp sends a provider program `spawn`, `pause`, and `delete` jobs, and each job must be safe to repeat and finish within five minutes. ([Self-hosted orbs](https://ampcode.com/docs/orbs/self-hosted).)

Nexus keeps the same split:

- One pi-durable harness on the control plane runs every thread's agent loop. It holds the model credentials and commits every step to its storage.
- Each pylon is a machine that executes tools. A pylon can be lost or rebuilt without losing the conversation.

The split matters for two reasons. Credentials for model calls never enter a pylon. A thread also survives a pylon crash, because a tool call that was in flight is reported to the model as interrupted instead of rerun. That is pi-durable's documented behaviour for tools not marked `replay: "safe"`.

## A thread is one conversation and one pylon

A thread is one unit of work. It always has exactly one pi-durable conversation and exactly one pylon. Every thread belongs to a project, and a project is one git repository. A scratch project has no remote: each of its threads starts from an empty repository, made with `git init` on the project's branch, for work that does not exist yet. Pylons are ephemeral, so deleting a scratch thread deletes everything in it. Nexus keeps no copy, and the agent publishes what is worth keeping, typically to a new GitHub repository.

You use a thread in either of two ways, or both at once:

- **Autonomous.** You give the thread a prompt. The pi-durable agent works while you are away.
- **Hands-on.** You open sessions inside the pylon with Herdr: interactive Claude Code, interactive pi, or a plain shell. These sessions play the role of Amp's Terminal pane. The conversation stays empty if you never prompt the pi-durable agent.

A Claude Code session is a session inside a thread, not a separate kind of thread. A second thread kind would need its own code paths in the dashboard, the outputs, and the wake rules, and would save only one empty record.

## The parts

- **Nexus control plane.** One process on the main node, `rj-firebat`. It owns the API, the registry in SQLite, the event stream, and the dashboard. It stores the desired state of every thread and pylon.
- **The harness.** pi-durable, running inside or beside the control plane. It reaches a pylon through pi-env's Rust daemon inside the pylon, over a byte stream the probe carries. Spike S3 chose the daemon over a new adapter.
- **Probes.** One node agent per machine, today `rj-firebat` and `infra-testbench`. A probe runs pylon jobs, reports what it observes about its pylons and sessions, and carries terminal streams. The control plane opens every connection to it over HTTP and WebSockets on the home tailnet. The probe accepts a caller only if `tailscaled` names it as the expected node. The tailnet policy is unchanged, with no tags and no ACL edits. The control plane follows the nodes `control.json` names and every node that joined with a token, and adds a joined node's probe without a restart. It tells each probe the tailnet node IDs of the other nodes, its peers, which may fetch its images and templates, and the probe keeps `auth.peers` from `probe.json` until then.
- **Backends.** A probe never creates a VM itself. It drives an in-process backend interface. Amp's provider uses one dispatch program per job, but a pylon cannot dial out the way an orb does, so the probe also carries exec, terminals and services, and those do not fit one short program per job. The jobs keep Amp's `spawn`, `pause` and `delete` shape. The first backend is `pylon-vm`, a hard fork of pi-sandbox that drives Gondolin and QEMU. A Docker backend is a cheap test double. A Firecracker backend can come later without changing the control plane.
- **The pylon image.** A Debian root filesystem with Amp's conventions: a non-root `user` with passwordless sudo, the checkout at `/home/user/workspace/repo`, git, `gh`, Neovim, Node, Python 3, Herdr, Claude Code, and pi, with your Claude Code and pi setup baked in (see Configuration). Gondolin supplies its own kernel and takes the root filesystem from an OCI image. Spike S1 checks this.
- **Sessions.** Sessions run in Herdr inside the pylon, which starts when the first session opens or a terminal attaches. Nexus does not use tmux. Herdr reports pi status through its pi integration, and Claude Code hooks report Claude Code status. One table in `src/session-harness.ts` holds what differs between the harnesses a session runs, `claude-code`, `pi` and `shell`: the dashboard label, Herdr's agent kind, the launch arguments, whether it takes a model or a first prompt, the state it seeds, whether a session runs in one pane only, and whether Herdr's working status is its agent activity. The probe's command schema, the API, the dashboard, the CLI's usage line and the registry's ingest all read it, so a new harness is one entry plus any launch code of its own.
- **Previews.** Each probe publishes a pylon's previews with `tailscale serve`, so any device on the home tailnet opens them over HTTPS. A preview belongs to a declared service, or to a port something in the pylon listens on, which a person or the agent publishes and can unpublish. Gondolin's ingress reaches a pylon only through its 127.0.0.1, so each preview goes through a relay in the pylon that connects to the server on 127.0.0.1 or `::1`. A server bound only to `::1`, as Node servers that bind `localhost` are, is previewed like any other. Spike S4 checks this. The app gets plain HTTP from the probe's gateway, with the public `Host` and `X-Forwarded-Proto: https`. An app that ignores that header names its own scheme, so it redirects the browser to `http://`, which the preview's port does not answer, and links its assets and live-reload socket over `http://` and `ws://`, which the browser blocks as mixed content. The gateway therefore rewrites a `Location` that points at the preview's own `http://` address to `https://`. It also adds `Content-Security-Policy: upgrade-insecure-requests` to every response, as a policy of its own, so the browser fetches the rest over HTTPS and WSS. The browser upgrades a navigation to an `http://` address on the node's tailnet name too, whatever its port, so a preview's link to a plain-HTTP port on that name, such as the dashboard's HTTP listener, fails with a TLS error. No CSP setting upgrades a page's own subresources but not those navigations, and rewriting bodies to do it would be far more work, so previews accept that cost. The gateway sends no HSTS, because HSTS covers every port of the node's tailnet name, and the dashboard still serves plain HTTP there. A preview of a pylon that cannot serve it yet, such as a paused one, gets a page that reloads every 3 seconds, and the visit wakes the pylon. A fault in finding the preview's origin, such as a status file the probe cannot parse, gets 502 with the reason, which also goes to the probe's log.
- **Clients.** You drive Nexus from four places, which show the same things: the `nexus` CLI on the Mac, the control plane's web dashboard, a Claude Code mod in the `claude-mods` repository, and the `pi-nexus` pi extension. The two extensions run the CLI and read its JSON, so the CLI is the contract they share. The control plane streams each thread's conversation to them over server-sent events as the harness commits it.
- **The thread page.** A terminal is the closest thing to working in the agent's own session, so the dashboard makes it the easy path and carries what a terminal does badly: the overview of threads, diffs, images and questions. Every thread page that can attach shows `nexus attach <thread>` with a copy button, as `nexus show` prints it, and a Terminal tab beside the conversation that attaches over the attach route in the page, with xterm.js. Both land in a Claude worker's Claude Code pane, ready to type into. The attach focuses that pane in Herdr before Herdr's client starts, and Herdr's focus is the server's, so every client lands there. The Pylon tab's Sessions list opens a shell, pi or Claude Code session, shows each running one in the terminal, and closes any but the worker's own after a confirm. Show in terminal attaches a terminal that is not attached yet in that session's pane, and asks Herdr to focus the pane for one that is, which moves every attached terminal, `nexus attach` included, as the list says. The terminal stays the whole Herdr session rather than one pane, so it is the same thing `nexus attach` gives. The tab behaves like a desktop terminal. Shift+Enter or Option+Enter makes a newline, and Option otherwise types the layout's characters, such as @ and | on a Swedish keyboard. Option-drag selects natively, and Herdr's own mouse selection copies to the clipboard through OSC 52, so output in the pylon can set the person's clipboard but never read it. A link, printed or OSC 8, opens in a new tab. A dropped connection attaches again with backoff while the page shows, and a page hidden for 10 minutes detaches so the pylon can pause, then attaches again when it shows. The state bar and questions stay under the terminal, and the composer gives way to it, since a Claude worker's terminal is its prompt. A Nexus agent runs on the control plane, so its thread's terminal is the pylon's Herdr session, and its conversation is the composer's. Above the composer, one line says whether the agent is working, waiting for the person and why, or idle, and the composer works the same for both agents: ⌘↵ sends, or steers a run that works, and ⌥↵ queues a message after a Nexus agent's run. A Claude worker takes any message at its next step, so it has nothing to queue after.
- **Themes.** The sidebar's footer picks the dashboard's theme on every page: System, which follows the device's light or dark, Light, Dark, and the person's own Tokyo Night, Catppuccin Mocha and Kanagawa Wave, as [macarchy](https://github.com/ramtinJ95/macarchy) defines them. A toggle beside it switches between Light and the last dark theme picked. The choice stays in the browser's localStorage, so each device keeps its own, and the control plane holds no setting. A theme is one block of `src/control/dashboard/style.css`: its colours, the Shiki theme the diff panel highlights with, and the terminal tab's palette. A script in the page's head, which the content security policy allows by its hash, names the stored theme on `<html>` before the first paint, and a change applies at once, to an open diff and terminal too.

## Shared attention and dashboard notifications

The control plane owns attention and the shared seen marker, rather than each client keeping its own interpretation. List rows and detail expose failed, decision, parked, limited, unread reply, working, waiting or null, in that order. The registry persists reply-end and seen timestamps. Marking seen or unread is not human activity and never wakes a paused pylon; a dashboard visit remains the separate human-activity action described below. The dashboard marks a reply seen once, when its conversation is visible and focused and shows that reply, so a reply another client marked unseen stays unseen until the page shows a newer one. It sends a reply watermark captured before reading the rendered conversation, never a newer timestamp from attention polling. A streamed conversation is certified without replacing the stream's patch structure when the poll names the view the stream's last frame showed, since a poll does not render the conversation while it streams, or else against a matching HTML snapshot; while disconnected, only a rendered HTML refresh advances the watermark. A Claude worker's transcript is as of its last read, so its page sends no watermark until a read that started after the newest reply was recorded, and reached the transcript's end, is stored. The API caps the mark at that watermark. Reply timestamps advance monotonically past seen markers, including when both events happen in the same millisecond.

The dashboard uses attention in the sidebar and home table, which build each thread's line from its API row, once per page. A page reads the threads, the queue and the release reports a fixed number of times, however many projects and nodes it shows, and the sidebar's release lines are `GET /v1/release`'s view, so a stale report reads pending and a node without one reads pending with no deployer report. It silently baselines threads on first load, notifies immediately for a new failed, decision, parked, limited or waiting state, and delays a new reply by two seconds, cancelling if work restarts and scheduling again for the follow-up’s final reply identity even if attention never stopped being reply. A focused dashboard shows a toast with Open for another thread; an unfocused one uses a system notification only in a secure context with permission. Permission is requested only by clicking its control. On plain HTTP, background system notifications are unavailable; toasts still work. System notifications use the optional direct HTTPS listener on 7443; see the deployment guide for certificate provisioning. One tab of the browser holds a Web Lock and follows `/v1/events?follow=true&since=latest` for the kinds that change a row's attention, reply or turn: `attention.changed`, `thread.turn-ended` and the session events but heartbeats. It reads `GET /v1/threads?deleted=false` each time the stream connects, once for each batch of those events, when a held-back reply comes due, every second while a turn runs over an unread reply, whose stop may send no event, a second after a read failed, and every ten seconds for what sends no event, such as a delete. It hands the rows to the other tabs over a BroadcastChannel, and a tab that loads or comes back into view asks it for them, so a hidden tab notifies as fast as the stream's one-second tick without a request or a stream of its own. Every tab shows that one tab's reads in order, so none shows older rows over newer ones, and every tab holds a reply back to the same moment. When that tab closes, another takes the lock. A page over plain HTTP has no Web Locks, so each of its tabs follows the stream and reads the list on that schedule itself, and hands its rows to no other tab. It closes the stream while it is hidden, since a hidden tab there cannot notify and the control plane has few streams to give, and keeps the ten-second read, so its rows are fresh when it comes back. Each list read and seen update has a ten-second deadline, including its response body, so a stalled connection releases its lock and the next read retries. A notification says the attention's label, such as "needs your decision" or "waiting for input", and opens the card in [Needs you](#needs-you) for what the thread waits on, or the thread for a reply. The browser tab shows no count: its title is the page's own and its icon is always the Nexus icon.

Rows of open threads whose attention is working or null are dimmed in the sidebar and home table, so the eye goes to the threads that need a fix, a review or a reply: failed, decision, parked, limited, reply and waiting stay bright. Waiting ranks below working in the order, yet it is the one of the two that is blocked on the person. One table in `src/control/attention.ts` holds each attention's label, tone and whether it needs the person, and the rows, Needs you and the notifications all read it, so a thread whose row stays bright is notified. The open thread's row never dims, and a dimmed row comes back to full strength on hover or focus. A thread whose harness or session turn runs shows `working 1m 03s` in its row, its home-table and inspector Agent field and the run bar, counted from the registry's `workingSince`. The page ticks it every second from that one timestamp, so the clock makes no requests of its own. A turn that began before the registry recorded starts shows `working` without a clock.

A conversation shows each tool call as one line: a mark for whether it succeeded, failed or still runs, the tool, its key argument, what it changed or how many lines it printed, and how long it took. A command shows its first line and a path in the checkout shows relative to it, so Claude Code's absolute paths read as pi's relative ones. Both agents' tools read under one name, so pi's `bash` and Claude Code's `Bash` are both Bash, and an MCP tool reads as its own name without its server's. The harness records how long a call ran, and a Claude worker's call is timed from its transcript, from the call to its result. A line opens to the call's whole input and output. A failure, an edit's diff and a running call start open. An output or diff of more than 30 lines shows its first 12 and a Show all line that opens the rest in place, while a running call's output shows whole and follows its end. Calls run in a row between two messages group under a line that says what they did, such as "Ran 3 commands, changed 2 files", and how many calls it holds. Calls are counted by what they do rather than which tool made them, after t3code's tool-group summaries: an edit and a write to the same file are one changed file. Commands, changes and subagents come first, then reads and searches, and past three phrases the rest are counted as other tools. A group of up to five calls starts open, so each call's line shows, and a longer one starts closed unless a call failed or runs, so a busy turn does not bury the answer around it. A lone call has no group line. The calls are set in small, muted monospace on a thin rule, apart from the agent's prose. A notice, such as an interrupted turn or a model error, stays visible between two groups. The harness conversation and a Claude worker's transcript look the same.

### Needs you

The home page starts with Needs you: a card for each thing that waits on the person, so one with many threads running finds every Land button and question in one place. The sidebar's Needs you link, on every page, counts the cards, and on a phone each page's bar has the link, as the sidebar is a drawer there. No tab's title or icon counts anything. The list is server-rendered from the registry's attention and each thread's detail, as the thread page is, and polled with the page, so acting on a card takes it off within a poll. In the open threads, a card is:

- a review held for the person, `needs-person` or `approved` with holds, that its thread page would offer for landing: the PR's link, the opening of its description, the reviewer's quote of what was not checked live, and the thread page's own landing card, with its holds, whether each is waivable, the findings and the Land button that waives what the person may;
- any other `needs-person` review, as its thread page's card, described below;
- each open question, a Claude worker's AskUserQuestion and a planning proposal among them, as its thread page's card, with the judgment it belongs to above one a failure judgment asks;
- a builder that stopped short of a pull request after two nudges, as its thread page's card;
- a thread that failed, is parked, stopped on its usage limit, or has a dialog in its terminal, with what is wrong and the one action that gets past it: Retry, Archive or Open terminal, which opens the thread page on its terminal tab.

Each source of the `decision` attention, a `needs-person` review, an open question and a nudge that reached the person, has a card on the thread page's dock, and Needs you shows that same card with the same buttons, so a thread whose header says "needs your decision" always has something on its page to act on:

| Source | Card | Action |
|---|---|---|
| A `needs-person` review the person can land | Held for you, with the holds and findings | Land, waiving what the person may, or a note to merge on GitHub when a hold holds again |
| A `needs-person` review with nothing to land, its pull request open | Review needs you: the reasons, the round it ended in, and a link to the reviewer thread | Review again, which starts a new review through `POST /v1/threads/<thread>/review`, landing when the project's auto-review lands; Cancel review |
| A `needs-person` review whose pull request merged outside it | Merged outside its review | Deploy with `nexus deploy` when it is Nexus's own repository; Cancel review |
| A `needs-person` review whose landing merged and did not deploy | Merged, not deployed, with the landing's steps | Deploy the merge commit with `nexus deploy`; Cancel review |
| An open question, a judgment's or a planning proposal among them | Needs your decision, Claude asks or the proposal | A button per option, or the AskUserQuestion form |
| A builder that stopped short of a pull request after two nudges | Stopped short of a pull request | Write to it, which focuses the composer: the person's message makes the thread theirs |

Cancel review is `nexus review --cancel`, which since CLI 0.46.0 also ends a `needs-person` review, so it stops counting as the person's decision: the review ends `cancelled` by them and its reviewer is archived, while the pull request and the builder stay as they are, and a new review can start. Review again on a project that lands its reviews needs a deployer, as Land does, and a device that is not one gets the button disabled with the reason.

A new reply waits on no one, so it gets no card, but it does not hide a dialog in the terminal, which the session's own state says waits. Cards go oldest first, by when each began to wait: when the review entered the phase it waits in, from its `review.changed` events, or its own `since` once those are gone, the question's asking, the usage-limit stop, or else the agent's last activity. Each card keeps its place while the person works down the list, and the one that has waited longest is at the top. The PR watch keeps the description's first paragraph past its headings, at most 400 characters, as `PullRequest.summary`, and the card shows three lines of it.

## Lifecycle follows Amp

- Starting a thread boots a fresh pylon from the current image, on the node the request names, on the node where it fits best when the request asks for `auto`, or else on the project's default node, which may itself be `auto`, as [Placement](#placement) describes. When the node holds a ready template of the project's setup at the thread's commit, the pylon copies the template's disk, checks out that commit and runs `.nexus/resume`, so `.nexus/setup` does not run. Otherwise it clones the repository and runs `.nexus/setup` itself, and the first such start of a setup on a node builds a template of it for later threads. `nexus show` says which path a thread took and why.
- A pylon sleeps when its agents are idle and nobody has used it for a while. Amp uses 5 minutes of agent idleness and 20 minutes without a human. Nexus starts with the same numbers. A terminal attached to the pylon's Herdr session, such as `nexus attach` through the control plane, counts as a human for as long as it stays attached, because the probe counts the guest's Herdr clients in every observation. Close the terminal to let the pylon pause. The dashboard's Terminal tab detaches on its own once its page has been hidden for 10 minutes.
- Sleep is a disk checkpoint. The VM stops and memory is lost.
- Waking boots the pylon from its checkpoint, runs `.nexus/resume`, restarts services, and relaunches every recorded Herdr session into its prompt. Claude Code runs `claude --resume <session id>` and finds its transcript on disk, or starts afresh under the same ID when the session was never prompted. The command that was running at sleep time shows as cut off.
- A Claude Code session runs in one pane, whatever the number of wakes. Herdr restores each workspace as a shell, because the image turns off its own agent resume, and the relaunch starts Claude in the restored pane. The probe runs a wake's relaunch, the launches and the sends of one Claude session one at a time, so a message that comes while the relaunch runs waits for it. A send that finds the session in no pane uses the restored pane the sessions file records for it before it opens a new workspace. A sessions file that names one Claude session in several panes, as wakes before this fix left behind, brings it back in the first and closes the others. Captures are in [`docs/verification/one-claude-session/`](https://github.com/ramtinJ95/nexus/tree/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/one-claude-session/).
- A session is `paused` only while its pylon is. The pylon's first running observation after a wake resumes its sessions in their panes with status `unknown`, before the probe has read them, so a read that fails or comes late never leaves a running Claude labelled paused. The probe logs a failed sessions read once, until one succeeds. Captures are in [`docs/verification/session-state-after-wake/`](https://github.com/ramtinJ95/nexus/tree/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/session-state-after-wake/).
- Archiving a thread puts its pylon to sleep at once, and its pylon is deleted once the thread has been archived 24 hours. The thread and its conversation stay, and an unarchive then boots a fresh pylon from the thread's recorded image and commit, so unpushed work is gone and a Claude worker's session starts without its history. If no online node still holds that image, the pylon fails with `artifact-missing`, and the person retries it or starts a new thread. Deleting a thread deletes its pylon.
- A clean shutdown or reboot of a node pauses its pylons before the machine goes down. systemd stops the probe with SIGTERM, and the probe asks `systemctl is-system-running`. Only when the answer is `stopping`, so the whole machine is going down, does the probe refuse new jobs and pause every running pylon as an archive does. It gives the pauses 150 s, and the unit's `TimeoutStopSec` of 180 s makes systemd wait for them and the close. Before the first pause starts, the probe writes the pylons it found running to `/var/lib/nexus/shutdown.json`. The probe that starts after the boot reports each of them, and the control plane counts that report as agent activity, so the thread runs again as after any new activity and sleeps later under the idle policy. A thread that was already paused or archived is not in the file, and stays as it was. A pylon whose pause failed, or did not finish in time, comes back broken, and the planner fails it with the reason the shutdown recorded until a person retries it. A node whose encrypted root waits for its unlock over SSH only boots later, and its pylons wake once its probe reports in. A restart of the probe alone, as every deploy makes, pauses nothing.
- A stopped pylon could move to another node by copying its disk. Disk checkpoints do not depend on the CPU, so moving between the Intel and the AMD node works. Spike S7 tested one round trip by hand. Nexus has no move job yet, so a pylon stays on the node it started on.

Pylons are owned by threads only. Named pylons that outlive a thread are deferred. The pylon record stores its thread, so adding them later changes one field and the delete rule.

## Placement

Each probe reports what its node has and what its pylons hold of it. A VM that is up holds its CPUs and memory, from the moment it launches until it stops. Every pylon holds its disk size until it is deleted. A paused pylon holds no memory, because its VM has stopped. Counting its memory would make a node with many paused pylons look full while it runs none of them. Committed CPUs and memory count every VM whose controller is alive, whatever runs in it: running and booting pylons, check and reviewer threads, and orphaned VMs the registry has not placed there. The probe also names the secrets in its node's secret file, without their values, the secrets it takes from the control plane, and whether the node has a git SSH key. `auto` counts a secret the probe takes as one the node has, even before the control plane has handed it over, so a start right after a restart is not refused. The pylon's boot waits for the handoff instead.

A thread starts on its project's default node unless the start names another node or asks for `auto`. A project's default node may itself be `auto`, and new projects default to it, because the person wants work spread out. A pinned default sent every thread to one node: about ten Claude worker threads committed 40 GiB on `rj-firebat`'s 22.8 GiB while `infra-testbench` sat idle. `auto` still refuses a node that cannot run the project's pylons, so a project needs a pinned node only when it must run on one machine. The cost is that when no node has room, a start fails instead of booting into an overcommitted node. Existing projects keep their default until a person edits it. With `auto`, the control plane weighs every node. A node can run the pylon when it is online, holds the current image, has every secret the project grants, and has a git SSH key if the repository or the dotfiles use SSH. The allowlist is the same on every node, so it never rules one out. Of the nodes that can run it, the pylon goes to the one with the most memory left once it boots there, then the most CPUs, then the most free disk. Memory and disk must fit, and a node whose committed memory already exceeds its memory is refused as overcommitted. CPUs may go below zero, because VMs share a node's CPUs and an idle pylon uses little of them. The room left counts pylons the planner is about to boot or wake on the node, which its last observation does not count yet: an unreported pylon holds all it asked for, and a paused one about to wake, or one whose controller died and a person retried, holds its CPUs and memory again. A broken VM that is still up is already counted in the node's capacity. A node whose last observation came from a probe too old to report grants is never chosen. When no node fits, the start fails with each node's reason and starts nothing. The review loop starts a builder's reviewer and check threads beside the builder while its node can run them, and once it cannot, on the node with the most room left, as `auto` does. When no node has room they go beside the builder all the same, so a review never waits for room. The thread records the placement, and `nexus show` prints it. The dashboard's start dialog offers `auto` beside the nodes.

A start may size its thread over its project's resources, field by field, so one heavy thread need not raise every thread's size. The size is frozen into the pylon's boot like its repository and grants, and placement weighs and reserves the thread's size, not the project's.

Every start reserves the room it placed its pylon in, whichever way the node was chosen, from the choice until the pylon's registry row exists or the start fails. A harness thread's conversation is created between the two, so without the reservation two overlapping `auto` starts would choose the same room. The registry holds the reservations in memory, shared by the API and the review loop. A crash ends the starts that held them, so losing the reservations loses nothing.

`nexus nodes` and the dashboard say which nodes are overcommitted, and sort each node's observed pylons into up, paused, archived, crashed and orphaned, so a person can see what a full node holds and what its paused pylons need to wake.

A scheduler that places work on its own still needs:

- A move job. A pylon stays on the node it booted on, so a node that fills up stays full until its threads are deleted. [The lifecycle](#lifecycle-follows-amp) describes how a move could copy a stopped pylon's disk, and spike S7 showed that copying checkpoints needs verifying.

## Node diagnostics

When a pylon's controller crashed, the only way to see why was to SSH to its node as root and read `controller.log`, and Tailscale SSH's login check stops an agent from doing that on `rj-firebat`. So a coordinator, an agent or the person could not tell a node's failure from the code's, as with the 13-second guest-command timeouts on `infra-testbench` on 2026-10-27 that only an SSH session found. Two read-only paths now answer it.

A broken pylon's observation carries the last 60 lines, at most 8 KiB, of its instance's controller log, and the planner's failure for it ends with them, as a failed job's ends with its log. The registry stores the failure, so the lines outlive the node and a control-plane restart. The probe redacts the text first: the values it holds, Gondolin's placeholders, and the shapes of common credentials. It cannot know a secret it does not hold that has no known shape, so a setup script that prints a password in plain text still leaks it. [The CLI reference](cli.md#node-diagnostics-0360) lists what it catches.

The probe also serves its host's health on request: load, CPUs, memory and swap, free disk where the pylons' disks are, temperatures where the host exposes them, and each running pylon's controller and QEMU with their CPU and resident memory. It is not in the observation, because sampling CPU takes a second and nobody needs it every minute. The control plane passes it on to deployers only, as `nexus node` and the dashboard's node page. Nothing on these paths acts on the node.

## Network and credentials

- Gondolin blocks all outbound traffic except HTTP, TLS, and SSH to allowed hosts. Each project lists its allowed hosts.
- Model credentials for pi-durable threads stay on the control plane.
- Tool credentials, such as a GitHub token, stay on the node. Gondolin substitutes a placeholder in outbound HTTP headers for allowed hosts only. Git over SSH is terminated on the host, so the private key never enters a pylon. Git over HTTPS to github.com asks `gh` for credentials, and `gh` reads `GH_TOKEN` at that moment, so git never stores the placeholder, which changes on every boot.
- Git over SSH reaches only the remotes a pylon booted with, so a repository its agent creates is pushed over HTTPS. A project granted `GH_TOKEN` for `api.github.com` and `github.com` gives its agents `gh`, which creates repositories and hands git the token on each push. PYLON.md tells the agent this, and the configured git author. The optional control.json `gitIdentity: { name, email }` is the person’s identity, not a separate agent account. A project may override it. Every boot, including checkpoint wake, sets `user.name` and `user.email` globally for `user` after installing common dotfiles. With neither configured, git stays unchanged and agents are told to ask the human, not invent an identity.
- Interactive Claude Code and Codex sessions need a `/login` inside the pylon for now. `nexus session open` opens a Claude Code session and `nexus attach` gives a Mac terminal on it, through the control plane, so the Mac needs no ssh access to the node. The project needs `logins: ["claude"]`, whose hosts (`src/control/project.ts`) cover Claude Code's own list of required hosts for a claude.ai login, including `platform.claude.com`, where OAuth tokens are refreshed. The optional hosts are left out: `sso.claude.com` for organizations with SSO, `mcp-proxy.anthropic.com` for claude.ai connectors, `raw.githubusercontent.com` for the changelog, and Datadog telemetry. Claude Code's Remote Control, which lets you steer from the phone, needs a claude.ai login and does not work with a long-lived setup token. Because pylons are thread-owned, every new thread that uses these tools needs a new login. pi needs none in a project with the `chatgpt` login, as [pi's ChatGPT login in a pylon](#pis-chatgpt-login-in-a-pylon) describes.
- Templates never contain secrets.

### pi's ChatGPT login in a pylon

A project with the `chatgpt` login gives the pi in each new pylon a ChatGPT login, and nobody signs in. The control plane already holds one ChatGPT login, the harness's, and keeps it fresh. It hands the current access token to every node's probe, and Gondolin puts the token in place of a placeholder in requests to `api.openai.com`. The token never enters a pylon.

1. Every 60 seconds the control plane reads the harness's `openai` OAuth credential through pi-ai, which refreshes it first when less than 10 minutes remain. The refresh runs under the credential store's lock, so it never races the harness's own refresh of the same rotating refresh token. The control plane sends the access token to every probe with `PUT /v1/secrets/NEXUS_CHATGPT_TOKEN`, which only the control plane may call. It also sends it at once whenever a snapshot shows a probe that takes the token and has not got it, as after the probe or the control plane restarts. The refresh token never leaves the control plane. The control plane sends nothing while the harness signs in with an API key.
2. The probe keeps the token in memory and writes it nowhere. It hands it to the controller of every running pylon, which calls Gondolin's `secretManager.updateSecret`, and a pylon that boots takes the current token in its boot spec. Each handoff goes to every probe and pylon, changed or not, so a pylon that booted during a refresh has the current token within a minute. A probe that gets the token for the first time sends a snapshot at once, which lists it among the secrets it holds. The control plane sends a boot that needs the token only to a probe whose snapshot lists it there, so no pylon boots with a token its first request would be refused with. A probe from before the login looks for the token in its secret file instead and never lists it, so its boots wait for its upgrade. A missing secret fails a spawn for good, so a probe that restarted between that snapshot and the spawn boots the pylon with an unusable stand-in, which the next handoff replaces.
3. The `chatgpt` login grants `NEXUS_CHATGPT_TOKEN` for `api.openai.com` only. Like every grant, it is fixed when the thread starts. Every boot exports the grant's new placeholder to login shells, and a boot hook, after the dotfiles pull, writes it as the access token of the `openai` entry in `~/.pi/agent/auth.json` and keeps every other entry. That entry has an empty refresh token and expires in 2100, so pi never tries to refresh it, and could not.
4. pi's `openai` provider sends `Authorization: Bearer <placeholder>` to `api.openai.com/v1/responses` over HTTPS, with the reply streamed as server-sent events and no WebSocket. Gondolin swaps the placeholder there and refuses a request that carries it to any other host.

The design hands the token to pi's `openai` provider, not to `openai-codex`, because that is the client the token was issued to. The harness's login is pi-ai's Sign in with ChatGPT, which OpenAI issues for `resource=https://api.openai.com/v1`, and pi sends it to the Responses API there. The `openai-codex` provider is another OAuth client, the Codex CLI's. Its token goes to `chatgpt.com/backend-api/codex`, first over a WebSocket, with a `chatgpt-account-id` header that pi reads out of the token as a JWT. Gondolin's swap would cover that WebSocket, because it runs its request hooks on the upgrade request too. But the harness's token would need a JWT-shaped placeholder that carries the account ID, and would go to a backend OpenAI did not issue it for. Nexus cannot test that without spending the live login. Both providers offer `gpt-6-astra`, and the harness runs `openai/gpt-6-astra` on this token every day. The cost is that a model reference in a pylon must name `openai/<model>`. One that names `openai-codex/<model>`, such as a shepherdr profile captured from the Mac, stops with `No API key found for openai-codex`.

| Way | Token in the pylon | Sign-ins | Why not |
|---|---|---|---|
| Device-code login in each pylon | Yes, both tokens, in `~/.pi/agent/auth.json` | One per thread | The person rejects a sign-in per thread, and every agent in the pylon can copy the tokens |
| A relay through the probe at `http://nexus.pylon` | No | None | Every model stream would go through the probe's pylon API, which serves short JSON requests |
| A second control-plane login on the Codex client, with a JWT-shaped placeholder for `chatgpt.com` | No | One, kept apart from the harness's, because a refresh rotates the refresh token | It keeps `openai-codex` model references working, at the cost of a second login to hold and refresh |
| The harness's login, swapped for `api.openai.com` (built) | No | None | |

An agent in the pylon can spend the person's ChatGPT subscription through `api.openai.com`, as it can spend any granted secret, but it cannot read the token. [`docs/verification/chatgpt-credential/`](https://github.com/ramtinJ95/nexus/tree/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/chatgpt-credential/) searched pi's environment and memory and the files under its HOME while a request ran, and found the placeholder and not the value. `api.openai.com` answers an invalid token with its first 8 and last 4 characters, never a valid one. Root on a node can read the current access token in the memory of the probe and of each pylon's controller, as it can read the node's `secrets.env`, and the token works for its remaining lifetime. The refresh token stays in the control plane's `harness-credentials.json`, as before. The Codex CLI and Claude Code in a pylon still need their own logins.

A Claude worker's shepherdr reviewer uses this login. The person's `reviewer` profile names `openai-codex/gpt-6-astra`, which is right on the Mac, where pi's `openai-codex` provider is signed in. In a pylon only the `openai` provider is, so the image's installer rewrites a captured profile's `openai-codex/` model to `openai/` and leaves the rest of the profile as captured. [`docs/verification/in-thread-review/`](https://github.com/ramtinJ95/nexus/tree/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/in-thread-review/) records what `openai-codex` itself would need in a pylon.

## Configuration

- Each project has its own files under `.nexus/`. `.nexus/setup` runs once, on a pylon's first boot, and has a 20-minute limit. `.nexus/resume` runs on every wake. `.nexus/services.yaml` declares supervised services and previews, with a schema that starts from pi-sandbox's. Services start on every spawn and wake, after setup, and after resume has finished or run for 10 seconds. A service added while the pylon runs is picked up within about 10 s of the node's next report, one with a preview once the control plane assigns its URL. Editing a running service needs `nexus service restart`. Nexus copies Amp's design, not Amp's file names.
- A template is keyed on the project, the image and a hash of the setup script, `preSetup`, the allowlist and the project's disk size, since a pylon's disk size is fixed once it exists, and is reused for at most 72 hours, as in Amp. The control plane reads the setup script at the thread's commit from the project's remote when the thread starts, with a fetch of that one commit that skips file contents, into a repository of its own that it removes after, so concurrent starts share nothing. A template boot checks out exactly the commit that was read, so a branch that moves during the start cannot pair a pylon with a template of another setup script. Dependencies that setup installed can be up to 72 hours older than the commit's lockfile, and `.nexus/resume` runs after the checkout to refresh them where that matters. A template is reused only on the node that built it. A remote that needs SSH, which the control plane has no key for, always boots fresh. Base images are built with Docker on `infra-testbench`, by the probe there, when the person runs `nexus image build`. The control plane builds the image recipe of the release it runs. `nexus image rollout` copies an image to every other online node and makes it current only once every online node holds it, because `auto` placement passes over a node that lacks the current image. The image that was current stays on the nodes, and `nexus image rollback` makes it current again. A running or paused pylon keeps the image it booted from.
- Your Claude Code and pi setup reaches every pylon in three parts. The image bakes the capabilities this Mac runs: Claude Code plugins and the mods they carry, skills, pi packages and extensions, and pi-shepherdr's agent profiles, minus those that are recursive inside a pylon or only work on the Mac. `node src/agent-setup.ts` on the Mac captures them into a pinned manifest in the image recipe, so a refresh is a capture and an image build, and the image ID changes with the setup. They are baked rather than installed at boot because a pylon reaches only its project's allowed hosts, and a boot hook has a 120-second limit. The common dotfiles layer holds rules and settings that are true anywhere, and a boot hook pulls it on every boot, before setup or resume. The pylon layer tells the agent that it is in a pylon, which hosts it can reach, where previews appear, and how to declare outputs. The image imports it into Claude Code's and pi's instructions. It also tells Claude Code to have a shepherdr reviewer check its diff before it opens or updates a pull request, and to report which findings it accepted or rejected and why, as the person's own Claude Code instructions say on the Mac. Those instructions stay on the Mac. They mix rules for any machine with rules for the Mac's two tailnets, its home SOCKS proxy and `ts-home`, sometimes in one bullet, so importing them would bring Mac-only rules into a pylon, and filtering them would depend on how the person words each bullet. The pylon layer restates the one rule a pylon needs, and Nexus writes it, so it can also say whether the project's login lets the reviewer run.

## Outputs

A thread produces a list of outputs, not one fixed kind. An output is a pushed branch, a diff, a live preview, or a file such as a screenshot. The control plane records most outputs without help from the agent, from what the probe observes: `git status`, pushed branches, and running previews. The agent declares the rest with `nexus output add`.

The probe reads Git facts through one guest exec in each running pylon's checkout, cached for one minute across snapshots and observer reconnects. A new boot or an observed non-running phase invalidates that cache. The helper reads HEAD, the current branch, tracked/staged/untracked dirt, local/remote-tracking refs and the pushes in the remote-tracking refs' reflogs; it never fetches, contacts a remote, refreshes the real index or wakes a paused pylon. Git's optional locks and filesystem monitor are disabled for the read. `GIT_NO_LAZY_FETCH=1` prevents partial clones from fetching missing objects; `GIT_ALLOW_PROTOCOL` is empty to refuse Git transports even on versions that do not support that flag. Missing objects make the facts unavailable rather than causing a fetch. Work is bounded by a 2.5-second helper deadline, a 3-second guest-exec timeout, 1000 refs, 256 KiB per Git reply and a 60 KiB observation. Each Git process runs in its own process group; cleanup kills the whole group, including clean filters and their children. Full `refs/heads/` names identify the current branch without tag-name ambiguity, and NUL-delimited ref fields preserve Unicode line separators. Dirty detection stops at the first status byte. An unavailable checkout, timeout, oversized or malformed reply reports `git: null`, not a partial or clean tree; failures are cached too and logged once, until a read succeeds or the probe sees the pylon not running. Sessions reads and counts of attached terminals log their failures the same way. Other pylon facts remain observable. The probe bounds controller waits too: all fact readers for a pylon start in parallel, with three-second wall deadlines (five seconds for services), so a stalled controller cannot block the node's snapshots for its 180-second RPC timeout. A timed-out read stays registered until its underlying call settles; later snapshots return unavailable facts instead of piling up duplicate RPCs, and late replies cannot overwrite published facts or caches. Healthy pylons still publish their facts within the same bounded snapshot.

Only a remote-tracking ref this checkout has pushed counts, which its reflog records as `update by push`. A clone, fetch or checkout of a branch someone else pushed writes that ref too, so without this rule a thread that only reads another branch would own it, and the PR watch would link that branch's pull request to it. A local branch's `pushedAs` is its pushed non-symbolic remote-tracking upstream if it has one. Otherwise a same-named pushed remote-tracking ref counts: prefer `origin/<branch>`, then a unique match on another configured remote. Ambiguous non-origin matches and symbolic remote aliases do not count. Thus a `push.default=current` push or a push made around `gh pr create` needs no configured upstream, and a force-push after a rebase is a push like any other. Commit equality alone never links differently named branches. The remote-tracking ref can lag local commits: this records a branch name the checkout pushed, not that the current local tip is pushed. A thread that pushes to a branch someone else made, such as one whose pull request already merged, owns that branch from its push on. A ref can be stale after remote deletion. Reconcile accumulates branch outputs from these names and diff outputs from dirty HEADs without retracting earlier outputs.

## Files and changes

A client sees what a thread did through two views, as in Amp: Files browses the pylon's checkout and opens any file in it, and Changes lists the files that differ and their diff. The control plane reads both from the running pylon on demand, through a raw pipe its probe carries, with one small Python helper (`src/checkout-files.py`) per read. Nothing is copied off the pylon in advance, so reading a paused pylon wakes it, as any other request a human makes does.

- Changes compare the working tree, untracked files included, with the commit the pylon booted at, so the agent's commits count too. Each pylon records that commit as `refs/nexus/base` in its checkout on its first boot. A scratch pylon boots an empty repository, which has no commit, so it records the empty tree, and every file the agent makes shows as added, committed or not. HEAD before the first commit is the empty tree too. Changes since HEAD show the uncommitted work alone. Latest turn compares with a snapshot before the autonomous reply starts, so pre-existing uncommitted work does not count.
- Before the first model request of each durable run, the harness snapshots through the checkout helper into `refs/nexus/turn`, a parentless commit built with a temporary index. Start rather than end snapshots isolate the reply from work between replies, and cover the first turn of an empty scratch repository. A turn is the whole reply, including tool rounds and steering; queued follow-ups start new ones. No snapshot asks for a wake. The first input submission identifies the whole reply; generation task IDs change after tool rounds and cannot identify it. The durable `nexus.turn-snapshot` conversation document records the attempted reply before capture, and an on-disk marker makes capture idempotent. Later tool rounds and recovery cannot replace the base after tools ran. Failure is logged and the reply continues; reads verify the snapshot's first input ID against the active reply or the last attempted reply in that document, refusing an old snapshot even after a transport failure. Interactive pi sessions do not capture turns.
- A Claude Code turn is each prompt Claude receives. Its `UserPromptSubmit` hook in the pylon snapshots the same way, through the image's copy of the checkout helper, and names the snapshot `claude:<session>:<at>`, with the session ID and the millisecond stamp it also sends as `session.turn-started`'s `at`. The hook rather than the control plane takes it because Claude does nothing until its hooks return, while the event reaches the control plane after Claude may have started editing. The hook waits for the snapshot but kills its whole process group if it has not captured its commit within 1.5 seconds, below Claude's 2-second hook limit, so a slow snapshot neither holds the prompt nor captures Claude's first edits, and removes its temporary index either way. Once captured, the short ref update is let finish, because one killed midway leaves a ref lock that fails every later snapshot; claiming a turn writes only `.git/nexus-turn`, which reads also check, so it needs no ref update. Sessions can snapshot at once: under a lock, an attempt claims the marker only if the marker names no later Claude turn by start stamp, and publishes only if it still holds the marker, so an older turn never replaces a newer one's snapshot. A Claude worker thread's reads expect the ID of the newest turn start the registry recorded for the thread, from any session, so a failed snapshot, a lost or rejected event, or an image that predates the hook's snapshot refuses rather than showing an older turn. Every Claude Code session in the pylon snapshots, an interactive one included, and the checkout holds one snapshot, so an interactive Claude Code turn in a harness thread's pylon leaves that thread's latest turn unavailable until its next reply.
- The dashboard shows a file's diff highlighted for its language by `@pierre/diffs`, unified or split as the reader picks. A window 760 px wide or less, such as a phone's, always draws unified, since split leaves each side too few characters. Long lines wrap, and the file's header, the review's bar and a note's kinds wrap their controls onto more rows, so even a panel narrower than those controls never scrolls sideways. A diff longer than 2,000 rows shows its first 2,000 and says so above them, because drawing many more freezes the page for seconds. A change of a file's line endings from LF to CRLF or back, which draws as every line removed and added again, is named above the lines. The library's own component writes markup with inline styles, which the dashboard's content security policy blocks, so the dashboard draws the library's render as DOM in a shadow root and leaves the policy as it was. The library and each language's grammar are chunks of the bundled client, fetched when a diff, and then a file of that language, first opens.
- The reader can write review notes on a diff: a comment, a question, a suggestion or a requested change, on rows selected by their line numbers or with the keyboard. A note keeps the line numbers of its first and last rows and a quote of its rows. The new side's numbers are the working tree's on every base, so a note shows again under its last row on any base while its rows still read as quoted. A note whose rows changed is listed above that file's diff with its quote. The library's annotation rows hold the notes, and the page fills them through slots of the shadow root, so notes keep the dashboard's styles and the content security policy stays as it was. Notes stay in the browser's local storage, per thread, until they are sent or discarded. **Add to message** puts the review in the composer as one message, with each note's file, lines and quote, for the reader to edit. Sending it is an ordinary message, so it reaches a Claude worker or the Nexus agent as the composer's other messages do, and it clears each note whose entry it still holds. A note edited after the send began stays, and so do notes that share an entry's header line when the message holds fewer of those entries than there are notes, since the page cannot tell which one was cut. Tabs in the review become spaces, because a Claude worker refuses a message with a tab.
- The dashboard offers Latest turn beside Only uncommitted. Scope changes use the same read gate as the existing controls: no timer reads, and a paused pylon needs the person's wake confirmation.
- Only paths in the checkout are read, so a client never shows the pylon's Claude Code and pi logins, which live in its home directory. The reads run in the pylon, so this guards against mistakes, not against the pylon, whose agent can read those files anyway.
- A file is served under a content type that cannot run as a page of the API's origin, because the dashboard shares that origin.

## Release reconciliation and caller checks

The release planner in `src/deploy/plan.ts` has the same boundary as pylon reconciliation: desired and observed state in, a decision out. Root workers poll control directly, validate main ancestry in their own clone, and reconcile each installed role. The control plane goes first; probes require its fresh healthy desired-release report. Link and unit rollback is journaled locally so recovery does not depend on the API that may have failed.

Release setting is separate from ordinary caller admission: callers must also be in `deployers`, which defaults off. Every infrastructure node, including self, is excluded even if listed. Thus guest egress carrying a host's tailnet identity cannot deploy. The same exclusion, without the `deployers` list, decides who is a person: an allowed caller that is neither the control node nor any node. Answering a question takes a person, and a question whose answer may deploy also takes a deployer. The pylon bridge has no deploy operation and no general-purpose API forwarding. Root node polling additionally requires a per-node token whose digest is in control.json, or in the registry for a node that joined, and verifies control's tailnet identity before sending the token. A node joins with a one-time token that only root on the control plane's machine mints, through `POST /v1/join`, the one route besides `/v1/whoami` that a machine the control plane does not know may call. The control plane records the node as whois names the caller, never as the request says, and refuses the control node and every caller, so a join never turns a person into a node. See [deployment](../deploy/README.md) for provisioning and the trust limits of machine identity.

A persistent drain lease blocks API and background PR-watch turn entry, and counts in-flight admission before examining committed harness runs and queues. It refuses at timeout rather than interrupting an in-flight tool. The final idle fence seals the lease before the link switch so it cannot expire underneath interrupted-install recovery. A fixed root supervisor and bootstrap worker remain outside automatic link updates, so a bad candidate worker cannot stop a later release fixing it.

## Backups of the control plane

The control plane's machine backs up its own state once a day, to `/var/backups/nexus` on that machine only, as the person decided on 2026-10-28. `src/control/backup.ts` derives what to copy from `control.json`: the registry, the harness's storage, the harness's credentials, and every file under `/etc/nexus`. Each database is copied with `VACUUM INTO` from a read-only connection, which reads one snapshot through the live WAL, and never as a file. A backup is complete only once its manifest exists, which is written last, after every copied database passed `PRAGMA integrity_check`, with each file's size and SHA-256. Older backups are deleted only after a new one verified, and the newest 7 stay. A restore replaces each file whole, and only on a stopped control plane with the deployer stopped. The check that `nexus doctor` is to call reports the newest complete backup's age and whether it still verifies. [Daily backup](../deploy/README.md#daily-backup) has what each backup holds and the commands.

## Open questions

- Spikes S1 to S7 test the riskiest assumptions on the nodes. Details are in `spikes/RESULTS.md`:
	1. S1 checks whether a Debian image boots in Gondolin with Herdr and Claude Code running as `user`. Passed with a workaround: the build took 35 s and a cold boot took 3.9 s. As `user`, the image ran Python, Bash, Node 24.22.1, Claude Code 2.1.308, and a headless Herdr 0.9.5. Gondolin 0.13.0's OCI build aborts when it copies Alpine kernel modules, because `fs.cpSync` follows the absolute link `vmlinuz -> /boot/vmlinuz-virt` to the host's unreadable `/boot`. A `postBuild.copy` of the unchanged module tree avoids the crash. The fix is tied to the kernel version. `spikes/UPSTREAM-ISSUE-DRAFT.md` holds an unfiled upstream issue. Image builds need Docker access for the build user.
	2. S2 checks whether Claude Code reaches Anthropic through Gondolin's TLS interception. Passed for requests without a login: `curl` received HTTP 401 from Anthropic, and `claude -p` stopped at "Not logged in". A non-root user cannot read `/etc/gondolin/mitm/ca.crt` through its FUSE mount. The pylon image therefore sets `NODE_EXTRA_CA_CERTS=/run/gondolin/ca-certificates.crt`. `vm.enableSsh()` needs `openssh-server` in the image. Resume from the checkpoint took 5.4 s. A logged-in Claude Code was later proven in a pylon on `rj-firebat`: after a `/login` in a session that `nexus session open` opened, the session recalled its conversation after an archive and a wake. Remote Control is not tested.
	3. S5 checks whether interactive pi logged in with ChatGPT works inside a pylon. Passed: a model request succeeded through Gondolin. The login needs the device-code method or a pasted redirect URL, because the browser callback on port `1455` listens inside the guest. pi 1.4.0 needs `auth.openai.com`, `chatgpt.com`, and `api.openai.com` on the allowlist.
	4. S3 checks whether pi-durable can run a tool inside a Gondolin VM. Passed with a scripted model: cold boot took 3.9 s and the tool round trip took 63 ms. pi-durable's `ExecutionEnv` interface covers far more than `exec` plus file reads and writes, so the harness uses pi-env's Rust daemon inside the pylon rather than a new adapter. The daemon's frames reach the harness over a raw pipe that the probe carries (`src/harness/pylon-env.ts`).
	5. S4 checks whether `tailscale serve` publishes a preview from a node. Passed: HTTP/2 200 from the Mac in 0.4 s, and the guest received the `Tailscale-User-Login` and `Tailscale-User-Name` headers. The guest sees `x-forwarded-proto: http`, so the pylon sets `PUBLIC_URL` to the `https://` address. The first HTTPS request timed out after 15 s and the retry passed, so the probe must warm up a new preview before it reports the preview as ready.
	6. S6 checks whether one node serves many preview ports through one gateway. Passed: six ports worked at once, the gateway saw each port in `Host`, and 72 requests from the Mac had no timeouts. Details are in `spikes/S6.md`.
	7. S7 checks whether a checkpoint written on `infra-testbench` boots on `rj-firebat`. Passed: a fresh checkpoint went from Intel to AMD and back, and its files survived. Resume took 2.4 s on AMD and 3.9 s on Intel. A checkpoint also booted from a different path after `qemu-img rebase -u`, so the same path on every node is a convenience, not a requirement. Streaming the copy through the Mac broke twice, so copies must be verified before a boot. Details are in `spikes/S7.md`.
- A Gondolin 0.13.0 guest with 2 GiB of memory hangs at boot on `infra-testbench`, while 3 and 4 GiB boot in 4 to 7 s. The console suggests the initramfs is loaded over the ACPI tables, but that is not proven. The pylon-vm backend refuses pylons under 3 GiB until this is understood. Pylons are planned at 4 to 16 GiB, and the whole slice passes at 4, 8, 12 and 16 GiB, with the guest seeing at least 90% of its size. Under load, a 16 GiB pylon held 14 GiB of touched memory on `infra-testbench` without an out-of-memory kill, and host swap use grew from 209 to 378 MiB, so that node has room for one such pylon under full load. `src/pylon-vm-memory.check.ts` runs that check. Gondolin keeps a running pylon's disk writes in an overlay in the temporary directory, and on a tmpfs those writes cost host memory, so each controller gets a scratch directory under the state root.
- The contracts leave spikes and source checks open, listed in [the contracts rationale](contracts/rationale.md#open-questions-and-risks). Copying checkpoints reliably between nodes is the riskiest, because streamed copies broke in S7.

## Pull request watch

The control plane discovers open GitHub PRs for recorded `origin/` branch outputs on the project's repository (derived from the probe's checkout Git facts: the remote-tracking refs the checkout pushed, including same-named ones when no upstream is set), and polls linked open PRs roughly every two minutes. Scratch projects and other remotes are not inferred from the checkout. Reads use the control plane's optional `github.tokenFile`, never a pylon, and therefore never wake one. Each GitHub resource has its own conditional request cache, which keeps the 4096 resources read most recently and drops a PR's check runs and statuses at a head once the PR's head moves or it closes or merges; threads share discovery and PR reads in each pass, and each thread's branch searches, then its linked PRs' reads, run together, while its news keeps the order of its links. Checks include check runs and legacy commit statuses; passing means all reported checks are complete and successful (neutral/skipped check runs are accepted), not just branch-protection-required checks. A failed read of a head's check runs or statuses leaves its checks unknown for that pass. The watch keeps the checks it last read, and a landing waits for a complete read rather than passing or holding on it.

A failed check, recovery after a reported failure, new submitted review or comment, or a conflict batches into one follow-up message per thread per pass. The first link baselines existing comments, but reports current failures and conflicts. pi-durable 1.4.0 supports application input entries: messages use `nexus.pr-watch`, sender metadata, and an explicit automated text prefix. They count only as agent activity, so the usual five-minute agent grace and twenty-minute human idle rule still apply. A Claude worker thread has no harness conversation, so the same message is typed into its Claude session through the steering path (`src/control/inbox.ts`), with CRLF line ends made newlines and tabs made spaces, as Claude's prompt needs. It too counts only as agent activity: it wakes a paused pylon and waits, kept pending, until the pylon runs and Claude is not at a dialog. Its request ID is fenced like a person's message, so a send that failed partway is never typed twice.

Only reviews, review comments and issue comments whose GitHub `author_association` is `OWNER`, `MEMBER` or `COLLABORATOR` are forwarded to the agent. The same rule applies to the PR author: being the author alone grants no trust. Missing or other associations are skipped before event tracking and never count toward the wake cap.

GitHub gives no reliable provenance distinguishing a person's comment from an agent's arbitrary `gh` or HTTP call with the same token. The watcher therefore does not filter by login, bot status, or activity timing. Such guesses would lose the person's reviews. Ten consecutive comment-only wake messages stop the thread's watch durably; any check or conflict wake resets that counter. An unarchive does not clear the cap. Existing comments are identified by their resource kind and ID; edits alone do not wake.

Merged and closed PRs retain their final state and last known check/review summary but are no longer polled. Rediscovering a closed PR as open reactivates its link without clearing consumed event IDs, reported failures or the comment-wake count; reopening does not bypass a reached cap. Archived and deleted threads do no discovery, polling or delivery, except that for a thread a queued thread waits for, each pass first reads its unmerged linked pull requests and searches its branches for pull requests in any state, and saves every one's current state in one write once all are read, whatever its status, cap or undelivered message, so the queued thread sees the merge. Unarchive resumes an uncapped watch with its old cursor, including feedback received while archived. A durable pending message and a stable harness request ID bridge the registry and harness databases: retry after a crash does not send the same news twice. Read or delivery errors appear on the detail and are retried, without exposing credentials or raw transport errors.

A GitHub 403 or 429 sets a shared rate-limit cooldown only when `x-ratelimit-remaining` is zero or `Retry-After` is present. The watcher honours `Retry-After` (seconds or an HTTP date) and an exhausted primary limit's reset time, waiting for both if supplied. Ordinary access denials, including repository-specific SAML restrictions, fail that watch without putting other repositories into cooldown.

## The review loop and landing

A task's review used to run on the person's Mac, through a Claude Code coordinator and its workers, so it stopped whenever that session did. The control plane runs it now, from the moment a builder thread's pull request is open until it lands or needs the person, under [the merge policy](merge-policy.md). `src/control/review.ts` holds the loop, `src/control/review-model.ts` the review's record and the pure rules over it, `src/control/policy.ts` the policy's checks, and `src/control/holds.ts` its hold rules.

`nexus review <thread>` starts a review of the thread's open PR, the one the PR watch linked. A project can ask for it to start on its own, with `nexus project edit <id> --auto-review review`, or `land` to land each approved PR too, as `nexus review --land` would. Only a person sets it, through the human-only project edit, and the project records the caller who did. Landing deploys, so `land` needs that caller among the control plane's `deployers`, and each landing checks again before every merge that the project still asks for it and that its caller still is one. When the PR watch first links an open PR to a thread of such a project, it tells the loop before it saves the link, so a call that failed is made again on the next pass, and the loop starts the review. It never starts one for a reviewer thread or a check thread, nor a second one for the same PR: a review that ended stays ended until the person runs `nexus review`. A PR the watch linked before the project opted in is not reviewed on its own. A review that cannot start, such as for a harness builder whose project grants no Claude token, or while the builder's review of another PR runs, is logged and not tried again. A builder still in its turn gets the findings once the turn ends, as for any review. The control plane starts a reviewer thread in the same project and node, on the PR's branch. Its model is another family than the builder's where one can run. A Claude worker builder gets a harness thread, which runs the harness's OpenAI model. A harness builder gets a Claude worker on Claude Opus 5.5, with no `/poteto-mode`, when the project grants a Claude token (`CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY` for `api.anthropic.com`). Without one the review is refused, saying so, because a `/login` needs the person. The PR watch skips reviewer threads, because a reviewer's checkout of the branch would link it to the PR it reviews.

Each round goes through the inbox that the PR watch also uses (`src/control/inbox.ts`), so a harness thread gets attributed `nexus.review` input entries and a Claude worker gets the text typed into its session through the steering path. Each request carries a fresh random token that only its recipient is told, which the answer must echo, so neither an earlier answer nor the other agent can answer it. The reviewer reviews the head against the base and ends its reply with a fenced `nexus-review` JSON block: approve or request changes, its findings, each with a priority from P0 to P3 as [the merge policy](merge-policy.md) defines them, the reserved cases the change touches in code or config that ships, and its quote of what the PR says could not be checked live. The reviewer approves when no P0 to P2 finding is open, and the loop reads every verdict that way, whatever word the reviewer chose. The builder gets the findings and ends its reply with a `nexus-review-answers` block that fixes or rejects each P0 to P2 finding with a reason. P3 findings come as notes that need no answer: an approval with only P3 findings goes straight to the check, and the builder gets the notes to take up in a later pull request, told not to push to the approved branch. A stored review or an answer whose findings use the earlier `serious` and `minor` reads them as P1 and P3. When it says it fixed something, the loop waits for the PR's head to move, then sends the reviewer the new commits and the answers for the next round. Commits pushed with answers that fixed nothing get a round too, since they are unreviewed. A clean approval runs `.nexus/check` at the approved head, and a failure goes back to the builder as a P0 finding. A builder that answers it without pushing a new head ends the review for the person with the check's output, since the reviewer cannot change the check's result: at once when it rejects the finding, and after the 10 minutes a push may take to show when it says it fixed it. A check that fails again at a head where it failed before goes to the person too. A round is one review, and a round in which the reviewer approves again the head the round before it approved reviewed nothing new, so it does not count against the limit. The loop ends approved, after the rounds a review allows (five unless `--rounds` asks for fewer, and never more than five, even for a review stored with a higher cap), or when an agent stays silent: a turn that ends without a readable block gets a reminder, at most two in a row, and three hours without an answer Nexus could read ends the review. A turn that ended because the agent's model failed is not silence, and costs no reminder: a harness thread's last assistant message stopped with `stopReason: "error"`, or a Claude worker's transcript ends on the error notice Claude Code writes when an API call fails for good. The loop sends the same message again under the same token, after 2, 5, 10 and 20 minutes for the first to fourth failures in a row, and the review keeps its round. A fifth failure in a row ends the review for the person with the model's last error and a reason that says to run `nexus review` again once the provider recovers. The phase records the failures and the next retry, so `nexus show` and the dashboard say the model is failing and when the loop tries again. The builder and the reviewer wait the same way. A check or verify thread runs no model, so nothing of this applies to them. A Claude worker's turn that ends with a background shell or subagent running reports heartbeats rather than its end, and the thread stays working, so for a Claude worker the loop also takes the turn's end from its transcript, where Claude writes each main turn's duration as it finishes: a reply or a turn there after the loop's message is read, and a turn there without the answer gets its reminder a minute later though heartbeats keep the thread working, unless a prompt or a finished task after it there started a newer turn that still runs. An answer that says it fixed something waits for its turn to end there before the 10 minutes a push may take start. A harness thread's turn end is reported reliably, so only that counts for it. Every message is saved in the review's record before it is sent, under a request ID made from the review and a count of its messages, so a pass after a crash sends it again under the same ID, which the harness and the Claude send both deduplicate. The time the first send began is saved before it too, and the wait for an answer counts from then, so an answer that came before a crash cleared the sent message is still read.

The check runs the pull request's own code, so no pylon whose contents decide a verdict ever runs it, and nothing it writes decides its own result (`src/control/gate.ts`). Each run starts a bare check thread, with no harness conversation and no Claude worker, whose pylon clones the repository at the approved commit. Once that pylon runs, the control plane opens one raw pipe into it, the probe's stream, whose process verifies the checkout's commit and then becomes `.nexus/check` with `exec`. The stream reaches the guest over ssh, whose non-login shell reads no `/etc/profile.d`, so the script first takes the image's environment, its PATH and the egress proxy's CA in `NODE_EXTRA_CA_CERTS` among it, from the guest's PID 1, where Gondolin put it at boot. Unlike the profile files, which `.nexus/setup` runs before the check and could rewrite, that environment is fixed before any of the pull request's code runs. The verdict is that process's exit status as the probe reports the stream's end, and the output's tail goes to the builder when it fails. A check the pylon cannot run goes to the person with its output and costs no round: a check pylon whose boot or `.nexus/setup` failed, a repository with no `.nexus/check`, an image environment the script cannot read, or a command the check needs that the pylon lacks, which the shell reports with exit status 126 or 127. A script that exits 75, EX_TEMPFAIL, says its failure was transient and says nothing of the change, as Nexus's own `.nexus/check` does when `npm ci` fails on a registry timeout: the run is void, so its thread is deleted and the check starts again in a fresh one. Three such runs in a row at one head go to the person with the last run's output, as a check that cannot run does, and cost no round. A repository whose install can also fail for a reason the builder must fix, such as a lockfile out of step with its manifest, sends that to the person too after three runs, so a script exits 75 only where it cannot tell the two apart. The check thread is deleted after its verdict, so no process the check left behind reaches a later round. Only this control-plane process knows that it opened a run's pipe, so a check thread it holds no run for, as after a restart, or one whose pipe was lost, may have run something already: it is deleted, and the check starts again in a fresh one. A check thread no review holds, such as one started just before a crash, is deleted on the next pass. A Claude reviewer's verdict is still read from its transcript in its own pylon, where the reviewer itself may run the pull request's tests, so code from the change could forge one there. A Claude reviewer's findings still go round, and a review without a landing still ends approved, but its approval never lands: the policy holds a landing it approved for the person. A harness reviewer's verdict is the control plane's own agent loop's answer, out of the pylon's reach.

Once `.nexus/check` passes, a head with a `.nexus/verify`, as GitHub's contents read at that commit says, gets the merge policy's live check (`verifying`). The loop starts a fresh verify pylon: a bare thread started by `nexus-verify`, at the approved commit, whose boot asks for nested virtualization and 8 GiB, placed with `auto` on a node whose probe reports that its KVM nests. A pylon-vm probe reports it when its host's `kvm_amd` or `kvm_intel` module has `nested` set, and the image's `nexus-kvm` loads the modules in the guest, failing the boot when no `/dev/kvm` results. The script runs as `.nexus/check` does, through one raw pipe in the image's environment, and its exit status is the verdict. Nexus's own `.nexus/verify` starts the image's Docker and drives the verify-nexus skill's stack through the real CLI: a thread started, its agent messaged and its answer read, its changes read, archived, woken with its disk, and deleted ([decisions](#decisions), 2026-10-31). The round records it as `live`, pass or fail with the output's tail and the verify pylon's thread, or that the head has no `.nexus/verify`, and the verify pylon is archived rather than deleted, so the person can unarchive it within 24 hours to see what the stack left. A round with no `live` holds the landing, so a landing saved by an older control plane runs its live check before it merges. A live check that passed stands in for the pull request's statement of what it could not check live. One that failed goes back to the builder as a `LIVE` finding (P0), as a failed check does, and holds the landing until a new head passes: a builder that answers it without pushing ends the review for the person with the output, and one that fails again at a head where it failed before goes to the person too. A live check that cannot run, such as a verify pylon whose boot found no `/dev/kvm`, goes to the person with its output. `.nexus/verify` may exit 75 for a transient failure as `.nexus/check` does, with the same three runs at a head. A start no node can take, because none nests KVM or has the room, is tried again on each pass, and after an hour without a verdict the review goes to the person with the last refusal. A head with no `.nexus/verify` goes from the check to approval as before and lands on the statement, and a landing tried again keeps the round's live check, which ran at the same head. A verify pylon no review holds is archived on the next pass, unless the person has been to it since it started, so one they unarchive to look at stays open.

When the rounds run out, the review ends for the person and the loop adds the label `needs human review` to the pull request, creating the label in the repository if it is missing. The rounds run out in five ways: the reviewer still requests changes after the last round, the builder pushed fixes after the last round so they are unreviewed, `.nexus/check` failed after the last round, the head moved after the last round's approval, during a landing or while the review waited at approval or for the person, or the branch conflicts with its base after the last round, so a rebase could not be reviewed. No other reason a review goes to the person adds the label. The review ends for the person first, with `label.state` `adding`, and a later step of the same pass adds the label, so the person never waits on GitHub. Adding a label GitHub already has changes nothing, so a pass after a crash adds it again safely, and an error GitHub may recover from is retried on the next pass. Labelling needs a token that may write issues or pull requests. When GitHub refuses the control plane's token, the label's state becomes `failed`, and the review gets one more reason that says the label could not be added and GitHub's answer. The loop does not try again, and changing the token stays the person's decision.

A review ends without the person when nothing is left to review. A pull request closed without a merge ends it `closed`. One merged outside a review that does not land ends it `merged`, while a review that lands still decides whether that merge deploys. Before each step the loop reads the PR watch's state, and before it sends a message, starts a check or ends the review it reads the pull request from GitHub, since the watch reads it only every two minutes. A builder or reviewer thread the person archives or deletes while the review runs ends the review `cancelled`. Neither ending runs a check, sends a message, adds the label or sets the `decision` attention, and a check thread the review held is deleted. A review already held for the person ends the same way, `closed` or `cancelled`, which clears the `decision` attention, unless it merged: a held deploy or rollback stays with the person whatever happens to the threads.

The person cancels a running review, or one that ended for them, with `nexus review --cancel <thread>` or the Cancel review button on the builder's page, which ends it `cancelled` by them, without archiving the builder, so a builder the person still wants keeps its pull request and can get a new review at once. A landing that has authorized its merge, or is deploying or rolling back, is refused, because a merge or deploy that has begun is seen through: it ends landed or with the person.

A review that stopped at approval, and one held for the person that has not merged, follow the pull request's head too. The PR watch records the head at each read. When it differs from the head of the review's last round, the loop reads the pull request from GitHub and acts on what GitHub says. A review that would land as it is, approved with its check passed and held only for the person's decision, gets a new round on the new head, as a landing does, so the reviewer, `.nexus/check`, the live check, the policy and any hold for the person run again there. A waiver stays with the head it named. A review that stopped at approval does the same, and stops at approval again. With no round left, it goes to the person with the label and a reason that names the new head. A review held after an approval only for the loop's own findings, a failed check, a failed live check or a conflict, such as one whose builder did not rebase a conflicting branch, pushed nothing for a failed check, or ran out of reminders answering one, gets a new round on the new head too, while it has rounds left and no label, since the push may answer what the loop asked for. Any other review the loop gave up on, such as one held with changes the reviewer requested or one whose rounds ran out, starts no round. Its reasons gain one that names the new head, and the person can start a new review with `nexus review`. A merged review held over its deploy or rollback ignores the head. `nexus show` and the dashboard say when a round started because the head moved after an approval. The watch's read may be older than the review's latest round, so the loop acts only on a head GitHub confirms, and a force-push back to a head an earlier round reviewed gets a new round too. The card offers no Land while the watch's head differs from the latest round's, since it cannot tell an old read from a reset. A watch stopped by its comment cap reads nothing new, so neither the loop nor the card uses its head. A held review under a stopped watch reads the head from GitHub itself, as it reads whether the pull request closed, at most once per PR watch interval of two minutes, as the watch would, and again right after a restart. One that stopped at approval leaves it to its landing, which reads GitHub before it merges.

The record lives in the registry's `reviews` table, keyed by the builder. `reviewed_prs` remembers every pull request a review started for, after a later review of the same builder replaced its record, so a review that starts on its own starts once per pull request. A pass runs every 15 seconds, and each phase reads the world again before it moves: the agents' replies, the PR, the release. A pass reads each PR from GitHub once and its steps share that read, so the step that sends a message the step before it queued reads nothing new. A landing's step reads its PR afresh, since the policy is checked again with what GitHub says before every attempt, and a merge drops its PR's read, so the read after GitHub refused a merge, which asks whether the PR now conflicts, is GitHub's answer then. Each reviewing or fixing step reads its agent once (`src/control/agent-conversation.ts`). A pass leaves out a review that ended landed, merged, closed or cancelled with no message left to send, and its sweep of check threads and verify pylons reads only those threads. A pass saves a step only over the record it read, as `saveJudgment` does, so a land or cancel the person saved while the step awaited GitHub or the inbox is kept, and the next pass steps from it. A turn's replies are read only after a turn of that agent ended since its last message from the loop. A Claude worker's are its stored transcript, and a harness thread's come from one read of its conversation. A review that ends for the person makes the builder's attention `decision`, whose reasons `nexus show` and the dashboard list.

The builder's page on the dashboard shows a review the person can land above the composer, so the decision needs no terminal and works from a phone: why it waits for them, the reviewer's findings, the check's result, the approved head and the PR. Its Land button asks for a confirmation that names the PR and the commit, then calls the land route with that commit, which lands nothing if the review has moved on, and the page shows the landing's steps, check, merge, deploy and landed, from the review's phases, until it lands or ends for the person again with the reasons, a rollback's among them. The page asks the land route's own questions, whether the browser's device is a deployer and whether the control plane has a review loop, and a device the route would refuse gets a disabled button that says why, while the route still refuses it. Each reason is marked as one the person may waive or not, with why. A reason that holds every landing of the same commit and that the person cannot waive, a Claude reviewer's approval, offers no button, and neither does a review whose pull request closed, nor one whose pull request the PR watch read at a head other than the approved one. The card says the new head gets a new round instead. Between a push and the watch's next read, up to two minutes, the card still offers the old head, and a Land pressed then merges nothing: the landing reads the moved head from GitHub and starts the new round.

When every reason that would hold the landing again is one [the merge policy](merge-policy.md#what-the-person-may-waive) lets the person waive, the Land button sends those holds with the commit, and its confirmation says it waives them. The review loop checks that the review is landable at that commit and that each hold is one it has now and one the person may waive, then lands as `nexus land` does, and the merge step checks the whole policy again with the named holds met at that commit only. The review records the waiver and the event stream gets `review.waived`. `nexus land` sends no holds, so from the CLI a reserved hold holds the landing again.

With `--land`, or `nexus land <thread>` after an approval, or a project that lands on its own, the loop lands the PR once its check passes. Landing deploys, so it needs the same right as `nexus deploy`, whatever the repository. Right before every merge attempt, including one retried after a restart, it runs all of the policy's checks again with what GitHub says then, and holds for the person with every condition that fails. A head that moved after the approval, such as a builder's rebase on the PR watch's news of a conflict, is not merged: it gets a new round, as a push after findings does, and the reviewer is told to read it against the base, since a rebase rewrites the commits it reviewed. A landing held for nothing but a branch that conflicts with its base, or a merge GitHub refuses while it then reports the conflict, goes back to the builder as a P0 finding, `CONFLICT`: rebase onto the current base, resolve the conflicts keeping both sides' intent, run the checks again and push. The rebased head gets a new round under the same cap, then a check, then the landing. A builder that rejects `CONFLICT`, or pushes nothing for it, ends the review for the person with its reason, and a conflict found after the last round ends it for the person with the label, since no round is left to review a rebase. Then it squash-merges with GitHub's head check, so only the approved commit can merge. A PR of Nexus's own repository, the one releases come from, then deploys: the loop records the release it replaces, sets the merge commit as the desired release, and waits up to 30 minutes for every component to report healthy, as `nexus deploy --wait` does. Landings that deploy go one at a time: before it merges, a landing waits while another landing deploys, rolls back or has saved the head it is about to merge, while a deploy drains the control plane, and while not every component reports the desired release healthy, as after a deploy that failed with nothing to roll back to, and `nexus show`, the pipeline and the dashboard say what it waits for. So main gains one undeployed commit at a time, no landing's release replaces another's before it is healthy, and the release a landing records to roll back to is one every component reported healthy. A failed, rolled-back or late deploy moves to rolling back: the previous release becomes desired again, and the loop waits up to 30 minutes more for every component to report it healthy before it tells the person it rolled back, and that the merge commit is still on the default branch. A rollback that fails too is reported as failed, with the components that failed. The control plane redeploying itself restarts the loop mid-landing, so the merge step saves the head it is about to merge before calling GitHub, and on a restart checks whether the PR merged already, and at the approved head. A merge at a head the review saved is its own. Any other merge, such as the person merging while the check ran, deploys only if every condition of the policy holds, the reserved paths and the reviewer's kind included, and otherwise ends in `decision`, and the deploy and rollback steps check whether their release is already desired, before acting. Once merging, a landing sees its deploy and any rollback through even if its threads are archived. A merged review never lands again.

A review that ends `landed` leaves its builder and its reviewer nothing to do, so the pass archives both, as `nexus archive` would, in the transaction that saves the landing, then tells the planner, which pauses their pylons. A landing that fails to save archives nothing, and the next pass decides it again from what the release says then. A thread in a turn at that moment, such as a builder the person is talking to, stays open for the person to archive, and the loop never archives a thread later, so a builder the person unarchives after its landing stays theirs. A review the person cancels archives its reviewer the same way, and never its builder. A review held for the person, rolled back, stopped at approval, or ended `merged` or `closed`, or `cancelled` because the person archived or deleted one of its threads, archives nothing. Only the review's own reviewer is archived: a reviewer of an earlier review of the same builder is not linked to it, and stays as it was.

Merging needs the control plane's GitHub token (`github.tokenFile`) to have write access to the repository's contents and pull requests. A read-only token, enough for the PR watch, makes a landing hold with GitHub's answer, and granting the wider token is the person's decision, as [deployment](../deploy/README.md) says.

## Nudging a builder that stopped short

A review starts only once a builder's pull request is open, so a builder that ends its turn before it pushes, or before it opens the pull request, stops the work until someone reads it. On 2026-10-25 one stopped at a draft and no one noticed. In a project with `--auto-review`, the control plane now nudges such a builder through the inbox, and after two nudges hands it to the person (`src/control/nudge.ts`).

A pass runs every 15 seconds. It reads only active and idle threads, and the threads whose nudge record it clears once they are archived or deleted, so an unarchived thread's count starts over. It judges each turn of a thread once, while no other turn runs. The thread is a builder unless it is a reviewer or a check thread, or its project has no repository or no auto-review. A Claude worker stopped on its usage limit did not stall, so the pass skips it until its next turn. A turn stalled when the thread has no pull request: the PR watch has linked none, it has no review, and GitHub finds none on any branch the thread pushed. The pass judges a turn only once the registry knows every branch the thread pushed before the turn ended, and a PR watch pass that started after that has finished. The thread's branches reach the registry only through the probe's snapshots, once a minute, and the probe reuses a git read for a minute (`gitPollMs` in `src/git-facts.ts`), so a branch pushed just before the turn ended can be missing for two minutes. So the pass waits for a snapshot of the thread's running pylon, with its git read, taken at least `gitPollMs` after the turn ended. A paused pylon's snapshot says nothing of git, so a turn the pass had not seen such a snapshot for before the pause waits until the pylon wakes. The PR watch links only pull requests it finds open, so the pass then searches GitHub for the thread's branches in every state, and a pull request that merged or closed before the watch saw it gets no nudge either. The pass reads GitHub only for a turn it would otherwise nudge, and at most once per turn. A turn is judged one to five minutes after it ended.

A stalled turn gets one fixed message, prefixed `[Nexus nudge — automated, not a message from the person]`, under the request ID `nudge:<thread>:<turn end>`. It is saved with its count before it is sent, so a pass after a crash sends it again under the same ID, which the inbox never delivers twice, before it judges any later turn. Like every inbox message it never interrupts a turn: it goes only to a thread whose turn ended, as a harness follow-up or typed into the Claude session, and counts as agent activity. When the turn after the second nudge stalls too, the thread's attention becomes `decision`, and no third message goes out. A pull request linked, a review started, an archive or the person's message clears it.

A thread the person talks to is theirs, and the pass leaves it alone. Once the person has sent a thread a message after its first reply, through `nexus send`, the dashboard or a Claude session's terminal, the pass records that, never nudges the thread again and never searches GitHub for it. A thread's first message, a harness thread's brief, does not count. An investigation thread the person started without talking to it since may get one nudge before the person's reply makes it theirs. The record lives in the registry's `nudges` table, keyed by the thread: the turn the latest nudge answered and how many nudges in a row, or that the thread waits on the person.

## Queued threads

`nexus start --after A,B` records a thread now and starts it once A's and B's pull requests have merged, landed by the review loop or merged outside it. Builders branch from the default branch as it is when they start, so the start waits for the merge and not for a deploy. [The CLI's contract](cli.md#queued-threads-0290) has the rules and the types, and `src/control/queue.ts` holds them.

A queued thread is not a `threads` row. It is a record in the registry's `queued_threads` table, keyed by the ID the thread will have, holding the start request as it was asked for, with its size filled in from the project's, the predecessors and a Nexus agent thread's first message. So nothing that reads threads sees it: the planner boots no pylon for it, placement counts no room for it, and the PR watch and the review loop pass it by. Only the API's views, the CLI and the dashboard show it.

The control plane runs one pass over the queue every 15 seconds. A queued thread whose predecessors have all landed, or whose start the person asked for with `nexus start-queued`, starts through the same `threadStarter` a `nexus start` uses, under its recorded ID, so placement, capacity, templates and grants apply as for any start, and an `auto` thread that finds no node with room stays queued until one has it. The transaction that inserts the thread's row and pylon also marks the record started, and refuses when the record is no longer queued, so a start never runs twice and a thread archived while its start was in flight gets no row. The harness hands back the conversation it already made for a thread ID, so the same process can try that start again. A start passes the deploy drain's gate, so a draining control plane refuses it, leaving it queued, and waits for one in flight. The first message goes to the thread under the request ID `queued:<id>` after the start, and the record says whether it was sent, so a pass after a crash sends it again under the same ID, which the harness answers with its first submission.

What each predecessor means is read from its thread, its review and the PR watch's links on every pass and every view, never stored: merged and landed, open or not yet opened and waiting, or blocked because its pull request closed, its review ended for the person, or it was archived, cancelled or deleted before a merge. A blocked thread stays queued and says which predecessor blocks it and why, so the person can start it now or archive it to cancel it. The PR watch stops reading an archived thread's pull requests, a capped watch's, one behind an undelivered message and a closed one, and searches only open ones, so for a thread a queued thread waits for it first reads each unmerged one and searches its branches for any state, and a merge just before an archive, after a reopen, or of a pull request it never saw open is not missed.

## Pipeline items

A pipeline item is a brief lined up ahead, with the items whose work must merge first (`src/control/pipeline.ts`). It is a record in the registry's `pipeline_items` table, and it only ever becomes a queued thread: the queue starts it and the review loop reviews, lands and archives it, as for any builder. [The CLI's contract](cli.md#pipeline-items-0370) has the rules, the phases and the types.

A pass every 15 seconds, beside the queue's, goes through the items in the order they were added. An item whose project runs the pipeline, that the person approved where the project asks for that, and whose items ahead each have a thread, is added to the queue after those threads. It is added under the request ID `pipeline:<item>`, which the queued record's own transaction stores, so the item's thread is whatever that request made: a pass after a crash finds it and adds nothing, and the item record never holds a thread ID that could disagree. The person who added the item starts its thread, so its `startedBy` and the policy's checks are theirs.

Nothing about an item's progress is stored. Its phase is read from its thread's records on every view: the queued record and what blocks it, the review's phase, the PR watch's links, the thread's status and its attention. So an item moves as soon as the records it reads do, a reopened pull request moves it back, and the phase the dashboard shows is the phase the CLI prints. An item waits on the person, `held`, when it needs an approval, when its queued thread is blocked, when its review ended for the person or stops at approval, or when its thread failed or needs a decision. Each such item holds only itself.

Items are the person's plan. Only a person adds, approves or cancels one, through the API, the CLI or the dashboard, or by accepting a planning thread's proposal on its card, as [Planning threads](#planning-threads) describes, and no route or tool lets a pylon, a harness thread or the control plane's own caller do so. A thread never starts, messages or drives another thread: each piece of work stays in its own thread, an agent that needs helpers runs them in its own pylon, and only the control plane's passes, the pipeline's, the queue's, the review loop's and the watchers', create threads or act across them.

Which projects the pipeline runs for is `Project.pipeline`, set with `nexus project edit --pipeline off|approve|start` as auto-review is. `start` turns briefs into builders without the person approving each, and `approve` keeps a card's worth of work per item for the person. An off pipeline is stored as null rather than dropped, so the registry migration that turned the pipeline on for project `nexus` never turns it on again.

## Failure judgments

When a builder's pylon fails in a project that runs the pipeline, a model judges whether the failure is an infrastructure fault worth retrying, worth retrying on another node, or one for the person, and the control plane acts on the judgment (`src/control/judgment.ts`). [The CLI's contract](cli.md#failure-judgments-0390) has the answers, the brief's facts and the types.

The judgment is a conversation in the control plane's harness, created with no tools, no extensions and no `cwd`, and with no `nexus.thread` document, so it has no pylon and no registry thread. Its environment factory returns no environment for a conversation without a `cwd`, so building one never reaches a pylon. It can read its brief and answer, and nothing more. The control plane writes the brief from its records: the thread, the whole `failed` text with the controller log it ends with, the pylon's failed jobs, whether its node lists it and whether its disk holds a checkpoint, the node's health read live through its probe with a 5-second limit, the room each other node has for the pylon as placement weighs it, the thread's earlier judgments, and what each answer would do and whether it can run. A fact the brief lacks is the judgment's reason to answer `person` and name it, and a later change adds it to the brief.

A pass every 15 seconds, beside the nudge pass, starts and moves each judgment. It starts judgments only for active and idle threads, and moves every judgment not done, so one whose thread the person archived or deleted while it waited still ends. It runs without the control plane's GitHub token too, because a judgment needs none. Its harness calls pass the deploy drain's gate, so a draining control plane refuses them and the next pass tries again. A failure is the `thread.failed` event that the pylon's `failed` appended, so the judgment's record in the registry's `judgments` table is keyed by that event's ID. A failed Claude launch appends a `thread.failed` event too, with another message, so the pass reads the newest event whose message is the pylon's `failed`. The record is saved before the conversation is created, the conversation's ID right after, and the brief goes out under the request ID `judgment:<failure>`, which pi-durable admits once. A crash between the creation and its save leaves an empty conversation that never got a brief, so it never calls a model. Every save replaces only the record as the pass read it, and the action it records, a retry, a move or a question, runs in the save's transaction, so two passes or a pass after a crash never make two judgments of one failure or act twice on one.

The control plane reads one fenced `nexus-judgment` block from the reply, the newest whose JSON echoes the brief's random token, as the review loop reads `nexus-review`. A reply without one, a run that ends without a reply, and no answer in 15 minutes go to the person. Then it closes the conversation, counts its tokens under the builder thread, and acts, but only while the pylon still holds the failure: a person's retry from the dashboard, an archive or a delete leaves Nexus nothing to do. A failure whose event the registry's event log has dropped, which keeps the last 10,000, cannot be told from a later failure with the same reason, so Nexus does nothing for it either. A project whose pipeline was turned off while its judgment ran gets no retry or move on the verdict: the person decides on the card. A `retry` takes the API's retry path, as agent activity so the pylon is wanted. A `retry-elsewhere` moves the pylon only when its node holds nothing of it, no checkpoint, no VM it lists, no preview and no job in flight, because Nexus has no job that moves a disk. Placement then weighs every other node, and one registry transaction gives the pylon its new node, a fresh first boot and a live spec for that node, and gives the thread its new placement and a fresh setup, since templates stay on the node that built them. Nexus retries one thread's pylon at most twice on its own, a move included. After that each failure goes to the person without a judgment. The person's answer has no cap.

A question for the person offers only the actions that can run then, and `Leave it failed`. When nothing but that is left, Nexus asks nothing, and the failed pylon waits for the person on the thread page. A judgment's question cannot be withdrawn, so one that the person never answers stays open after a retry from the dashboard ends the judgment, and answering it then does nothing.

Failures that were in the registry before judgments began are never judged. The migration that adds the `judgments` table records the newest event then in `judgment_since`, and the pass judges only failures above it, so deploying judgments never retries a pylon the person left failed.

## Questions for the person

A question is a record the control plane owns, in the registry's `questions` table: the thread that asked it, the text, two or more options, the merge policy's reserved case it is if any, and who may answer it, a person or a deployer. It generalizes the review's hold for the person. A [failure judgment](#failure-judgments) asks one when a failed pylon is the person's to decide, a [planning thread](#planning-threads) asks one per item it proposes, and the orchestration pipeline will ask what the merge policy reserves for the person, as [the exploration](explorations/orchestration.md#asking-the-person-through-the-attention-status) describes. The asker chooses the ID, so asking again after a crash finds the question it asked.

An open question makes its thread's attention `decision`, so it notifies and has a card in Needs you as a held review does. The thread page shows it as a card above the landing card, with the text and a button per option, each asking for a confirmation, and `nexus show` lists it. The answer is a person-only route, `POST /v1/questions/<id>/answer`, which records the option, the device that chose it and when. An answer never changes: the same option again answers with the stored record, so a retried answer is safe, and another option is refused. As the Land button does, the card asks the route's own question, and a device the route would refuse gets disabled buttons that say why. Acting on the answer is the asker's part: the judgment pass reads the answer to its question on its next pass.

A Claude worker's AskUserQuestion call is a question too. It is a question the agent chose to ask, not an approval prompt, so it does not reopen [the decision against approvals](roadmap.md#not-planned): workers still run with permissions bypassed. The pylon's hook says which call waits, because the transcript cannot. Claude Code may write the call to its transcript only once its dialog is answered. In one run on Claude Code 2.1.310, the call's line reached the file 20 seconds after Claude made it, together with its result, so a card opened from the transcript never showed while the dialog waited. So after a transcript read that reaches the transcript's end, the control plane runs `nexus-claude-hook asks` in the pylon through the probe: while one of the thread's asks is open, and otherwise once after each session event of the thread, or the first read since the control plane started, while a turn runs or waits. Once a report listed asks, every read while a turn runs or waits runs it until a report lists none, since an ask withdrawn by a delivery that gave up may still wait with no event to follow. Otherwise the reads every 2 seconds of a watched turn do not run it, so a long turn starts no process in the pylon to learn that nothing waits. A run that fails is due again at the next read. The registry stores the asks it prints in `waiting_asks`, in place of the thread's last report, and a run that fails keeps the last report. An empty report after an empty one is not stored again. One with asks always is, since a withdrawn ask or an archive changes the stored report behind the reader's back. Each ask the latest report lists for the worker's current session is the question `ask-<call ID>`, unless the stored transcript holds the call's result, and every unanswered ask that is not one is withdrawn. The registry applies that rule after each report, transcript read and worker launch, and archiving or deleting the thread drops its report. The Notification that the dialog waits is a session event, but nothing orders it after the hook's waiting file, so the PermissionRequest hook also reports `session.waiting`, with no message, once it has written the file. The read after that event opens the card, and the thread shows "waiting for input" as it does for the Notification. A pylon on an image from before that event gets the card from the read after the Notification, which came 6 seconds after the dialog in [`docs/verification/ask-pull-gate/`](https://github.com/ramtinJ95/nexus/tree/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/ask-pull-gate/). The PostToolUse heartbeat of a call the terminal answered makes the read that withdraws it, and the hook sends that heartbeat past its five-minute throttle. Another Claude's ask in the pylon, such as the person's own, asks nothing. The thread page shows an open ask as a form: each asked question with its options as radios, or checkboxes for a multi-select one, their previews, an answer of the person's own and notes. Answering stays person-only, through the same route with the person's choices as its body. The control plane hands the answer to Claude in the pylon first, through [the PermissionRequest hook](#event-stream-and-claude-code-thread-workers), and records it only once Claude has it, so a recorded answer is one Claude got. The terminal's dialog stays open meanwhile, and whichever answers first is the answer. An answer that finds no hook waiting, because the terminal answered, the turn ended or a pause stopped Claude, withdraws the ask and drops it from the stored report, so a read before the pylon's next report cannot ask it again. An answered ask leaves the dock, and the conversation shows the call as a card with the choices and the device, or with Claude's result when the terminal answered it.

## Planning threads

A planning thread is a Nexus agent thread the person opens to plan, with `nexus start --plan` or the start dialog's Planning thread box (`src/control/planning.ts`). It is an ordinary harness thread in its own pylon, recorded in the registry's `planning_threads` table with a random token. It gets no tool that reaches another thread or an item: its tools are a harness thread's, which reach only its pylon, as [Who starts a thread](#who-starts-a-thread) describes.

The control plane puts a guide in front of the thread's first message: the token, and the `nexus-plan` block to end a turn with, which holds each proposed item's key, title, brief, and the keys of earlier items in the block or the IDs of pipeline items it waits on. A pass every 15 seconds reads the replies of each planning thread whose turn ended since its last read, and asks the person one question per item of every block that echoes the token, with the brief in full and the options `accept` and `reject`. The question's ID is made from the thread, a hash of the block's items and the item's place in it, and asking with an ID that exists asks nothing, so a block read twice, by passes that overlap or after a restart cut a read short, makes each card once. A revised block is another block, with new cards.

Only a person answers, as with any question. An accept adds the pipeline item through the same code as `nexus item add`, in the transaction that records the answer, with the person who answered as its adder and an ID made from the question. Its `after` resolves an earlier item of the block to the item that item became, so an accept before the earlier one is accepted, or after it was rejected, is refused and leaves the card open. The item then moves as any item does, under the project's pipeline setting. A reject records only the answer. The next message to the planning thread, under its request ID, starts with what the person accepted, with each new item's ID, and what they rejected, so the thread can revise. Each message's request ID is stored with the guide and answers it carries before it is sent, so a resend sends the same text, and only a message the harness took counts, so a send that failed leaves them for the next message. The nudge pass leaves a planning thread alone, since it is not meant to open a pull request.

A planning thread is a Nexus agent thread, whose replies the control plane's harness records, rather than a Claude worker, whose transcript is read from its pylon, where code it runs could write it. A wrong block still makes only cards, which the person reads before any item exists.

## Retry-safe starts

A start with a request ID can be repeated safely, so a client that lost an answer, or a pipeline step that crashed after it asked, sends the same start again instead of checking what exists. The control plane stores the request ID and a hash of the start's body in the transaction that inserts the thread's row, or the queued record, so a start that failed stores nothing and the ID stays free, and one that succeeded is found by every repeat. A repeat that arrives while the first is still starting shares it in the API's memory, which is enough because one control-plane process serves the API. An immediate start's first message goes to the thread under `brief:<thread>` before the start answers, and a repeat sends it again under that ID, which the harness answers with its first submission, so a start and its brief succeed or retry together without a record of whether the message went. The request IDs are global rather than per caller, because every caller is the person's own machine or the control plane. [The CLI reference](cli.md#retry-safe-starts-0340) has the contract.

## Who starts a thread

A person starts a thread with `nexus start`, `nexus start-queued` or the dashboard's start dialog, messages one with `nexus send` or the dashboard, and adds the pipeline items that become queued threads. The control plane starts every other thread from its own passes, in its own process, through the same `threadStarter`: the queue starts queued threads (`src/control/queue.ts` line 148), including those the pipeline queues from approved items (`src/control/pipeline.ts` line 144), the review loop starts reviewers (`src/control/review.ts` line 596), and the gate starts check and verify threads (`src/control/gate.ts` line 157). Its messages go to the harness in-process too: the queue's first message (`queue.ts` line 139, wired in `src/control/thread-services.ts` line 29), and the review loop's findings, the PR watch's feedback and the nudger's nudges through the inbox (`src/control/inbox.ts` line 127). None of them calls the API. A pylon or a harness thread never starts, messages or waits on another thread, as the decision of 2026-10-28 says, and the API refuses it:

- `POST /v1/threads`, `POST /v1/threads/<id>/start` and `POST /v1/threads/<id>/messages` answer only a person, with `isPerson` (`src/control/releases.ts` line 25), the rule items and question answers use. The API's route table (`featureRoutes` in `src/control/api.ts`, over one module per feature under `src/control/api/`, such as `thread-routes.ts`, where the dashboard's pages are its GET entries in `dashboard-routes.ts`) declares who may call each route that changes state: `person` names the action only a person may take, which `handle` checks with `personOnly` (`src/control/api/access.ts`) before the route runs, and `open` says why any allowed caller may, such as a deployer check the route makes itself. Its type gives a route that changes state no way to leave the declaration out. A person is an allowed caller that is neither the control node nor a registered node. Anything else gets 403 `caller may not start a thread: only a person may, never the control plane, infrastructure nodes or pylons`, with `start a queued thread` or `message a thread` for the other two. A pylon that reached the API would arrive as its node, the control node or an infrastructure node, so it is refused too.
- Every other route that acts on a thread or its pylon answers only a person in the same way: aborting or retrying a turn, retrying a pylon, opening or closing a session, attaching a terminal, publishing or unpublishing a preview, starting or cancelling a review, archiving, unarchiving and deleting, and the human-only project edit, `PATCH /v1/projects/<id>`. A session or an attach is a shell in the pylon, and a review starts a reviewer thread, so each would let one thread drive another. No pass of the control plane calls these routes. The review loop archives the threads of a review that landed or was cancelled in its own process, as it starts them.
- A pylon's own way to Nexus is its host bridge at `http://nexus.pylon`, whose requests are the `PylonApiRequest` kinds (`src/probe/pylon-api.ts` lines 50 to 59): events, info, services, previews and outputs. The probe parses each one against that closed list (`requestSchema` in `src/probe/pylon-api.ts`, lines 106 to 124), and the bridge answers only `/v1/request` (`pylonVmHostBridge` in `src/pylon-vm-backend.ts`, line 254). None of them starts, messages or reads a thread, and the bridge names the calling pylon from the VM the request came through, never from the request (`src/pylon-vm/host-bridge.ts` lines 15 to 18). The Docker backend's bridge, which only the local verify stack uses, answers the same path alone (`src/docker-host-bridge.ts` line 37).
- Every other request from a pylon leaves through Gondolin's HTTP hooks, which pass only the pylon's allowed hosts (`src/pylon-vm/network.ts` lines 23 to 24): the project's, its repository's and its logins' (`effectiveAllowedHosts` in `src/control/project.ts` lines 66 to 72). None of these names the control plane unless a person adds it.
- Even a host a person adds does not reach the tailnet. On the pylon-vm backend, Gondolin's hooks refuse an address in an internal range unless the host is also in `allowedInternalHosts`, and the ranges include Tailscale's `100.64.0.0/10` and the IPv6 unique local range (`blockInternalRanges`, true by default, in `@earendil-works/gondolin@0.13.0`'s `dist/src/http/hooks.js` lines 43 and 162 to 170, and `dist/src/utils/ip.js` lines 111 to 150). Nexus never sets `allowedInternalHosts`.
- A harness thread's turns run on the control plane, but its only tools are pi-durable's `CodingTools` (`src/harness/host.ts` line 105). They reach files and processes only through the pylon's environment (`host.ts` line 114), so a harness thread reaches no further than its pylon. A [failure judgment](#failure-judgments) is offered no tools at all.

So the rule holds in the API as well as in the network. `isPerson` tells a person from a node by the registry, so a device in `control.json`'s `callers` counts as a person. Listing a pylon there, if it ever joined the tailnet as its own node, would let it start threads, and only a person edits that list. The node checks (`src/control/on-node-kit.ts`) run on a node, so their requests to their own control planes would come from that node. Their whois names the node as the person running the check on every port but the probe's.

## Editing project settings

Humans can use `nexus project edit <id>` or `PATCH /v1/projects/<id>` to change placement defaults, branch, resources, allowed hosts, logins, secret grants, git identity and whether builders' pull requests are reviewed and landed on their own. IDs and repository URLs remain fixed. Add and edit share validation; secret hosts must be explicit, nonempty hostname lists. An edit changes only supplied fields; supplied lists replace whole lists, and a null identity removes the override. No agent-facing edit tool is provided. The dashboard's current limited creation dialog is unchanged.

Existing threads retain their placement, checkout, resources and network boot inputs. Running and paused pylons keep their original grants, and `show` exposes whether those differ from the project. The backend reconstructs network options on checkpoint wake, but reconciliation supplies the original saved boot network, not current project settings: archive/unarchive does not apply new grants. Start a new thread to use them, preserving the old thread's work first. Git identity alone is resolved again before a fresh boot or checkpoint wake, so a configured default reaches existing pylons too. Removing configuration does not erase an identity already on disk. Neither project edits nor identity configuration hot-update a running VM.

## Event stream and Claude Code thread workers

The control plane owns a retained, globally ordered event log, separate from the
conversation stream. Any authenticated session follows the same endpoint with a
cursor and thread/project/kind filters. A follower catches up from the registry
rather than subscribing to an in-memory-only broadcast, so disconnecting between
replay and live delivery cannot lose an accepted event. Retention expiry is an
explicit conflict, not a silent jump. Filtering and cursor validation live with
the event model in `src/events.ts`.

Claude workers run inside the pylon, not in the Nexus harness. Thread creation
persists a first prompt; reconciliation opens a Herdr Claude session when the
pylon runs. The initial argument preserves the prompt literally and avoids a
terminal-readiness/keystroke race. `/poteto-mode` is added unless already present.
Herdr 0.9.5's `agent start` refuses an argument holding a newline, tab or other
control character, so a multi-line prompt never reached Claude and the launch
stalled at the shell prompt. A prompted launch therefore types its own command
with `herdr pane run`, each argument a bash ANSI-C quoted word. Control
characters, `'` and `!` are escapes, so the typed line holds nothing the terminal,
readline or history expansion acts on, and Claude receives the exact text. A NUL
cannot be an argument, so the API refuses a prompt with one. Unprompted and
resumed sessions still use `agent start` and its readiness wait.
An uncertain launch is not retried automatically, since starting two coding
agents is worse than asking the person to inspect a possibly started session. A
launch cut off by a probe restart is the exception, as described under
[a launch survives a probe restart](#a-launch-survives-a-probe-restart).
The sandbox justifies bypassed permission prompts, including on resume. Existing
secret injection supplies OAuth placeholders through login-shell environment.
Before every launch/resume, merge Claude's empirically observed onboarding and
trust state for the real checkout into its user files; retain credentials and
unrelated keys and file modes. Already-seeded files are not written. When a
write is needed, re-read before rename and re-merge changed content, up to five
attempts; fail rather than replacing a repeatedly changing file. Trust only the
pylon checkout, never a restored pane cwd, root or HOME. Theme and bypass acceptance live in settings.json on Claude
2.1.308, while onboarding and project trust live in .claude.json.
A worker is normally started after a launch-specific UserPromptSubmit hook writes a
local receipt. This avoids depending on best-effort network event delivery and
cannot confuse another session's event with the worker's first submission.
Herdr 0.9.5 offers only an interactive-readiness wait, not a submission wait,
and a prompted launch does not use it. Even when typing the command errors, allow
30 seconds for the receipt. A live Claude
process plus working status is fallback startup evidence. Never roll back an
uncertain first-prompt launch: retaining an empty pane is safer than killing work.
For unprompted launches, close only after confirming no Claude process runs. Missing proof leaves the
pane open and records stalled state, pane text, thread.failed and failed attention.
The probe answers such a launch with its pane and a `stalled` diagnostic in the
open-session result, not an error, so the control plane never reads a stall from
error text. A probe from before that field reports a stall as a failed launch.
The launch fence forbids any other automatic retry.
Persist its session ID before launch so a late turn-started report can clear
stalled attention without another session clearing it; retain the diagnostic
in the event history.

Claude hooks report lifecycle facts through the narrow host bridge. The probe
supplies identity, validates the event, journals a bounded reconnect buffer and
forwards it through observations. Control deduplicates those reports, updates
activity and attention, and appends the public event. A hook never waits on the
probe. It writes its event to an outbox in the pylon, `~/.nexus/outbox`, and
returns, and a sender it starts delivers the outbox in order and deletes each
event once the probe answers, which it does only after journaling the event. A
probe that is down or restarting delays reports instead of losing them, and an
event sent again after a lost answer carries the ID control already applied, so
control ignores it. Every boot, a wake included, starts a sender too, for the
events a pause left behind. So an outbox on a disk that pylons boot from would
reach every one of them: the image build starts no agent, and the hook writes
only in a pylon a thread owns, which has the overlay's `~/.nexus/pylon.json`, so
neither an image nor a template carries one. Running session state is a 30-minute lease independent of
the retained log and of harness activity. Throttled PostToolUse heartbeats renew
it; a dead or silent worker cannot keep its pylon awake indefinitely. At most 16
session states per thread are kept, and ended or expired working rows are removed.
Waiting persists without refreshing activity. Hook timestamps and bounded durable
ordering cursors reject stale reports after an end; heartbeats renew existing
working leases or resume waiting sessions when newer than their waiting event. A waiting or ended turn returns to the normal
idle policy; seen remains unrelated to activity.

A main turn can end while background subagents keep working, as `/poteto-mode`
does when it delegates. Claude 2.1.308's Stop hook input lists them in
`background_tasks`, and Claude starts a new turn, with a `<task-notification>`
prompt, as each one finishes. So a Stop hook that lists a running subagent
reports a heartbeat, not a turn end. The session stays working, keeps its pylon
awake and gets no reply until the Stop of the turn that follows its last
subagent. Subagent tool hooks carry the main session ID, so their heartbeats
renew its lease. SubagentStart and SubagentStop are not used: Claude's own list
cannot miss a start, and SubagentStop also fires for internal helper agents that
never started one. A subagent that dies without a
finish leaves no follow-up turn, and the lease expires as for any silent turn.
Captures are in [`docs/verification/claude-background-subagents/`](https://github.com/ramtinJ95/nexus/tree/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/claude-background-subagents/).

A Bash command Claude runs in the background lists as a running `shell` in the
same Stop input, and its finish starts a `<task-notification>` turn too. A shell
may also be a dev server that never finishes, so the Stop reports a heartbeat and
the hook holds the turn end back. Claude Code starts each Bash command as its own
child, leading a process group of its own, which the command keeps through `exec`,
redirected output or closed stdio. Its stdio MCP servers stay in Claude's group.
At the Stop the hook records those groups and starts a detached copy of itself,
the hold, which checks every minute whether a recorded group still has a process.
Each group is recorded with its leader's start time, so a later group that reuses
the ID does not count. Once its leader exits, a group counts only while a member
the hold already saw in it, or one that started before the hold, lives: the kernel
reuses no ID while its group has a process, so a reused group's members are all new. A command that leaves its group, such as one that calls
`setsid`, still counts while a process writes to its output file, which Claude Code
names by session and task ID. While the command runs, the hold sends a heartbeat every five minutes, so
a long build keeps its lease and its pylon. Once it exits, the hold waits 30 seconds
and sends the turn end. Every report carries the Stop's own stamp, so the lease
renews by receipt time, and the turn Claude starts when the command finishes, or a
message from the person, makes the rest stale. One hold owns a session at a time,
because a newer Stop lists every shell still running. Holds start in any order, so
under a lock a hold claims the session only from one for an older Stop, and exits if
the owner's Stop is newer. A replaced hold stops at its next check, and only the
owner releases the claim. At the cap the hold sends the turn end and waits for its
sender to finish before it sends the waiting report, so the turn end cannot remove it.

Nothing tells a dev server from finite work. A command still running after 2 hours
has its turn ended, and the hold also reports `session.waiting` with the message
"A background command was still running after 2 hours", which the dashboard shows
in place of "waiting for input" once the reply is read. A waiting session does not
keep its pylon awake, so with no other activity the pylon pauses after the idle
rules and stops the command. A held process does not survive a pause either, but
before the cap the session is working, so its pylon is not paused.

Claude's Notification hook also fires for an idle prompt, 60 seconds after any
turn ends, even with a background command still running. Only `permission_prompt`,
which AskUserQuestion also fires, and `elicitation_dialog` report waiting. The
event does not say which notification fired, so the control plane cannot drop an
idle prompt without risking a real wait whose turn start was lost or late. Until
the image is rebuilt, the old matcher's idle prompt still counts.

An AskUserQuestion dialog can be answered from the dashboard, as [questions for
the person](#questions-for-the-person) describes. Claude Code 2.1.310 runs a
PermissionRequest hook while the dialog shows, in `bypassPermissions` mode too,
and `nexus-claude-hook ask` runs there for AskUserQuestion alone, with a timeout
of a day. Its input has the session and the tool's input but no call ID, so an
ask is named by the SHA-256 of the session and the questions' texts. The call's
PreToolUse input has the ID, and Claude finishes its PreToolUse hooks before it
asks for permission, 35 ms earlier in a spike. So `nexus-claude-hook ask` also
runs at AskUserQuestion's PreToolUse, with a timeout of 2 seconds, and writes
`{"toolUseId": ...}` to `~/.nexus/asks/<key>.call`. The PermissionRequest hook
takes that file and writes `<session>.<key>.waiting`, where `<session>` is the
SHA-256 of the session, a JSON record `{pid, start, at, session, toolUseId, input}`:
its pid and the pid's start time from `/proc`, when it started waiting, the
session, the call's ID or null when no PreToolUse recorded one, and the tool's
input. The start time keeps a pid that a pause or a killed hook freed for
another process from passing for the hook. Once the file is written, the hook
queues a `session.waiting` event, so the control plane's pull after it lists the
ask. The hook then checks every half second that the file still starts with its
own `pid`, `start` and `at`, reading only those first bytes, and for the answer to its call,
`<key>.<call>.answer`, where `<call>` is the SHA-256 of the call's ID, so an
answer meant for one call never reaches another of the same questions.

`nexus-claude-hook asks` prints one JSON array, newest first, of
`{session, toolUseId, at, input}` for each waiting file whose hook still runs
and names its call, and exits 0. It leaves out a waiting file over 256 KiB, and
stops before its output passes 1 MiB. The hook of an image from before prints
nothing for `asks`, which the control plane reads as no asks.

The control plane writes the answer through the probe with
`nexus-claude-hook answer <json>`, whose JSON names the call's ID. It creates
the answer file whole and only once, and only while the live hook's waiting file
names that call. It exits 0 and prints `delivered` once the hook has taken the
answer, now or before, 20 when no live hook waits for the call, 21 when another
answer was written first, and 64 for an argument that is not an answer. While it
waits for the hook to take the answer, at most 5 seconds, a waiting file that
goes away or the time running out makes it take the answer back by renaming it,
which races the hook's own rename, so exactly one of them has it. When the hook
lost, it exits 20. The hook renames the answer to `<key>.<call>.delivered` and
prints a decision that allows the call with Claude's own input plus `answers`
and `annotations`, which closes the dialog and gives the tool its result. A
picked option's preview goes in its annotation from the hook's own input, as the
terminal puts it, since the transcript cuts long strings. When the terminal
answers first, Claude neither stops the hook nor reads what it prints later, so
the call's PostToolUse removes the waiting file, and the hook exits with nothing
printed, as it also does once Claude is gone. That PostToolUse sends its
heartbeat even within five minutes of the last, as no other heartbeat does,
since only the read after it withdraws the question and ends the session's wait.
The start and end of a turn and the end of a session remove the session's
waiting files too, by the session's hash in their names, before the hook queues
their event. No dialog of the session
shows then, and a dialog the person interrupted may have closed without a
PostToolUse. A PreToolUse hook that blocks until the answer would work too, but
it hides the dialog while it waits, so the terminal could no longer answer. The
hook of an image from before exits 0 for `answer` without printing `delivered`,
which the control plane takes as an image that cannot take answers, as it takes
a missing hook's 127.

Every Claude in the pylon reads the same hooks, including one a worker starts to
verify its work, whose turn end would otherwise give the thread a reply while the
worker still works. The hook reports, and snapshots a turn, only for a Claude under
the pylon user's own HOME whose process started without `CLAUDE_CODE_SESSION_ID`, which Claude Code puts
in the environment of everything it runs, even after `env -u CLAUDECODE`, and only in a pylon with `~/.nexus/pylon.json`,
which a template build lacks. Sessions
Nexus opens in Herdr panes, the worker's and the person's, start without it.
Captures are in [`docs/verification/claude-activity-accuracy/`](https://github.com/ramtinJ95/nexus/tree/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/claude-activity-accuracy/).

Filtered stream reads use indexed registry columns, not decoding then filtering
every retained payload. Id-only keep-alives carry the scanned watermark past
skipped records. The CLI consumes those without printing them and waits for
stdout drain before reading more response data or advancing its cursor. Network
failure cannot start another reader around a pending output write.

### Claude launch policy (0.16.0)

Before every start/resume, merge `model: "claude-opus-5-5"` and
`attribution: { commit: "", pr: "" }` into Claude settings, retaining unrelated
keys, hooks and permissions. A per-thread model is passed explicitly with
`--model`, recorded in the registry, and saved from argv when checkpointing.
Claude 2.1.308 was verified with an actual local commit, a no-network `gh pr
create` shim and model usage responses; captures are in
[`docs/verification/claude-worker-launch/`](https://github.com/ramtinJ95/nexus/tree/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/claude-worker-launch/). This token can use Opus 5.5.

Submission evidence wins over a later launch RPC error. Only genuine unresolved
launches publish failure, using the same message stored on the worker. Matching
late submission reports recover failed as well as stalled launches. Neither
recovery nor restart resubmits a first prompt. Views render these registry facts
rather than interpreting historical failure events as current failure.

### A launch survives a probe restart

A deploy restarts each node's probe, and the probe closes its connections at once.
A Claude worker launch in flight then loses its answer, though the pylon and every
guest command already started keep running, so the launch may have done any part
of its work. The control plane treats a lost probe connection as no answer, not
as a failure. It waits up to three minutes for a snapshot from the probe that came
back and sends the same launch again, under the session ID it recorded before the
first. It does the same for a launch still `starting` when the control plane
itself starts, as after its own deploy.

Sending a prompted launch again is safe because the launch records its progress in
the pylon, in `~/.nexus/claude-launches/<session>/`: `opened` names its workspace
and pane once they exist, `typed` is the claim of the guest command that types the
launch, and `submitted` is the UserPromptSubmit receipt. That command creates
`typed` with `mkdir` and types only if it created it, so of two typing commands,
such as one the stopped probe's guest started late and one from the probe that
replaced it, only one types and the other waits for the receipt. A launch sent again
reads them. If the command was typed, it only waits for the receipt, as the first
one would have, and reports a stall the same way. If nothing was typed, it types
into the pane the first one opened, or opens one if that pane is gone. A launch
from a probe older than these files leaves none, so a pane whose Claude already
runs the session ends it as started, and a session with a transcript but no
running Claude fails without typing, since its prompt already went in. One that an
older probe lost before typing gets a new workspace, and the older probe's empty
shell workspace stays beside it. Captures are in
[`docs/verification/launch-survives-deploy/`](https://github.com/ramtinJ95/nexus/tree/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/launch-survives-deploy/). The probe
runs the launches, the sends and a wake's relaunch of one session one at a time, so
a launch sent again while the first still runs waits for it and reads what it did.

Every node runs a probe that reads these files, so the control plane sends the
launch again to whichever probe comes back. Snapshots once said so with
`claudeLaunchRepeatable`, which every probe sent as true. Probes no longer send
it, and the control plane ignores it from one that still does. A launch left
`starting` for a deleted thread fails, since its pylon never runs again. Any other
error, or a probe that does not come back in time, fails the launch with the same
diagnostic as before.

The probe does not drain in-flight commands on SIGTERM. A prompted launch can take
over 50 seconds, longer than a drain that fits the unit's 30-second stop timeout,
so a drain could not make launches safe and the retry is needed anyway. The guest
commands a drain would wait for finish on their own, and a drain would delay every
deploy and keep the old probe answering while the new one waits.

Other calls a probe restart can cut:

- Jobs are retried by the control plane until they expire, under the same job ID,
  and the next job converges from wherever an aborted one stopped.
- Closing a session, dropping a failed session and linking or unlinking a port are
  safe to repeat. The person or client that asked gets a 503 and can ask again.
- A transcript or checkout read is read again on the next event or request. A
  check run whose pipe breaks is discarded and runs again in a new check thread.
- A message sent to a Claude worker that loses its answer stays fenced as
  `sending`. A repeat asks the probe with `send-claude-outcome`, but the probe
  keeps that answer in memory, so after a restart the repeat is refused as
  uncertain, though nothing may have been typed. An agent's message is logged and
  not typed again. Surviving a restart needs the same treatment as a launch: a
  record of the request in the pylon, written by the command that types it.
- Opening a session for a person, with no prompt, opens a second workspace if the
  person asks again after a lost answer.

### Claude worker conversations and steering (0.17.0)

A Claude worker thread has no harness conversation, so its conversation is the
transcript Claude Code writes for the worker's session in the pylon. The control
plane reads it the way it reads the checkout for Files and Changes: one raw pipe
through the probe per read, with a small `sh` helper that prints the file's size and
the bytes after the stored offset. Unlike a checkout read, a transcript read is never
a human's request. It runs only while the node reports the pylon running, never
records activity, and a pylon the probe finds not running keeps what was stored. The
registry keeps the parsed entries, so a paused pylon, or a control plane that
restarted, shows the transcript as of its last read. Only complete lines are taken,
and a record over 4 MiB is skipped with a visible marker, so one huge tool output
cannot stall the reader.

The parser in `src/claude-transcript.ts` was written against real Claude Code 2.1.308
transcripts from a pylon. It turns them into a small model that only grows: prompts,
replies, tool calls, tool results paired by call ID, background task notifications
(subagents and shells), queue operations, notices, turn durations and the pull
requests Claude opened. Claude Code's
bookkeeping records are named in tables and left out. Any other record stays visible
as a generic entry, so a Claude Code upgrade that adds record types degrades to
showing them rather than hiding work. Subagents show as their `Agent` call, its
prompt, and the answer their notification carries. Their own transcripts under
`<session>/subagents/` are not read.

The session events decide when to read rather than a timer. The service follows the
retained event log, an indexed registry read once a second, and reads a Claude worker
thread after each `session.*` event for it. Heartbeats are throttled to one per five
minutes, so while a turn runs and a dashboard watches the thread, it is also read
every 2 seconds. That is what makes entries appear during a turn. These reads do not
ask the hook which dialogs wait unless an ask is open, as [questions for the
person](#questions-for-the-person) describes. The reads stop at the turn's end, so an
idle or unwatched thread costs nothing beyond its event reads.
The dashboard follows its thread stream as it does for a harness conversation, and
the conversation pane renders the entries with the same blocks. While a thread is
watched, its view reads only the entries after the last one it holds, and a read
that found nothing new sends the watchers nothing. A stream whose view has not
changed sends a bare ping, and the client ticks the ages in the page itself. A poll
from a page that streams a conversation, a Claude worker's or a harness thread's,
names the view it would show instead of rendering it
([`docs/verification/transcript-render-once/`](https://github.com/ramtinJ95/nexus/tree/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/transcript-render-once/)).

Steering types the person's message into the worker's Claude session through the
probe command `send-claude`. Typing is the only input Claude Code's terminal takes,
and it behaves as the person at the terminal would expect. While Claude is busy, the
message joins Claude Code's own queue. Claude reads it at its next tool step within
the same turn (recorded as `absorbed_mid_turn`), or takes it after the turn. A
bracketed paste, or any long burst of input, is wrapped by Claude Code in
`<pasted_content>` tags. So the probe types the text in pieces of at most 64
characters, one Herdr `send-text` each, within one guest exec. It then waits half a
second and presses Enter, because Claude reads an Enter that directly follows a burst of
input as a newline. A newline types a line break without submitting, so multi-line
text arrives exactly.
Claude's prompt swallows a tab, and a carriage return submits early, so a message
holding them is refused rather than changed. The probe finds the session's pane by
Herdr's session ID or by Claude's command line. It resumes the session in place, or
in a new workspace, when no live Claude runs it, and it types nothing while Claude
waits at a dialog, because typing would answer that dialog. Right before typing, it
checks again that the pane runs Claude under the session's ID, and types nothing if
another agent or session took the pane meanwhile. The probe runs one send per session
at a time, from finding the pane to the Enter, so two sends never interleave their
pieces and never resume the session twice. Every outcome in which nothing was typed is
a result, not an error. A failed command may have typed part of
the message, so it is never retried automatically: the request ID is fenced as
sending first, and a repeat of a fenced one is never typed. The probe remembers each
send by its request ID until an hour after it settles, so a repeat asks it with
`send-claude-outcome`, which waits for a send still queued behind another and answers
what the send did. A send queued behind a slow one can outlast the control plane's
90-second wait for the probe, and its answer is then lost although the message is
still typed. The repeat reports it. The control plane handles one send per request ID
at a time, so a repeat made while the first is still asked waits for it rather than
sharing its answer. Only a repeat the probe cannot answer, because the
send failed partway or the probe restarted or forgot it, is refused.

Interrupting a Claude worker goes through the probe command `interrupt-claude`, which
finds the session's pane as a send does and presses Esc there with Herdr's `send-keys`,
the key a person at the terminal presses to stop a turn. It takes no key from the
caller. It presses nothing unless Herdr reports Claude working: a dialog would be
cancelled by Esc, and two quick presses at an idle prompt open Claude's rewind picker,
which Herdr still reports as idle. It reads Claude's state again right before the key, since finding the pane
inspects its processes first, but Herdr has no conditional key press, so a dialog that opens between that read and the
key would still get the Esc. It never resumes a session that no live Claude runs,
since that session runs no turn. It waits behind the session's sends, so Esc never
lands between the pieces of a typed message. The person-only abort route sends it for a
Claude worker thread, and never wakes a paused pylon.

Nexus follows a Claude worker by the session ID its launch gave it. `/clear` starts a
new session in the same pane: Claude's SessionStart hook reports the new ID to Herdr,
and Claude writes a new transcript, but the worker record, the conversation view and
the AskUserQuestion questions stay on the old ID. A send after it then finds no pane
running the old session and resumes it in a new workspace, beside the new one.
`/resume`, `/branch` and `/exit` change or end the session the same way. Following a
new session would mean moving the worker record, its transcript cursor and its asks
to the new ID, so the dashboard's composer refuses these commands instead and points
to the terminal, where the person sees what happens. It also refuses commands that
open a picker, such as a bare `/model` or `/config`, because Herdr reports Claude idle
while the picker is open, and the next message would be typed into it
([`docs/verification/claude-interrupt/`](https://github.com/ramtinJ95/nexus/tree/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/claude-interrupt/)).

The API decides by the thread's Claude worker record before anything else, so no
mode or retry of a Claude worker thread's message reaches the harness. Sending is
human activity: it wakes a paused pylon, and clients retry the 409 until it runs with
the same request ID. A message that comes while the wake still relaunches the session
waits for the relaunch. Captures are in [`docs/verification/claude-thread-streaming/`](https://github.com/ramtinJ95/nexus/tree/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/claude-thread-streaming/).

### Usage-limit stops (0.21.0)

Claude workers share the project's Claude subscription, so when it runs out, every
worker stops mid-task at once. Claude Code ends each turn with a synthetic assistant
record, `isApiErrorMessage` with `apiError: "usage_limit_reached"` and the reset time
in `apiErrorParams.rate_limit_info.resetsAt`, whose text reads `You've hit your session
limit · resets 5am (UTC)`. It runs the StopFailure hook rather than Stop, so the image
reports that hook as `session.turn-ended` too. The parser marks the record's notice with
`usageLimit` and its reset. The text is Claude Code's rendering of that same field,
so Nexus never parses it.

A stop is a state of the session rather than something to read, so it is its own
attention, `limited`, rather than `waiting` with a message. `waiting` ranks below
`reply`, which the stop's turn end records, so it would never show. It also means
Claude asks the person something, and a stop asks for nothing until the reset. And a
reply clears when it is seen, which a stop must not. The registry derives the stop on
each read of the thread from the newest transcript entries and the session's state,
rather than storing a flag, so it holds whichever of the turn's end and the
transcript's read arrives first, and the next turn ends it, whoever starts it. An
image without the StopFailure hook never reports the turn's end. The stop record then
ends the session's working lease itself, so such a thread does not show `working`
for 30 minutes.

Other API errors stay plain error notices, and the thread shows an unread reply. Claude
Code has already retried an overload or a server error several times before it gives
up, a 429 that is not the usage limit passes in seconds, and neither says when the API
will take a request again. So the person can send "continue" as soon as they read it,
and there is no time to wait for or to show.

Claude Code continues a session it still runs on its own, about 90 seconds after the
reset. That timer lives in the Claude process, so a pylon that paused while the
worker was idle loses it. `nexus send <thread> continue` after the reset always works.
The control plane can also send it, when `resumeAfterUsageLimit` is set in its
config. It is off by default, because it spends the subscription while the person
may be away. Three minutes after the reset, a pass every 30 seconds types one
attributed message into each stopped active or idle thread whose session has not
continued. Its request ID names the session and the stop, so a restart or a second
pass never types it again. It is never typed into an archived thread, so it never
wakes a pylon the person archived. Each message typed appends `usage-limit.continued`
to the event stream. Captures are in [`docs/verification/usage-limit-stops/`](https://github.com/ramtinJ95/nexus/tree/2c88196d10cd9108d655a05153efa7f72dfdf394/docs/verification/usage-limit-stops/).
