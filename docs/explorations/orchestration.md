# Orchestration inside Nexus

This page explores [the roadmap's orchestration wave](../roadmap.md#the-orchestration-wave): how to run the whole build pipeline on Nexus, with no coordinator chat on the person's Mac. It looks at how other tools orchestrate coding agents, lists what the Mac coordinator did and what each step would reuse, weighs whether there should be one coordinator at all, shapes the pieces the roadmap lists, and proposes an order to build them. The person decides. Until then the roadmap items stay open.

## Decided on 2026-10-28: a thread never drives another thread

On 2026-10-28 the person decided that a Nexus thread never starts, messages, waits on or drives another thread. Each unit of work stays in its own thread and its own pylon. An agent that needs helpers runs them inside its own pylon, as Herdr tabs beside it. A Claude worker already does this when it has a shepherdr reviewer check its diff before it opens a pull request (the "Review before a pull request" guide in [`src/project.ts`](../../src/project.ts) lines 449 to 451). Only the control plane acts across threads: it starts builders, reviewers and queued threads, nudges, archives, lands, deploys and watches pull requests. The control plane is deterministic code, not an agent.

So this page no longer plans tools that let a thread drive other threads. [nexus#179](https://github.com/ramtinJ95/nexus/pull/179) built them as step 6 of the build order and was closed without landing for this reason. The sections changed for the decision are [What replaces the drive tools](#what-replaces-the-drive-tools), [How planning works under the rule](#how-planning-works-under-the-rule), [the build order](#build-order) and [the decisions for the person](#decisions-for-the-person). They were rewritten against Nexus at `66e6073`.

## Recommendation: pipeline rules on the control plane, judgment in short-lived threads

Don't build one long-lived coordinator agent. Extend what the control plane already does for reviews and queued threads: a pass every 15 seconds that reads the registry, GitHub and the release, and moves each piece of work one step. Add a pipeline item that carries one roadmap item from its brief to an archived builder, and derive its phase from the records Nexus already keeps: the queued thread, the builder thread, its pull request link, its review and the release. Where a step needs a model's judgment, such as writing a brief or deciding that a failed pylon is an infrastructure fault, the pipeline starts a short-lived harness thread with one question, reads a fenced answer block from its reply, as the review loop reads `nexus-review`, and archives it. The builder thread stays the owner of everything inside its pull request: it builds, answers findings and rebases, as it does today.

The reasons, in short:

- **Most of the pipeline already runs without a model.** Reviews start on their own for a project that asks for it, and the review loop lands under the merge policy, deploys Nexus's own pull requests, rolls a failed deploy back and rebases a conflicting branch through the builder ([`src/control/review.ts`](../../src/control/review.ts) lines 461 to 533). Queued threads start when their predecessors merge ([`src/control/queue.ts`](../../src/control/queue.ts)). What is left for a coordinator is small: choosing and briefing the next items, noticing a builder that stopped short of a pull request, judging failures, and cleaning up.
- **A long-lived agent keeps every weakness of the Mac chat that the roadmap names.** It still moves only during a turn, its context still fills, and one stuck turn still stalls every item. Running it on the control plane removes only the laptop.
- **The tools surveyed below that do reach across turns and restarts keep their state in code, not in a model's context.** t3code commits every command, event and effect in one SQLite transaction and recovers from that. Codex's and Grok Build's model-driven delegation keeps live state in memory inside one session.
- **Each item fails alone.** A deterministic pass that reads state on every step converges after a crash, as [the section on idempotent steps](#make-each-step-idempotent) describes, and an item waiting on the person holds only that item.

The cost is code on the control plane, roughly the size of the queue and a fraction of the review loop, and a fixed pipeline shape that a person changes by changing code rather than by telling an agent. The person's interface becomes the dashboard: a list of pipeline items and their phases next to the thread list, decision cards for the calls the merge policy reserves, and the items they add, either themselves or by accepting a planning thread's proposals, as [How planning works under the rule](#how-planning-works-under-the-rule) describes. No single chat is the interface to every pylon.

## How other tools orchestrate

Five questions for each tool: who decides what runs next, how it wakes, where its state lives, how it asks a person, and what it does when a worker fails. Each tool's claims come from its source at the commit above. Several documentation sites could not be read from the pylon, and [What this page could not check](#what-this-page-could-not-check) lists them.

### t3code

t3code has no planner. An agent drives other threads through an MCP server that t3code hosts, and a single event-sourced orchestrator in the server carries out what it asks.

- **Who decides.** A person's message, an agent's MCP call, a scheduled or webhook task, or the usage-limit recovery sweep. The MCP server lets an agent "create an app-owned sub-agent on any supported provider instance", wait for it, poll it and cancel it, and send to, wait on or interrupt any thread ([`orchestrator-mcp-server.md`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/docs/orchestration-v2/orchestrator-mcp-server.md#L5) line 5). A delegated task always gets a new child thread with none of the parent's history (line 17). A child's runtime and interaction mode may "stay equal to or become narrower than the parent" (line 498). Within a thread, runs wait in a FIFO queue, and a delegated child's completion message goes to its front ([`QueuedRunOrder.ts`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/apps/server/src/orchestration-v2/QueuedRunOrder.ts#L12) lines 12 and 23). The search found no limit on depth or on the number of children, which is inferred, not proven.
- **How it wakes.** Events, with a polling fallback. Subscribers get events only after their commit, and replay the store before they follow live ones ([`EventSink.ts`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/apps/server/src/orchestration-v2/EventSink.ts#L245) lines 245 and 834). The effect worker wakes on a notification, on the next retry time, or on a 30-second poll whose comment says it "recovers missed wakeups" ([`EffectWorker.ts`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/apps/server/src/orchestration-v2/EffectWorker.ts#L869) lines 869 to 885). `t3_thread_wait` holds the agent's tool call until an event or a timeout, and a timeout does not cancel the work ([`ThreadManagementService.ts`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/apps/server/src/orchestration-v2/ThreadManagementService.ts#L931) line 931).
- **Where state lives.** SQLite. `commitCommand` writes the command's receipt, its events, the projections and the outbox's effects in one transaction ([`EventSink.ts`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/apps/server/src/orchestration-v2/EventSink.ts#L635) line 635). Every command has a `commandId`, and a repeated one replays its stored events or its stored rejection ([`Orchestrator.ts`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/apps/server/src/orchestration-v2/Orchestrator.ts#L12736) line 12736). An MCP call's IDs derive from its `clientRequestId`, so "retrying the same call returns the same durable work" ([`orchestrator-mcp-server.md`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/docs/orchestration-v2/orchestrator-mcp-server.md#L511) line 511).
- **How it asks a person.** A runtime request, such as an approval or a `user_input` question, is pending until answered, and the answer becomes an outbox effect ([`orchestrationV2.ts`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/packages/contracts/src/orchestrationV2.ts#L1175) line 1175). A child's question goes to its parent agent as a queued message, but "approvals are not routed" ([`orchestrator-mcp-server.md`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/docs/orchestration-v2/orchestrator-mcp-server.md#L485) line 485). The person hears through browser notifications and an iOS push relay ([`AgentAwarenessRelay.ts`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/apps/server/src/relay/AgentAwarenessRelay.ts#L285) line 285).
- **When a worker fails.** An effect is retried up to 5 times with backoff, then marked failed ([`EffectWorker.ts`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/apps/server/src/orchestration-v2/EffectWorker.ts#L633) line 633). After a server crash, unfinished runs become `cancelled`, queued runs are held, and effects tied to the dead process are cancelled while replay-safe ones run again ([`ProviderRuntimeRecoveryService.ts`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts#L386) line 386, [`EffectOutbox.ts`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/apps/server/src/orchestration-v2/EffectOutbox.ts#L125) line 125). A parent's held wait on a child that the crash cut becomes a wake-up message instead (line 494 of the recovery service). A project can opt in to a "Continue where you left off." run after a restart, at most 3 in a chain ([`RestartContinuation.ts`](https://github.com/pingdotgg/t3code/blob/e0b3cfe666b4f902b290b585081dbc9168152aa2/apps/server/src/orchestration-v2/RestartContinuation.ts#L31) lines 31 to 33).

What Nexus should take: request IDs on every call that starts or sends work, a wait that times out without cancelling, a held wait that turns into a wake-up message when the process restarts, children that can only narrow what their parent may do, and a poll that recovers missed wake-ups. Nexus already decided against t3code's event sourcing and effect outbox ([Not planned](../roadmap.md#not-planned)), and nothing below needs them. The registry appends most events in the same transaction as the change they report, such as `thread.turn-ended` and `thread.failed` ([`src/control/registry.ts`](../../src/control/registry.ts) lines 1055 and 1104). `savePrWatch`, `setDesiredRelease` and `reportRelease` write the event and the state in separate statements outside one transaction (lines 961 to 982), so a crash between them can leave one without the other. That matters little here, because the passes below read state, not events.

### Grok's bot and Grok Build

"Grok's bot" has two plausible readings. The `@grok` bot on X is a reply bot whose system prompt is public, and it has search and X-thread tools but nothing about code ([`grok-prompts`](https://github.com/xai-org/grok-prompts/blob/a7c186f5ccac95875c0041aed60398f6ecb6d6c7/ask_grok_system_prompt.j2#L1) line 1). The one that orchestrates coding agents is Grok Build, xAI's open-source coding agent and TUI, so this section reads Grok Build. Which one the roadmap meant is a guess.

- **Who decides.** The model, through the `task` tool, which takes `run_in_background` ([`task/mod.rs`](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/task/mod.rs#L649) line 649). A coordinator actor in code owns the queue, deadlines and cancellation ([`task/coordinator.rs`](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/task/coordinator.rs#L1) lines 1 to 10). Scripted workflows can also call `agent()` and `parallel()` ([`engine.rs`](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-workflow/src/engine.rs#L489) lines 489 to 530).
- **How it wakes.** A held turn first. The parent waits on the child, and when the wait's budget runs out the coordinator moves the child to the background and hands the model a task ID to poll ([`task/mod.rs`](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/task/mod.rs#L722) lines 722 to 743). When background work ends, the session queues a synthetic "auto-wake" prompt, such as `TaskCompleted` or `SubagentCompleted` ([`session/mod.rs`](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/session/mod.rs#L223) lines 223 to 238).
- **Where state lives.** Live task state is in the coordinator actor's memory ([`coordinator.rs`](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/task/coordinator.rs#L65) lines 65 to 95), transcripts are JSONL files, and a durable attempt store says of itself "no code calls this module yet" ([`attempt_store/mod.rs`](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/agent/subagent/attempt_store/mod.rs#L1) line 1).
- **How it asks a person.** Permission prompts and an `AskUserQuestion` tool. A child gets its parent's permission handle, so its prompts reach the same person, which is inferred from [`handle_request.rs`](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/agent/subagent/handle_request.rs#L1579) lines 1579 to 1583.
- **When a worker fails.** A waited-on child's failure comes back as the tool's error ([`task/mod.rs`](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/task/mod.rs#L774) lines 774 to 779). A background child's failure is only logged ([`coordinator.rs`](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/implementations/grok_build/task/coordinator.rs#L1170) lines 1170 to 1184). No task-level retry turned up.

What Nexus should take: the synthetic wake-up message. A parent that delegated should not hold a turn for the child. It ends its turn, and the child's end arrives as a new input.

### Muse

The coding tool named Muse that fits is Meta's Muse Code. Its SDK repository holds the protocol's types, but the agent binary is "not part of this repository" and its source is "mirrored, not developed here" ([`README.md`](https://github.com/meta-models/muse-code-sdk/blob/a45cb67cd2e27c8b6b4b55dcbaae6e6341123ea4/README.md#L52) lines 52 and 65). So this section describes a protocol, not a runtime. All line numbers are in [`schema/msp/msp.d.ts`](https://github.com/meta-models/muse-code-sdk/blob/a45cb67cd2e27c8b6b4b55dcbaae6e6341123ea4/schema/msp/msp.d.ts).

- **Who decides.** The model proposes workflows (`triggerSource` `"modelProposal"`, lines 1240 to 1241). A parent drives subagents with `subagent/sendMessage`, `interrupt`, `stop` and `resume` (lines 3022 to 3071). A client can cancel, pause, resume, skip or retry a workflow's child (lines 3923 to 4014).
- **How it wakes.** Pushed events from a cursor (line 2641), a monitor inbox (lines 1515 to 1566) and cron (line 1136). A control command's acknowledgement is "admission-only", and its outcome "arrives as the workflow item's view events, never through the ack" (lines 3978 to 3984).
- **Where state lives.** Session files, and a git worktree per child with its own cleanup states (lines 1998 to 2023).
- **How it asks a person.** `approval/request` and `approval/decide`, where the decider may be a user, a policy or an LLM judge (lines 122 to 251). A subagent's approvals show on its parent's session (lines 212 to 217). `userInput/request` can time out (lines 3614 to 3810).
- **When a worker fails.** A workflow child records a `failureKind`, and skip or retry is a manual command guarded against a stale attempt (lines 3940 to 3976). A host crash yields a synthesized `failed` end (lines 1350 to 1354).

What Nexus should take: the decider of an approval is a field, so a policy can answer what it may and a person answers the rest. The merge policy already works that way for landings.

### Claude Code

The CLI's source is not public, so this rests on its changelog and on the GitHub Action's code. The changelog describes fixes, not designs, so read these as observed behaviour.

- **Background agents.** The model starts them through the Agent tool. They notify the parent when they end ([`CHANGELOG.md`](https://github.com/anthropics/claude-code/blob/58d6da1e34d6cd1c6379dcbf568bd66f5f9b6102/CHANGELOG.md#L791) line 791), and a wake starts a new main turn (line 59). They can be resumed with SendMessage after the session was killed (line 977), but a cloud container's replacement could lose one (line 565). Their own permission prompts reach the person (line 1354). This is the Mac coordinator's mechanism, and its limits are the roadmap's: the parent session must be alive to be woken.
- **The GitHub Action.** A GitHub event decides. The action picks a mode from the event and needs the `@claude` trigger and an actor with write access ([`detector.ts`](https://github.com/anthropics/claude-code-action/blob/d70510b174a1244958df0b03166a54912811f3e6/src/modes/detector.ts#L14) lines 14 to 81, [`run.ts`](https://github.com/anthropics/claude-code-action/blob/d70510b174a1244958df0b03166a54912811f3e6/src/entrypoints/run.ts#L196) lines 196 to 223). Each run is one job whose state is a tracking comment it keeps updating, and a `finally` block updates it even on failure (`run.ts` lines 316 to 358). It asks the person through that comment thread, and a separate check needs human approvals on pull requests with agent-written commits ([`agent-approval-check/README.md`](https://github.com/anthropics/claude-code-action/blob/d70510b174a1244958df0b03166a54912811f3e6/agent-approval-check/README.md#L9) lines 9 to 28).

What Nexus should take: the Action's shape. An event starts a short job, the job's state is outside the model, and the job always reports where the person already looks. Nexus's review loop has that shape already.

### OpenHands

OpenHands' main repository is now a frontend, and its agent loop lives in the SDK. A `while True` loop asks the model for the next action, up to an iteration cap ([`local_conversation.py`](https://github.com/OpenHands/software-agent-sdk/blob/46b1fa5cb91ada17e6ec938c7e8624a4fa19fa98/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py#L2015) lines 2015 to 2126). State is a directory with `base_state.json` and an `events/` folder. A confirmation policy pauses the loop until the person approves (lines 2091 to 2094). On a run of failed actions it nudges the model once, then marks the conversation stuck (lines 787 to 810). Its `delegate` tool runs at most 5 children in threads and joins them ([`delegate/impl.py`](https://github.com/OpenHands/software-agent-sdk/blob/46b1fa5cb91ada17e6ec938c7e8624a4fa19fa98/openhands-tools/openhands/tools/delegate/impl.py#L44) line 44).

What Nexus should take: one nudge, then hand it on. The review loop already nudges an agent twice before it goes to the person ([`src/control/review.ts`](../../src/control/review.ts) lines 391 to 397).

### What the survey shows

Every tool that delegates lets the model start children, and every one of them keeps the parent alive while it waits, either in a held tool call or in a session that a completion message wakes. None runs a multi-day pipeline from one model's context. The parts that survive a crash are code: t3code's receipts and outbox, Muse's admission-only commands, the Action's tracking comment. Nexus's control plane is already that kind of code, with request IDs on messages ([`src/control/api.ts`](../../src/control/api.ts) lines 265 to 271) and a review loop that saves each step before it acts. Nexus takes the code half of these tools and leaves the model half: under [the decision of 2026-10-28](#decided-on-2026-10-28-a-thread-never-drives-another-thread), no model in Nexus starts a child thread.

## What the Mac coordinator did

The roadmap lists its steps ([roadmap](../roadmap.md#the-orchestration-wave)). Between 2026-10-25 and 2026-10-28, 93 pull requests landed on main (`git log --since=2026-10-25 --format=%s | grep -c '(#[0-9]*)$'`). Some of the coordinator's steps moved into the control plane during that window: reviews and landing in [nexus#90](https://github.com/ramtinJ95/nexus/pull/90), agent-run deploys with drain and rollback in [nexus#66](https://github.com/ramtinJ95/nexus/pull/66), reviews that start on their own and rebase on conflict in [nexus#151](https://github.com/ramtinJ95/nexus/pull/151), and queued threads in [nexus#155](https://github.com/ramtinJ95/nexus/pull/155). [The design](../design.md#the-review-loop-and-landing) says reviews "used to run on the person's Mac, through a Claude Code coordinator and its workers".

| Step | Who can do it | What it reuses | What is missing |
|---|---|---|---|
| Pick the next item from the roadmap | A model. Ordering, dependencies and whether an item is ready are judgment | `nexus start --after` records dependencies ([`queue.ts`](../../src/control/queue.ts) lines 89 to 109) | A list of pipeline items, which the person writes or accepts from a planning thread's proposals |
| Write the builder's brief | A model | A Claude worker's brief is `claude` in `POST /v1/threads`. A harness builder's brief is a first message, which the route takes as `message` only for a queued start. An immediate start must send it with `POST /v1/threads/<id>/messages` ([`api.ts`](../../src/control/api.ts) lines 922 to 930) | Nothing beyond planning, but a start and its first message are two calls, and a crash between them leaves a builder with no brief |
| Start the builder | The loop | `threadStarter`, through the queue | A start request ID. `POST /v1/threads` has none, so a retried start can make a second thread. Only a queued start has a stable ID |
| Start `nexus review` | The loop, already | `auto()` in [`review.ts`](../../src/control/review.ts) lines 655 to 668, on the PR watch's link | Nothing, for a project with `--auto-review` |
| Notice a builder that stopped at a draft | The loop detects it. A nudge is a fixed message | `thread.turn-ended` and `session.turn-ended` events, the PR watch's links, the inbox | A rule: a builder whose turn ended with no linked pull request, after a PR watch pass that ran since, gets a nudge, then goes to the person |
| Triage review findings | The builder, already | The review loop's rounds and the builder's answers | Nothing. The coordinator relayed findings because no loop did. The round cap sends a dispute to the person |
| Merge under the merge policy | The loop, already | `merging` in `review.ts` lines 461 to 501, `policy.ts` | Nothing, for a project with `--auto-review land` |
| `nexus deploy --wait` | The loop, already | `review.ts` lines 502 to 533 sets the release and waits for `releaseOutcome`, as the CLI does ([`nexus.ts`](../../src/cli/nexus.ts) lines 925 to 943) | Nothing for Nexus's own pull requests. The deploy workers run as root, so the sudo prompt of 2026-10-25 does not recur. That the prompt predates [nexus#66](https://github.com/ramtinJ95/nexus/pull/66) is inferred |
| Check a deploy live | A model, in a thread the control plane starts | The verify-nexus skill, and the verify pylon that [the open question](../design.md#open-questions) recommends | The verify pylon, which the roadmap puts first |
| Gather evidence when a pylon's controller crashes | A model judges. Reading the logs is mechanical | `thread.failed` | Node diagnostics without SSH, the roadmap's own item |
| Decide whether a failure is infrastructure | A model | The diagnostics above | A judgment thread with a typed answer |
| Archive finished threads | The loop | `POST /v1/threads/:id/archive` | A rule. Today "only the person archives or deletes a builder or a reviewer" (`review.ts` line 566), and archiving a review's thread before it ends cancels it |
| Keep state | The registry | `reviews`, `queued_threads`, `pr_watches` | Pipeline items before they become threads |
| Bring the person real decisions | The loop, for the reserved cases | Attention `decision` and the Land card ([merge policy](../merge-policy.md#what-the-person-does-with-a-held-landing)) | Questions that are not landings, such as approving a brief or an image rebuild |

Two of the three stalls on 2026-10-25 are gone in today's code: the review loop merges a reviewed pull request whose live check couldn't run, under the policy's second branch, and the deploy no longer asks for a password. The third, a thread that stopped at a draft, has no rule yet.

## One coordinator or not

Three shapes, each running on the control plane.

### A long-lived coordinator agent

One harness thread holds the plan, gets the drive-other-threads tools and wakes on events. It is the closest to what worked on the Mac, and it needs the least new code outside the tools and the wake-ups.

Against it: it serializes every decision through one conversation, so a long turn on one item delays every other item's next step. Its context fills over days, and pi-durable's compaction replaces older entries in what the model sees with a model's summary (`pi-durable/README.md:552`), so what it remembers of an item is a summary, not a record. Each wake re-reads state the registry already holds, and pays for it in tokens. And it would repeat in a model what `review.ts` and `queue.ts` already do in code, so two parties would decide the same steps. On a restart, pi-durable gives an interrupted tool call an `interrupted` error unless the tool is marked replay-safe (`pi-durable/dist/harness/tool.js:104-123`), so every tool it calls must be idempotent anyway, and at that point the steps it drives are code too. The decision of 2026-10-28 rules this shape out as well, since the coordinator would be a thread that drives other threads.

### Pipeline rules on the control plane, with short-lived judgment threads

This is the recommendation. The pass reads each item's records and takes the next step. A judgment call becomes a thread with one brief and one answer block. Each item moves alone, a crash costs at most one pass, and the person sees the item's phase rather than a chat.

Against it: the pipeline's shape is code, so changing how work flows is a pull request. A judgment thread starts cold, without the context a long-lived coordinator would carry, so its brief must hold what it needs. Every judgment call adds a thread and a pylon boot, which costs seconds and the pylon's memory while it runs. A judgment thread needs no pylon, because its brief holds every fact it needs and it calls no tools, as [What replaces the drive tools](#what-replaces-the-drive-tools) describes.

### Per-item owner threads

One agent thread per item carries it from brief to deploy: it starts the builder, watches the review, deploys and archives.

Against it: the builder thread is already the per-item owner for everything a model must do inside a pull request, and the control plane must keep landing and deploying, because an approval or a deploy decision written inside a pylon can be forged by the code it runs ([merge policy](../merge-policy.md#how-nexus-checks-each-condition)). An owner thread beside the builder would wake on every review step only to watch what the loop already does, and its decisions would overlap the review loop's again. An owner thread that starts and watches its builder would also break the decision of 2026-10-28. What survives of this shape is already true: the builder owns its item's work, and the recommendation keeps it that way.

### What the person's interface becomes

The dashboard's thread list and attention stay the overview of every pylon. A pipeline view lists items with their phase, derived from their records: planned, queued behind named items, building, in review, landing, deployed, held for the person, or archived. A held item shows the same kind of card as a held landing. When the person wants to change the plan, they add, approve or cancel items, and may open a planning thread to draft proposals for them, as [How planning works under the rule](#how-planning-works-under-the-rule) describes. No chat has to stay open for the pipeline to move.

## The pieces

### Whether a tool can run on the control plane host

Nothing uses these findings now. They were the ground for the drive tools, which [the decision of 2026-10-28](#decided-on-2026-10-28-a-thread-never-drives-another-thread) dropped, and they stay here as findings. Only the per-conversation tool lists at the end of this section matter to the build order, because step 8 gives a judgment thread no tools.

A tool can run on the control plane host. A pi-durable tool's `execute()` always runs in the harness process: the tool task builds the environment and then calls `tool.execute(args, api, context)` directly (`pi-durable/dist/harness/tool.js:309-312`). The environment is only a field the tool may read, `api.env: ExecutionEnv | undefined` (`pi-durable/dist/harness/types.d.ts:165-166`), and the built-in `read`, `write`, `edit` and `bash` touch files and processes only through it (`pi-durable/README.md:247`). A tool that never reads `api.env` runs on the control plane host, in the control-plane process, since that is where Nexus runs the harness ([`src/harness/host.ts`](../../src/harness/host.ts) lines 99 to 102). There is no separate API for host tools, and none is needed.

Four details matter for building them:

- **The environment is built before every call, used or not.** A throw while building it becomes the call's error (`pi-durable/dist/harness/tool.js:309`, `:318-328`). Nexus's factory throws when a conversation has no `cwd` or no `nexus.thread` document ([`src/harness/pylon-env.ts`](../../src/harness/pylon-env.ts) lines 52 to 53, [`src/harness/thread-doc.ts`](../../src/harness/thread-doc.ts) lines 32 to 35). It does not reach the pylon while building, because the connection starts lazily (`pylon-env.ts` lines 2 to 4). So a host tool works while its thread's pylon is paused, but fails in a conversation without the thread document. A judgment thread with no pylon needs a factory that returns no environment instead of throwing.
- **Tools can reach the harness.** A tool's `api` has `conversation(id)`, whose handle can `submit` and read `entries`, and `commit`, whose transaction can create conversations (`pi-durable/dist/harness/types.d.ts:155-237`). Nexus code outside a tool can also close over the harness, as the turn snapshots do (`host.ts` line 94).
- **An interrupted call is not re-run by default.** Before `execute` runs, the call's arguments and its `replay` setting are committed. After a crash the call runs again only if both the stored and the current tool say `replay: "safe"`, and otherwise the model gets "was interrupted and may have partially run" (`pi-durable/dist/harness/tool.js:99-123`). The default is unsafe (`pi-durable/dist/harness/types.d.ts:243-244`).
- **A call has stable IDs.** `api.callId` and `api.taskId` identify the call (`pi-durable/dist/harness/types.d.ts:156-158`), and the README's own subagent pattern uses `requestId: \`subagent:${api.taskId}\`` (`pi-durable/README.md:663`). Submissions deduplicate on `requestId` (`pi-durable/README.md:129-138`). The README warns that "a replay-safe tool with external effects still needs its own idempotency" (`pi-durable/README.md:328`).

Per-conversation tool lists exist: `configure` takes `extensions`, `tools` and `modelTools`, as a list to enable or as `{ remove }` (`pi-durable/README.md:385-398`), and a tool's `callers` limits whether the model, other tools or both may call it (`pi-durable/dist/harness/types.d.ts:259-263`). Nexus creates every conversation with only a model and a `cwd` ([`host.ts`](../../src/harness/host.ts) lines 137 to 141), so every thread gets every installed tool today.

The tarball ships only `dist/`, the README and the changelog, so the README's examples, such as example 23's reporter task, were not available to read.

### What replaces the drive tools

This page used to plan five tools for harness threads: `nexus_start`, `nexus_send`, `nexus_read`, `nexus_wait` and `nexus_item`, with a cap on a thread's children kept on the thread record. [nexus#179](https://github.com/ramtinJ95/nexus/pull/179) built the first four. It added `nexus start --drive`, a `thread_tools` table that held each thread's `drive` flag and `parent`, a cap of 3 live children with no grandchildren, and a 15-second pass that delivered each `nexus_wait` watch once under the request ID `watch:<id>`. It was closed without landing, and none of it is on main. Under [the decision of 2026-10-28](#decided-on-2026-10-28-a-thread-never-drives-another-thread), three things replace the tools.

- **A thread's helpers live in its pylon.** An agent that wants a reviewer, a second opinion or a parallel search starts it as a Herdr tab beside itself, on the same checkout. The pylon's guide already tells a Claude worker to do this with a shepherdr `reviewer` before it opens a pull request ([`src/project.ts`](../../src/project.ts) lines 449 to 451), and pi's `openai` provider is signed in there for it ([design](../design.md#pis-chatgpt-login-in-a-pylon)). A helper shares the pylon's CPUs, memory, egress allowlist and secrets, so it can do nothing its thread cannot do. Nexus does not see it as a thread: it has no row, no attention and no review, and it stops when the pylon pauses or is archived.
- **The control plane acts across threads.** The review loop starts reviewers and check threads, lands and deploys. The queue starts queued threads, the pipeline pass queues items, the nudge pass messages a builder that stopped short, and the PR watch reads pull requests. Each is a pass in `src/control/` that runs in the control-plane process, and none of them acts on a model's words beyond a fenced answer with a fixed set of options, such as a review's verdict. [The design](../design.md#who-starts-a-thread) lists who may start a thread and why a pylon or a harness thread cannot.
- **A judgment thread gets its facts in its brief.** The control plane writes the brief from records it already holds, and reads one fenced answer block from the reply, as the review loop reads `nexus-review` ([`src/control/review.ts`](../../src/control/review.ts) line 256). For a failed pylon the brief holds the thread's `failed` text, which ends with the last 60 lines of the controller log when the node reported the pylon broken, and the node's health: load, memory, swap, free disk, temperatures, and each running pylon's controller and QEMU with their CPU and memory. [Node diagnostics](../design.md#node-diagnostics) already serve both. The answer is retry, retry on another node, or ask the person. The thread reads nothing else, so it needs no tools at all, and with no tools it needs no pylon. If the brief lacks a fact the judgment needs, the thread answers "ask the person" and names the fact, and a later change adds it to the brief.

What the tools needed goes away with them: a request ID per tool call, durable watches that message a waiting conversation, a parent and a child cap on the thread record, and a caller identity for pylons on the API, which the merge policy reserves for the person as an auth change.

### How planning works under the rule

Pipeline items exist since [nexus#180](https://github.com/ramtinJ95/nexus/pull/180), and only a person adds, approves or cancels one ([design](../design.md#pipeline-items)). So the question is how a model's help with planning reaches that list. Three shapes fit the pipeline:

1. **The person adds items.** `nexus item add` takes a brief, the items it is after and the start's fields ([CLI](../cli.md#pipeline-items-0370)). The dashboard's Pipeline page approves and cancels items but cannot add one yet. The person can ask any thread to draft briefs and paste them in. This exists today.
2. **A planning thread's proposals become items.** The person opens a planning thread. It ends a turn with a fenced block of proposed items, and the control plane reads the block, as it reads a judgment thread's answer, and adds each item.
3. **The person accepts each proposal on a card.** The same fenced block, but the control plane turns each proposal into a [question](../design.md#questions-for-the-person) on the planning thread, with options to add it or drop it. Only a person may answer it. An answer to add it makes a pipeline item through the same code as `nexus item add`, with the person who answered as its adder.

The rule allows all three in its letter, because in each one the control plane, not the planning thread, creates the item and later starts the thread. Shape 2 breaks it in substance. A judgment thread picks one of a few fixed answers about work that already exists. A planning thread's block is open-ended work, so under shape 2 every builder that starts would be authored by a model with no person in between when the project's pipeline is `start`, which is what `nexus_start` would have done by another route. It also contradicts the decision that only a person adds an item, and the item's `addedBy`, which becomes its builder's `startedBy`, would have to name the control plane.

This page recommends shape 3, with shape 1 kept. Shape 3 keeps the person as the only party that adds work, costs one card per proposal, which is the cost the person already pays under `--pipeline approve`, and reuses the question records and the decision card that [nexus#172](https://github.com/ramtinJ95/nexus/pull/172) built. A planning thread may be a Claude worker, whose reply is read from a pylon where code it runs could forge the block. That matters little here, because a forged proposal still becomes only a card that the person reads before an item exists.

### Wake-ups from the event stream

The control plane's passes are the consumers. The review loop, the queue and the pipeline pass run every 15 seconds and read state on every pass. An event only makes a pass run sooner. So a missed event costs at most one pass, and recovery needs no replay: the next pass reads the records the event described. This is the rule t3code's effect worker follows with its 30-second poll, made the only rule.

The events that matter, and where each comes from:

| Event | Exists | Source |
|---|---|---|
| A builder's turn ends | Yes | `thread.turn-ended` for a harness thread ([`registry.ts`](../../src/control/registry.ts) line 1055), `session.turn-ended` for a Claude worker |
| A turn fails or a pylon fails | Partly | `thread.failed` when a pylon's `failed` changes (`registry.ts` line 1104). A turn that fails without failing its pylon shows only in attention |
| A pull request opens | No | The PR watch links a pull request without an event. `pull-request.feedback` fires only for new feedback (`registry.ts` line 963). Add `pull-request.linked` |
| A review changes phase or ends | Yes | `review.changed` (`registry.ts` line 949) |
| A deploy finishes | Partly | `release.changed` fires when the desired release is set and whenever a node's report changes state, commit, target or reason, healthy and failed included (`registry.ts` lines 971 and 977 to 982). No event says the release as a whole is healthy, failed or superseded, so a consumer computes `releaseOutcome` from the reports, as the review loop does |
| A node's pylon crashes | Partly | `thread.failed`, without the controller's log. The diagnostics item adds the log |

Nothing inside Nexus follows the stream yet ([`docs/cli.md`](../cli.md) line 695 says the follower "does not itself schedule a new model turn"). An in-process consumer needs no follower: it can be a notification from the registry's `appendEvent` to the passes, since both run in the control-plane process. The SSE stream stays for clients. Its retention, the last 10,000 events (`registry.ts` line 598), matters only to those clients, because the passes never depend on having seen an event.

### Asking the person through the attention status

The `decision` attention already means a review ended for the person ([`src/control/attention.ts`](../../src/control/attention.ts) lines 9 and 25), and the Land card already answers it. Generalize the review's hold into a question record: the item or thread it belongs to, what is asked, the options, which reserved case of the merge policy it is if any, and who may answer. A question sets its thread's or item's attention to `decision`, the dashboard shows it as a card, and the answer is a person-only route, as project edits are. The answer is stored and the next pass acts on it, or submits it to the waiting conversation with the request ID `answer:<question>`.

An item waiting on a question holds only that item. Every other item keeps moving, which is what the Mac chat could not do. The pipeline asks only what the merge policy reserves, such as an image rebuild, secrets, the egress allowlist or a waivable hold, plus what the person chooses to keep, such as approving briefs. A judgment thread that cannot decide answers "ask the person" with its reasons, and that becomes a question too.

This overlaps the dashboard wave's AskUserQuestion card. Both are a card with options on a thread page. The pipeline's questions are records the control plane owns, so they need no hook in a pylon.

### Make each step idempotent

Each pipeline step derives what to do from the records that exist, as `queue.ts` derives each predecessor's state on every pass instead of storing it. Starting a builder is guarded by the item's request ID, as a queued start is guarded by its thread ID. Starting a judgment thread uses an ID derived from the item and the question, so a pass after a crash finds the thread it started. Archiving a thread that is already archived changes nothing.

## Build order

Each pull request delivers something on its own. The verify pylon, under the roadmap's Next, comes first, as the roadmap says, because the pipeline cannot check a deploy live without it.

Steps 1 to 5 and step 7 have landed: [nexus#169](https://github.com/ramtinJ95/nexus/pull/169), [nexus#168](https://github.com/ramtinJ95/nexus/pull/168), [nexus#177](https://github.com/ramtinJ95/nexus/pull/177), [nexus#171](https://github.com/ramtinJ95/nexus/pull/171) with [nexus#175](https://github.com/ramtinJ95/nexus/pull/175), [nexus#172](https://github.com/ramtinJ95/nexus/pull/172) and [nexus#180](https://github.com/ramtinJ95/nexus/pull/180). Node diagnostics, which step 8 needs, landed in [nexus#174](https://github.com/ramtinJ95/nexus/pull/174). Step 6 is dropped under the decision of 2026-10-28, and the list keeps its number so that the numbers of the steps after it do not change.

1. **A request ID on thread starts.** `POST /v1/threads` accepts an optional `requestId`, stores it, and returns the same thread for a repeated one. It also accepts `message` on an immediate start and delivers it as the first message under a request ID derived from the thread, so a start and its brief succeed or retry together. It makes every client's retried start safe, the Mac chat's included. Verify with an API test that posts the same start twice and gets one thread and one first message, and one that posts a different body under the same ID and gets a conflict.
2. **An event for a linked pull request.** Add `pull-request.linked`, written in the same transaction as the PR watch's link. Clients following the stream learn of a new pull request at once. Deploys need no new event, since `release.changed` already fires on every node's report. Verify with a registry test that it fires once per link, and a follower test against the local stack.
3. **Archive what landed.** A rule in the review loop's last step archives the builder and the reviewer once a review ends `landed`, and changes "only the person archives" in the design. It ends one manual chore. Verify with a review-loop test that drives a review to `landed` and sees both threads archived, and that a review held for the person archives nothing.
4. **Nudge a builder that stopped short.** A builder whose turn ended with no linked pull request, in a project with auto-review, gets a fixed nudge through the inbox, and after two nudges its attention goes to the person. The PR watch links pull requests only every two minutes ([`main.ts`](../../src/control/main.ts) line 198), so a builder that opened its pull request just before its turn ended looks stalled for up to two minutes. The rule counts a turn as stalled only once the registry holds the branches the builder pushed before the turn ended, which the probe reports up to two minutes after a push, and a PR watch pass that started after that has finished. A search of GitHub alone is not enough: on 2026-10-28 the pass searched before the registry had the branch, and nudged a builder whose pull request was open. It fixes the third stall of 2026-10-25. Verify with a test on a fake harness thread whose turn ends without a pull request, a test where the pull request opens just before the turn ends and gets no nudge, and on the local stack with a Claude worker told to stop before pushing.
5. **Question records and the decision card.** A question table, a person-only answer route, the dashboard card and `nexus show` output, with no asker yet besides tests. Verify with API tests for who may answer, and the verify-nexus skill driving a card to an answer on the dashboard.
6. **Dropped: host-side drive tools.** [nexus#179](https://github.com/ramtinJ95/nexus/pull/179) built them and was closed without landing, because a thread never drives another thread.
7. **Pipeline items.** An item table, the pass that turns an item into a queued thread, and the dashboard's pipeline view, with every phase derived from existing records. The person can line up a roadmap's worth of items that start themselves. Verify with a pass test over every phase, and with the local stack running two items where the second waits on the first.
8. **Judgment threads.** For a failed pylon, the pipeline starts a harness thread with no tools and no pylon. Its brief holds the failure, the tail of the controller log that the failure ends with, and the node's health, which node diagnostics already serve. The control plane reads a fenced answer (retry, retry on another node, or ask the person), acts on it, and archives the thread. The new parts are a conversation created with an empty tool list, through pi-durable's `configure`, and a thread with no pylon. Verify with a scripted model in the harness tests, and a forced pylon failure on the local stack.
9. **Planning proposals.** A harness thread the person opens to plan ends a turn with a fenced block of proposed items. The control plane records each proposal and asks the person one question per proposal, and an answer to add it makes a pipeline item with the person as its adder. The planning thread cannot add an item, call any route or start a thread: it has no `nexus_item` and no other Nexus tool. This is shape 3 of [How planning works under the rule](#how-planning-works-under-the-rule), and it waits for the person's call on that shape. Verify on the local stack by having it propose two items from a roadmap section, answering one card to add and one to drop, and checking that exactly one item exists, added by the person.

## Decisions for the person

The person decided these on 2026-10-28, as [the design's decision table](../design.md#decisions) records: to take this page's recommendation over a long-lived coordinator agent, that briefs start builders on their own unless a project asks for approval, that the review loop archives a landed builder and its reviewers, that the pipeline runs for project `nexus` first, and that a thread never drives another thread. The last one removed the questions about a cap on children and about drive tools for Claude workers.

Still open:

- How planning works: the person adds every item, a planning thread's proposals become items on their own, or the person accepts each proposal on a card. [How planning works under the rule](#how-planning-works-under-the-rule) weighs them and recommends the card, with the person's own `nexus item add` kept.
- Whether the always-on agent under [Later](../roadmap.md#later) is the planning thread, or stays a separate item. Under the decision it may propose work, but it never starts, messages or waits on another thread.
