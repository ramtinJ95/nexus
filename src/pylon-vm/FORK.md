# pylon-vm: a hard fork of pi-sandbox

This directory is a fork of pi-sandbox, MIT-licensed, by Igor Warzocha. Its licence is in [LICENSE](LICENSE).

- Upstream repository: https://github.com/IgorWarzocha/howaboua-pi-stuff
- Path: `packages/pi-sandbox/src`
- Commit: `187a70d621ccc99b119166e55fcd568e5b4f605e`

Nexus owns this code and does not track upstream. pi-sandbox stays the reference to compare designs against. The pi extension entry (`index.ts`) and the changelog tool (`changelog.ts`) were not copied.

Nexus calls it only through `run` in `client.ts`, from `src/pylon-vm-backend.ts` and `src/pylon-vm-templates.ts`. The probe's end of the host bridge (`src/probe/pylon-api.ts`) takes its socket path and header name from `host-bridge.ts`. Changes from upstream:

- The controller is started from `daemon.ts` with Node's type stripping, so there is no `dist/` build.
- `run` takes the state root as an argument instead of reading `PI_SANDBOX_HOME`.
- `create` and `prepare` take a typed config object, not a YAML path. The YAML config loader is gone. The guest's services file, `.nexus/services.yaml`, is read with Nexus's own parser, `parseServicesFile` in `src/project.ts`, and the service schema is its `serviceDecl` with upstream's defaults on top, so a pylon accepts exactly the files the rest of Nexus does. Upstream's `review: false`, top-level config keys, a `cwd` outside the repo and any `NEXUS_*` env name are refused.
- `create` always takes its config, plus optionally the path of a prepared template's disk, which it copies in (as a reflink where the filesystem has them). Upstream names a template and reuses its recorded config. Nexus publishes prepared templates into its own artifact store (`src/artifacts.ts`), so records carry no template name.
- `create` builds a new instance in a hidden staging directory and renames it into place, so a crash never leaves an instance directory without its record and intent.
- `destroy` renames the instance to a hidden tombstone before removing it, also sweeps a leftover staging directory, and succeeds when the instance is absent. `list` skips hidden directories, removes tombstones a dead destroy left behind, and drops an instance destroyed while it was listing.
- `stop` treats a failure anywhere before its checkpoint completes like a failed checkpoint: the VM is shut down and the instance is `interrupted`, instead of a controller left in `stopping`.
- Every path that closes the VM, a `stop`, a `destroy` or a failed controller, first ends the guest actions already let in, such as an `exec` or `exec-status`. It aborts their waits and Gondolin file operations, waits up to 5 s for them to settle, and logs any it closes the VM under. A stop with any still in flight then closes access and the VM without a checkpoint, as `interrupted`: one may be half done, such as a `write-files` half installed, or hold Gondolin's file slot, which every later guest command waits for, since Gondolin cannot abort a file write that awaits the guest's answer. Those actions run beside the lifecycle queue, and Gondolin never answers a file operation that reaches a VM as it closes, so upstream could leave one hanging until its client gave up, 180 s for the probe.
- Gondolin runs at most 64 guest commands at once, and counts one until the guest answers it, also after the host stopped waiting for it. The controller counts them the same way: a command's wait still ends after its timeout plus 10 s, but the command keeps its slot until the guest answers. While the VM runs, the controller starts a command only while fewer than 48 are outstanding, and the next one waits for a slot, within its own deadline. A stop refuses the commands still waiting, so the commands it runs always find room. Upstream aborted the wait through Gondolin, which left the command running in the guest uncounted, so reads against a slow guest that timed out and were asked again could fill every slot, and the stop that followed failed before its checkpoint.
- Whether setup ran is recorded on the disk, in `/var/lib/pi-sandbox/setup.json`, with the instance's name and creation time and any setup error, not as `fresh` and `setupError` in the intent. The record is in a checkpoint exactly when setup's work is, so a controller that dies before its first checkpoint reruns setup, and one that dies after it does not. A template's disk carries its build's record, so a pylon booted from it still runs its own setup. A config with `retrySetup` records only a setup that succeeded, so every boot reruns a failed one. Upstream keeps both in `intent.json`, which can disagree with the disk after a crash. An intent in that older shape fails to parse, so its pylon fails to boot.
- Records carry `labels`, which `inspect` and `list` return, and the status carries `bootedAt`.
- The hooks that ran `.agents/setup` and `.agents/resume` as root from the workspace are gone.
- The pi extension's help text and input helpers in `contracts.ts` are gone.
- `create`, `prepare` and `start` take a boot spec (`bootSchema` in `contracts.ts`): CPUs and memory, whether the guest gets nested virtualization, the HTTP allowlist, secret values with the hosts each may go to, git SSH remotes with the node's key, files to write and hooks to run. The client writes it to the new controller's stdin, so it is never in `record.json`, `status.json`, the controller's environment or its log. An instance whose controller already runs keeps the spec it booted with. The record's config lost `profile`, `resources` and `network`, and the `profiles` table is gone. `status` reports the resources of the current boot.
- Secrets reach `createHttpHooks`, so each value is substituted only in requests to its own hosts, and no value is written into the guest, its disk or the controller's log. Every boot rewrites `/etc/profile.d/nexus-secrets.sh`, which exports the new placeholders to login shells. A granted host that echoes a request header back in its response still shows the value to the guest. That is inherent to substitution at a proxy, so secrets are granted only to hosts that do not reflect credentials.
- Git over SSH uses Gondolin's SSH egress (`network.ts`). The host terminates the guest's SSH and authenticates upstream with the node's key, checked against the node's known_hosts. Its exec policy lets through only the exact commands git sends to fetch from and push to the spec's repositories, `git-upload-pack '<path>'` and `git-receive-pack '<path>'` with the path spelled as in the URL, because Gondolin forwards the command upstream unchanged. Every boot writes `/etc/ssh/ssh_config.d/nexus.conf`, which turns off host key checking in the guest, because the guest's only SSH peer is the host's proxy.
- Every boot sets the guest's root disk to write-through in `/sys/block/vda/queue/write_cache`, so the guest sends no flushes, and a stop sets it back to write-back before its `sync`, which then flushes. A stop that cannot set it back fails before its checkpoint, like any other failure there. Gondolin runs QEMU's drive in its default writeback mode, where each guest flush is an fdatasync on the host, and a boot never reuses the overlay a running VM wrote to, so those flushes protected nothing and made every fsync in the guest wait on the host's disk.
- A boot whose spec sets `resources.nestedVirtualization` runs the image's `/usr/local/libexec/nexus/nexus-kvm` as root right after the VM starts, which loads the KVM modules and opens `/dev/kvm` to `user`. When it fails, the boot fails with its output, so a node whose host passes no nested virtualization through refuses the pylon at once rather than leaving its stack to find out. Upstream has no such step.
- Every boot writes the spec's files with their owner and mode, then runs the spec's hooks one at a time to completion, before setup or resume. A hook that fails is logged and does not fail the boot.
- `resume` runs on every boot from an existing disk, so the first boot from a template disk runs it after that boot's setup, and a boot from no disk, which ran the whole setup, does not. Upstream also runs it right after setup. Its outcome is one `resume:` line in the controller log, with the exit code, also when it outlives the boot's 10 s wait and finishes in the background. A failed resume still does not fail the boot.
- `write` is replaced by `write-files`, which writes several files with owner and mode and makes missing parent directories as the owner.
- `stop` of an instance whose controller died (`interrupted` or `failed`) settles it as `stopped` on its last completed checkpoint, or on no disk, so the next start boots fresh. Upstream returns its offline status and leaves it for a `start`.
- Every request to a controller opens its own connection. Upstream uses Node's default agent, which keeps connections open, and a connection that carried a request in flight when the controller stopped still reaches it after it removes its socket. A wake soon after a pause then reached the stopped controller, so `start` returned its inspect instead of launching a new controller, and those requests kept the stopped one alive.
- The controller's `controller.pid` and the launch lock's `owner` hold a process identity (`identity.ts`): the PID, the process's start time and the host's boot ID, from `/proc` on Linux and `ps` and `sysctl` on macOS. A process is alive only while all three match, so a reused PID or one from before a host reboot reads as dead. Each file is written to a temporary file and renamed in, so a client never reads one half-written. Upstream records only the PID. An instance in `starting` whose controller has not published its PID yet is `unavailable` while the launching client lives, instead of `interrupted`.
- Every boot's HTTP hooks answer `http://nexus.pylon`, the guest's NEXUS_API, from the probe (`host-bridge.ts`). Gondolin runs the `onRequest` hook before its allowlist and IP checks, and a Response it returns short-circuits both, so the host needs no allowlist entry and never resolves. The controller forwards the method, path, body and content type to the probe's socket, `host-bridge.sock` in the state root (the boot spec's `hostBridge`), with the instance name in `x-nexus-pylon`, and drops every guest header, so the guest holds no token and cannot name another pylon. With a custom `onRequest`, Gondolin skips its pre-body policy check and applies the allowlist after the hooks instead, so a request to a blocked host is refused after its body is read rather than before.
- Gondolin's HTTP egress runs on undici 7.30.1, which `package.json` forces with an npm override, although Gondolin 0.13 asks for 6.x. The last 6.x, 6.29.1, can reject a promise no code holds when Gondolin evicts an origin's connection pool: if the pool closes with requests still queued, it closes again a connection that already finished closing. A guest whose requests fail upstream while others to the same host wait could therefore crash the controller with `ClientDestroyedError`, which killed the pylon and failed its thread. 7.x skips connections that are already closed. Drop the override once Gondolin depends on undici 7 or newer.
- The controller logs each error its server emits after it listens, such as a failed accept, and keeps serving: the server is still listening, the VM lives in the controller's process, and nothing restarts a controller that exits, so its pylon would only be `interrupted`. Upstream left its startup listener on the server, so the first such error went nowhere and the second crashed the controller.
- A port linked with the `preview` action is written to `linked.json` in the instance directory, beside `services.json` and `adhoc.json`, and every boot opens its portal again, so a linked preview survives a pause and wake. Upstream keeps linked ports in memory only, and the control plane keeps a preview for the thread's life, so after a wake the preview showed the waking page forever. The port is saved before the action answers, so a failed save fails the action and a retry saves it. The action refuses Nexus's own ports, `reservedPorts` in `src/project.ts`.
- The `unpreview` action, which upstream lacks, unlinks a port the `preview` action linked: it saves `linked.json` without the port before it drops the route and closes the portal, so a failed save leaves the port linked and a retry removes it. A port that is not linked succeeds. A port whose preview a service owns is refused with the service's name, and so is a port whose linked name `port-<port>` a service holds, because the caller drops the preview of that name. A controller started before this action refuses it until the pylon's next wake.
- Every boot starts the loopback relay (`relay.ts`) before any service, and each preview's ingress route, a service's or a linked port's, points at a relay port from 700 to 799 instead of at the port. The relay connects to the port on 127.0.0.1, or on `::1` when nothing listens there, because Gondolin's ingress dials only 127.0.0.1. Upstream cannot preview a server bound only to `::1`, which is how Node 17 and later bind `localhost`. A preview is routed only once the relay's status file confirms that its relay port carries to its port, and a dropped preview's route goes before the relay hears its relay port is free, so a route never reaches another app or a listener that is not the relay. A preview without a confirmed route reports why in its fact's `unrouted`. Readiness and health checks ask the port in the guest, on both addresses and within 2 s, not through the ingress, so a service without a preview has no route. A declaration may not fix 22 or a relay port, a preview past the 100th is refused before anything is saved, and a wake logs and skips restored entries on those ports rather than failing, and leaves one past the 100th unrouted until a relay port frees up.
