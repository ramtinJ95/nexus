# S7 — cross-node Gondolin disk checkpoint

**Verdict: PASS with caveats.** A fresh Intel → AMD → Intel disk-checkpoint round trip preserved both non-root markers. Relocating the assets and explicitly rebasing also worked. This is cold disk restart, **not live migration or process/RAM continuity**. Transfer interruptions required a staged copy through the Mac.

Run: 2026-10-22. This replaces the earlier environment-blocked attempt; its reconnaissance logs remain. `RESULTS.md` was deliberately not edited, so its S7 summary still describes that earlier attempt.

## Question

Does a fresh, login-free Gondolin checkpoint written on infra-testbench (Intel i9-9880H) boot on rj-firebat (AMD Ryzen 7 255), with identical base assets at the same absolute path? Does the return trip work? Is the same-path convention necessary?

## What ran

- Native **Gondolin 0.13.0**, **Node 26.8.1**, **QEMU/qemu-img 11.1.1**, QEMU/KVM, two vCPUs, 3 GiB RAM, writable COW root disks. No Docker was needed. Testbench kernel: `7.2.9-arch1-Watanare-T2-1-t2`; Firebat kernel: `7.2.5-3-omarchy`.
- On Firebat, `npm ci --ignore-scripts --no-audit --no-fund` used the repository's unchanged `evidence/package.json` and `evidence/package-lock.json` under `~/nexus-spikes`, never globally. npm added **106 packages in its reported 3 seconds**. The lock also includes the earlier pi-durable/pi-env dependencies; S7 only used Gondolin. Lifecycle scripts were disabled; no audit fix or npm update ran.
- The lock's SHA-256 matched locally and before/after npm: `047f267056a1f576ad15525788bac4f870fcf1bc4c43f1f256475c783edc5a45`. The installed Gondolin package reported **0.13.0**.
- Existing S1 Debian assets were copied, preserving sparse files, from testbench's `state/debian-assets` into **`~/nexus-spikes/s7/assets`**. Both hosts have the same absolute home path, giving an identical backing filename. Base build ID: **`836cdc05-a609-5162-8f18-320834da7d20`**.
- `s7-vm.mjs create` booted a **new** VM from that base. S1's base predates S2 provisioning, so it created a password-locked `user`, UID/GID 1000, and `/home/user/workspace`. No guest packages were installed. A guest command wrote a random marker **as `user`**, then `vm.checkpoint()` stopped and saved `s7/intel.qcow2`.
- HTTP allowlist: **empty**. No logins, model calls, API keys, guest SSH, or network provisioning. The test checked that the fresh guest's user/root `.claude` and `.pi` paths were absent, without reading authentication files.
- All six assets, the Intel checkpoint, and marker expectations were hashed on both hosts before resume. `VmCheckpoint.load(...).resume(...)` on Firebat verified UID 1000, exec, and the Intel marker, wrote a second random marker as `user`, then saved `s7/amd.qcow2`.
- That AMD checkpoint was hashed, copied back, verified, and resumed on testbench. Both markers survived. Return/relocation VMs were closed without retaining their disposable overlays.
- The optional path test renamed Firebat's assets to `s7/relocated-assets`, verified all six hashes, asserted the old directory was absent, and ran:

```sh
qemu-img rebase -u -f qcow2 -F raw \
  -b "$HOME/nexus-spikes/s7/relocated-assets/rootfs.ext4" \
  "$HOME/nexus-spikes/s7/amd.qcow2"
```

Resume with that explicit new `sandbox.imagePath` preserved both markers. The unsafe/header-only rebase is appropriate here **only because backing bytes were verified identical**, not for substituting a different base image.

The credential-bearing **`~/nexus-spikes/state/s2-debian.qcow2` was never opened, copied, booted, modified, or deleted**. S7 used neither the S2 VM options module nor its checkpoint path.

## Measurements and observations

**Single observations, not performance benchmarks.** Cold times start immediately before create/resume and end after the first successful guest `uname`/CPU exec; they exclude transfer and subsequent marker checks. Host page caches were not flushed.

|---|---:|---|---|
| Fresh Intel VM | **3.870 s** | Intel Core i9-9880H @ 2.30 GHz | Locked UID 1000 user; Intel marker written/read |
| Intel checkpoint → Firebat | **2.365 s** | AMD Ryzen 7 255 w/ Radeon 780M Graphics | Intel marker intact; AMD marker written/read |
| AMD checkpoint → testbench | **3.877 s** | Intel Core i9-9880H @ 2.30 GHz | Both markers intact |
| Relocated assets + explicit rebase, Firebat | **2.086 s** | AMD Ryzen 7 255 w/ Radeon 780M Graphics | Both markers intact; old backing path absent |

The guest has Debian userspace with the S1 Alpine boot artifacts. Its visible CPU model changed with the host; this did not prevent disk restart. Software compiled for vendor-specific CPU features was not tested.

### Transport caveats

The requested `$TMPDIR/nexus-%r@%h` socket was too long on the Mac for testbench's expanded hostname. After explicit approval, subsequent commands used **`ControlPath=/tmp/nx-%C`**, `ControlMaster=auto`, and `ControlPersist=60m`. Connections were reused per host; no Tailscale check was requested on the resumed run. No SSH/tailnet config was edited, and the Mac work-tailnet CLI was never used.

The initial direct `ssh source cat | ssh destination tar` attempt and retry ended with **255**; a diagnostic repeat ended with **2**, `gzip: stdin: unexpected end of file` and tar unexpected EOF. The incomplete destination was **not booted**. A standalone source download delivered the complete 111,001,577-byte archive. The final transfer script stages it in a Mac temporary file, validates gzip and SHA-256, then sends the second SSH leg. All destination file hashes matched before use. **The interruption's root cause is unknown**; a successful staged copy does not establish streaming reliability.

Two testbench audit invocations also ended with 255 partway through checksum output. A bounded, output-file-backed retry completed with exit 0 and verified all six original S1 assets. Partial logs are retained, not treated as completed verification.

## Reproduction and evidence

The scripts fail rather than overwrite an existing S7 workspace or Firebat `~/nexus-spikes`. Runtime limits: 180-second outer timeout, 60-second boot timeout, 30-second exec deadlines.

`s7-ssh.sh` wraps this command-line-only transport (substitute `rj-firebat` as needed):

```sh
ssh -o BatchMode=yes -o ConnectTimeout=15 \
  -o ProxyCommand='nc -X 5 -x localhost:1055 %h %p' \
  -o ControlMaster=auto -o ControlPath=/tmp/nx-%C \
  -o ControlPersist=60m infra-testbench
```

Every runtime/setup action in `s7-remote.sh` uses the earlier scratch environment:

```sh
export XDG_CACHE_HOME="$HOME/nexus-spikes/cache"
export PI_SANDBOX_HOME="$HOME/nexus-spikes/state"
export npm_config_cache="$HOME/nexus-spikes/npm-cache"
export TMPDIR="$HOME/nexus-spikes/tmp"
cd "$HOME/nexus-spikes"
```

From the repository root, after read-only dependency verification:

```sh
# Stop on any failed step; never resume an unverified transfer.
set -euo pipefail
bash spikes/s7-ssh.sh infra-testbench 'bash -s -- init-testbench' < spikes/s7-remote.sh
bash spikes/s7-ssh.sh rj-firebat 'bash -s -- init-firebat' < spikes/s7-remote.sh
COPYFILE_DISABLE=1 tar -C spikes/evidence -cf - package.json package-lock.json |
  bash spikes/s7-ssh.sh rj-firebat 'tar -xf - -C "$HOME/nexus-spikes"'
for host in infra-testbench rj-firebat; do
  bash spikes/s7-ssh.sh "$host" 'cat > "$HOME/nexus-spikes/s7/s7-vm.mjs"' < spikes/s7-vm.mjs
done
bash spikes/s7-ssh.sh rj-firebat 'bash -s -- npm' < spikes/s7-remote.sh
bash spikes/s7-ssh.sh infra-testbench 'bash -s -- create' < spikes/s7-remote.sh
bash spikes/s7-ssh.sh infra-testbench 'bash -s -- pack-forward' < spikes/s7-remote.sh
bash spikes/s7-transfer.sh forward
bash spikes/s7-ssh.sh rj-firebat 'bash -s -- verify-forward' < spikes/s7-remote.sh
bash spikes/s7-ssh.sh rj-firebat 'bash -s -- forward' < spikes/s7-remote.sh
bash spikes/s7-ssh.sh rj-firebat 'bash -s -- pack-return' < spikes/s7-remote.sh
bash spikes/s7-transfer.sh return
bash spikes/s7-ssh.sh infra-testbench 'bash -s -- verify-return' < spikes/s7-remote.sh
bash spikes/s7-ssh.sh infra-testbench 'bash -s -- return' < spikes/s7-remote.sh
```

## What this means for Nexus

**Disk checkpoint mobility across these Intel/AMD nodes is feasible** with the tested x86-64 image, matching Gondolin/QEMU versions, and explicit asset provisioning. Pre-positioning immutable, checksum-verified assets avoids copying the large base on every move.

**Identical absolute paths are a convenience, not a hard requirement** for the tested explicit rebase workflow. Nexus should resolve assets by build identity, verify backing bytes, and make path repair explicit. Installed Gondolin 0.13.0 source also contains resume-time backing-path repair; this spike tested explicit `qemu-img rebase -u`, not automatic repair by itself.

Nexus still needs agent/terminal restart and reconnect: checkpoints do not preserve running processes, RAM, sockets, or live CPU state. This single round trip does not establish arbitrary CPU-feature or cross-version compatibility, crash consistency, parallel access safety, or reliable streaming transport. Verify complete transfers before publishing or booting checkpoints.
