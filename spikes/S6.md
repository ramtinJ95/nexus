# S6 — many HTTPS preview ports through one loopback gateway

**Verdict: PASS with caveats.** All **six simultaneous HTTPS listeners** worked through one loopback gateway. Every successful request preserved its preview port in `Host`. Across three paired no-warm-up/warm-up rounds, there were **0/18 first-Mac-request timeouts without warm-up and 0/18 with warm-up**. S4's first-request hang did **not** recur; its cause remains unknown. This establishes six-port feasibility, not an arbitrary listener limit or a fix for that transient.

## Question

Can one node publish multiple pylon previews using `tailscale serve --bg --https=<port>`, all forwarding to one loopback gateway, with the destination port preserved in `Host` for routing? Does a host-side warm-up prevent initial Mac HTTPS hangs, and can one preview be removed independently?

## What ran

Run: **2026-10-22**, started **11:58:14 UTC**. Target: **infra-testbench only**, same Arch Linux home-lab node and scratch environment as S4. No pylon VM was needed: this isolates Serve → host gateway, without Gondolin's additional proxy hop.

- Host Tailscale **1.102.3**, commit `9329c3677031109ff6d0b80abee0cddc8f35ff6f-dirty`; Python **3.14.7**; curl **8.22.0**. Mac curl **8.7.1**. Full version output is in the transcript.
- First remote operations captured `tailscale serve status` and `tailscale serve status --json`. Original text: `No serve config`; original JSON: `{}`. Both were saved before creating scratch or changing Serve.
- `s6-host.py`: one Python stdlib HTTP server bound **only to 127.0.0.1:18090**, under `~/nexus-spikes/s6/`. Every GET returns JSON containing the received `Host`. Logs contain only a synthetic probe path, `Host`, and `x-forwarded-proto`; identity headers and client addresses are never enumerated, logged, or returned.
- `s6-run.py`: Mac-side orchestration, 20-second curl timeout, normal certificate verification, fresh curl process per request, no automatic retries or insecure TLS flags. The transferred host script's SHA-256 was checked before execution.
- `s6-analyze.py`: local evidence validation and reproducible tables; joins every successful response to exactly one gateway event by synthetic request ID, verifies the correct `Host` and scheme, configuration isolation, cleanup, and script syntax.

All SSH calls used exactly this route; neither SSH configuration nor the Mac's work-tailnet CLI was touched:

```sh
ssh -o BatchMode=yes -o ConnectTimeout=15 \
  -o ProxyCommand='nc -X 5 -x localhost:1055 %h %p' infra-testbench
```

Every remote invocation first exported the S4 environment and changed directory:

```sh
export XDG_CACHE_HOME="$HOME/nexus-spikes/cache"
export PI_SANDBOX_HOME="$HOME/nexus-spikes/state"
export npm_config_cache="$HOME/nexus-spikes/npm-cache"
export TMPDIR="$HOME/nexus-spikes/tmp"
cd "$HOME/nexus-spikes"
```

For **each of three rounds**:

1. Add all six entries back to back, in this order: **8443, 10000, 10001, 10002, 18443, 40000**. Each uses `tailscale serve --bg --https=<port> http://127.0.0.1:18090`.
2. Without any host HTTPS warm-up, fetch twice from the Mac per port, in that same order. Each request uses `curl --socks5-hostname localhost:1055 --max-time 20 -sS https://infra-testbench.example.ts.net:<port>/?probe=<synthetic-id>` plus curl's status/timing write-out.
3. Remove each entry separately with `tailscale serve --https=<port> off`; verify empty Serve JSON.
4. Add all six again. Run **one host-side GET per port** to its own tailnet HTTPS name, then repeat the two Mac requests per port. Host curl uses no SOCKS proxy.
5. Remove individually again and verify empty JSON. In round 3, first perform the independent-removal test below.

Thus: **six add/remove cycles**, **36 additions**, **72 Mac timing requests**, and **18 host warm-ups**. All six listeners coexist during every timing batch; requests themselves are sequential, not a concurrent-load benchmark. No intentional sleeps between additions or before no-warm-up probes; SSH/process overhead and earlier ports' requests still introduce delay. Warm-up of all six precedes the warm batch's Mac probes.

**No observed warm-up benefit.** Both first-request groups had zero hangs. These small, fixed-order, same-session samples do not demonstrate that warm-up prevents failures or that the true timeout rate is zero. S4 had already used this hostname; no certificate cache, daemon, SOCKS daemon, or underlying connection state was reset. The first request of this run, port 8443 at 0.114307 s, is a **single observation**, not evidence about pristine first-ever publication.

### Gateway Host and forwarding scheme

**95/95 successful requests** (72 Mac timing probes, 18 host warm-ups, 5 surviving-port probes) had exactly `infra-testbench.example.ts.net:<requested-port>` in both the response and the matched gateway log. Every gateway event had **`x-forwarded-proto: https`**. The removed-port request produced no gateway event.

Example, with no identity fields captured:

```json
{"host":"infra-testbench.example.ts.net:10001","request":"/?probe=r1-cold-mac-1-10001","x_forwarded_proto":"https"}
```

This demonstrates the routing discriminator reaches a single gateway; it does **not** implement pylon dispatch or test Host spoofing/authentication. S4's guest saw `x-forwarded-proto: http` after an additional Gondolin ingress hop; S6's direct Serve → host gateway result does not invalidate that observation or certify the full proxy chain.

## What Nexus's probe should do

1. **Allocate and track owned ports**, checking existing Serve configuration before mutation. A successful command means configured, not externally ready. Do not assume all possible ports or unlimited listeners work from these six observations.
2. **Probe the actual tailnet HTTPS URL from the intended client path**, verifying TLS, HTTP success, and the expected preview/pylon marker. Validate the exact hostname and allocated Host port at the trusted loopback gateway; reject unknown mappings rather than routing to a default pylon. Host preservation is a routing property, not an authorization guarantee.
3. **Use bounded readiness retries and expose failures.** A reasonable initial policy is a 60-second overall deadline, each request capped at 20 seconds and remaining budget, with short bounded backoff. Record attempt, elapsed time, HTTP/curl result, and routing marker. This policy is a recommendation, not tested here; preserve S4's transient as an unresolved failure mode.
4. **Treat host-side warm-up as optional diagnostic work, not proof of readiness or a demonstrated fix.** This run provides no reason to require it; successful host curl cannot substitute for a successful client-path probe.
5. **Check forwarding semantics at the final application hop**, and keep header logging allowlisted. Direct Serve supplied `https` here, while S4's extra proxy changed the final scheme.
6. **Remove only the owned entry and verify isolation.** Probe that its URL stops and surviving previews remain healthy; preserve unrelated Serve configuration. Never reset the node's shared Serve configuration.
